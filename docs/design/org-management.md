# 조직·사원 관리 첫 구현 계약

2026-10-24 Phase 5 착수 요청에 따른 [PRD F03](../prd.md)의 첫 작업 단위다. 기존 [논리 모델](data-model.md), [보안](security.md), [화면 계약](screens.md)을 구체화한다. 기능 구현과 로컬 DB·설정·검증 후 커밋·Push는 승인 범위이며 외부 서버·배포는 제외한다.

## 범위와 선택

조직 계층·사원 기본정보·적용일별 소속 이동을 함께 구현한다. 목록만 만드는 안은 업무 연결이 부족하고, 계정 초대·역할·승인자 연결까지 한꺼번에 만드는 안은 인증과 승인 영역을 함께 변경한다. 이번에는 소속과 재직의 연결을 완성하고 나머지를 독립 단위로 남긴다. F03 전체나 MVP 전체 완료로 표시하지 않는다.

- 조직: 코드·이름·상위 조직·활성 상태, 등록·조회·수정. 코드 불변, 같은 고객사 부모, 자기 부모·순환 금지.
- 사원: 불변 사번·이름·입사일·마지막 재직일·활성 상태, 등록·검색·조회·수정. 비활성 사원도 사번을 재사용하지 않는다.
- 소속 이동: 오늘 이후 적용일의 새 배정을 추가하고 기존 열린 구간은 같은 트랜잭션에서 종료한다. 마지막 배정 시작일보다 늦은 날짜만 허용한다. 날짜를 덮어쓰거나 과거 조직을 삭제하지 않는다.
- 감사: 변경 전후 최소 값·주체·사유·시각·명령 ID를 업무와 함께 저장한다. 감사 조회 UI는 후속 F12 단위다.
- 계정 초대·비밀번호·역할 수정·승인자 배정·근무 일정·출퇴근·휴가·계산은 별도 단위다. 사원 등록으로 계정이나 임시 비밀번호를 만들지 않는다.

## 업무 경계

1. `ATTENDANCE_ADMIN`만 같은 고객사의 목록·상세·변경에 접근한다. 세션뿐 아니라 명령 트랜잭션에서 고객사·계정·재직·권한·auth_version을 다시 확인한다.
2. 모든 변경은 고객사 단위 transaction advisory lock → 현재 권한 → 명령 재시도 → 대상·버전 검증 → 업무·감사 순서다. 초기 규모에서 계층·이동·마지막 담당자 경합의 정확성을 우선한다. 장기 부하 검증은 별도다.
3. 마지막 유효 담당자의 비활성화·퇴사일 지정·재직 범위 축소는 다른 활성 계정의 재직 중이며 퇴사 예정이 없는 담당자가 있을 때만 허용한다. 미래의 무담당 상태도 보수적으로 차단한다.
4. 재직일·활성 변경은 연결 계정의 `auth_version`을 증가시켜 잠시 비활성화했다가 복구해도 옛 세션이 살아나지 않게 한다. 이름·소속 변경만으로 세션을 회수하지 않는다.
5. 일반 앱에는 계정 식별·활성·auth_version과 역할의 최소 조회, auth_version 열 갱신만 추가한다. 비밀번호·계정 생성·역할 쓰기·관리 권한은 허용하지 않는다. 인증 전용 DataSource를 업무에 재사용하지 않는다.
6. 활성 자식 조직이나 오늘/미래 소속 배정이 남으면 조직을 비활성화할 수 없다. 비활성 자식은 기존 비활성 부모를 그대로 유지해 이름을 수정할 수 있지만, 해당 부모 아래에서 재활성화하거나 비활성 부모를 새로 지정할 수 없다. 자동 이동·연쇄 삭제·과거 이력 삭제는 하지 않는다.
7. 소속 구간은 `[valid_from, valid_to)`이고 퇴사일은 포함이다. 새 적용일은 입사일 이후·마지막 재직일 이내여야 한다. 기존 소속 설정은 재직 정정 때 삭제하지 않으며, 재직 여부는 Employee를 함께 확인한다. 소속 배정 자체를 근로·재직 증거로 간주하지 않는다.
8. 같은 날의 배정 재작성·과거 소속 정정·예약 취소는 이 단위에서 제공하지 않는다. 미래 계획도 마지막 시작일 이후의 새 이동만 추가한다. 이 제한은 화면에 안내한다.

## 물리 구조

V1은 수정하지 않고 `V2__organization_management.sql`을 추가한다.

| 대상 | 계약 |
| --- | --- |
| `tna.organization` | tenant/id 복합 PK, code40 고객사 내 유일, name120, parent 복합 FK, active/version, 생성·변경자·시각 |
| `tna.employee` | 기존 열 유지, version·생성/변경 메타데이터 추가. V1 행의 과거 생성 주체/시각은 NULL로 보존 |
| `tna.employee_assignment` | tenant/id PK, employee/organization 복합 FK, 적용 구간·reason500·version·처리자·시각 |
| `tna.org_audit_event` | tenant/command_id 유일, actor 복합 FK, action·target_kind/id·input_hash64·reason500·before/after JSON text·발생/요청 추적 ID |

새 테이블은 ENABLE/FORCE RLS와 명시 SQL tenant 조건을 함께 적용한다. 앱은 필요한 SELECT/INSERT·허용 열 UPDATE만 사용하며 DELETE/TRUNCATE를 갖지 않는다. 감사는 추가만 허용한다. 소속 중첩은 [PostgreSQL btree_gist](https://www.postgresql.org/docs/18/btree-gist.html)의 UUID opclass와 daterange exclusion 제약으로 DB에서도 차단한다. trusted 확장은 migration 역할로 설치하며 Java 의존성은 추가하지 않는다.

## HTTP와 입력

| 경로 | 역할 |
| --- | --- |
| GET/POST `/admin/organizations` | 조직 목록·등록 |
| GET `/admin/organizations/{id}`, POST `/admin/organizations/{id}/changes` | 조직 상세·변경 |
| GET/POST `/admin/employees` | 사원 목록·등록 |
| GET `/admin/employees/{id}`, POST `/admin/employees/{id}/changes` | 사원 상세·재직 변경 |
| POST `/admin/employees/{id}/assignments` | 소속 이동 |

일반 Thymeleaf 폼으로 완결한다. POST에는 CSRF·UUID commandId, 변경에는 expectedVersion, 모든 변경에는 1~500자 사유가 필요하다. 이름·코드·사번은 공백 정리 후 각각120/40/40자 이내, 재직일은 입사일≤퇴사일이다. 소속 이동은 사원 version을 함께 증가시킨다. 목록은 50개씩 조회하고 다음 페이지 링크와 검색을 제공한다.

성공은303→상세 GET, 필드·업무 오류422는 입력을 보존한 폼, 범위 밖404, 오래된 version·같은 commandId의 다른 입력409다. UUID·날짜·버전 등 타입을 해석할 수 없는 형식 오류는 기존 화면 계약처럼400 안내 화면으로 응답한다. 같은 주체·명령·정규화 입력의 성공 재시도는 감사·업무 효과를 반복하지 않고 같은 대상 결과로 이동한다. 민감정보·SQL·전체 요청은 오류에 노출하지 않는다. 감사 저장·직렬화 실패도 업무와 함께 롤백한다.

## 검증 기준

- 실제 Testcontainers PostgreSQL: V1→V2 적용·최소 grants·FORCE RLS·복합 FK·중첩 제약·audit 불변·계정 비밀번호 차단.
- 조직: 타 고객사 부모/ID, 코드 중복, 자기/간접 순환, 비활성 부모, 자식·배정이 있는 비활성화, 동시 상호 부모 변경.
- 사원: 사번 중복·재사용, 재직일 경계, 버전 충돌, 마지막 담당자·동시 제거, 비활성 복구 후 세션 회수.
- 소속: 인접 구간·이력 보존·원자적 종료/추가, 과거/같은 시작일/중첩·타 고객사·비활성 조직·재직 범위 밖 거부.
- 명령: 같은 요청 재시도·키 재사용 충돌·감사 실패 시 업무 롤백·권한 회수 뒤 제출·CSRF·비관리자 차단·입력 이스케이프.
- 기존 로그인·세션·RLS 테스트 회귀, Docker 이미지 빌드·Compose V2 적용·로컬 HTTP 확인. 외부 서버·배포는 수행하지 않는다.
