# 보안·테넌트 격리 설계

2026-10-27 사용자의 외부 공개 데모 승인에 따라 `public-demo` 단독 프로필을 추가했다. 전용 합성 DB에서만 예약 계정을 사용하고 일반 local 프로필의 외부 제한·실고객 자료 사용 금지를 유지한다. 공유 계정의 사원/역할/재초대 변경은 서비스의 UUID 경계에서 거부한다. DB 최소 역할·RLS·CSRF·세션 검증을 완화하지 않으며 실제 배포와 검증 상태는 [Hostinger 진행 보고](../quality/hostinger-public-demo.md)를 따른다.

> 2026-10-28 결재선 확장 계약: 관리자 전용 정의/배정과 APPROVER의 실제 지정·본인 결정 조회를 분리한다. 사원별 결재선 → 기존 지정 승인자 → 오늘 소속 조직 결재선 순서이며, 선택된 상위 경로가 부적격이면 우회하지 않는다. 제출 당시 스냅샷·기존 배정 참조는 불변이고 현재 담당 재할당은 별도 이력이다. V13은 네 테이블의 tenant 복합 FK·FORCE RLS·불변 버전/스냅샷의 수정 금지와 기존 신청의 배정 참조 두 열 UPDATE 회수를 적용한다. 상세는 [결재선 계약](approval-routes.md), 실제 실행 결과는 [3단계 보고서](../quality/approval-routes.md)를 따른다. 아래 최초 설계의 미실행 표기는 당시 이력이다.

## 1. 범위와 신뢰 경계

기준일: 2026-10-24. [아키텍처](architecture.md)와 [데이터 모델](data-model.md)의 설계 계약이며, 보안 구현·침투 테스트 완료를 뜻하지 않는다. 범위는 온라인 반응형 웹·세션 인증·IP 기반 출퇴근·고객사별 단일 앱·공유 DB다. QR·PWA·오프라인·생체·GPS는 구현하지 않는다.

브라우저, URL·폼·헤더, 클라이언트 시각, 객체 ID는 신뢰 경계 밖에 둔다. 세션 검증 → 고객사·사원 상태 → 역할·객체 범위 → 트랜잭션 테넌트 → SQL 조건·RLS 순서로 검증한다. 운영자 권한은 고객사 업무 권한과 별도다.

## 2. 계정·로그인 전 테넌트 식별

- 고객사 계정은 회사 코드 + 이메일로 로그인한다. 계정은 한 고객사·사원에 귀속되고 다중 고객사 자동 연결·전환은 후속이다.
- 회사 코드는 자격 증명이 아닌 로그인 이름 공간이다. 로그인 전 입력 코드에서 얻은 고객사 ID는 인증된 업무 범위가 아니다.
- 로그인 전 조회는 회사 코드·고객사 상태의 최소 레지스트리와 해당 고객사의 자격 검증·토큰 소비 작업으로 제한한다. 근태·연차·조직 목록 조회를 허용하지 않는다.
- 전용 pre-auth 저장소 인터페이스는 허용된 로그인·초대·재설정 연산만 노출한다. 일반 업무 Mapper에 전달 가능한 인증된 범위 객체를 생성할 수 없다.
- 자격 검증 성공 후에만 서버 세션에 `account_id`, `employee_id`, `tenant_id`, `auth_version`을 결속한다. 폼·헤더의 tenant_id로 세션 소속을 교체하지 않는다.
- 고객사·이메일·계정·토큰 존재 여부는 일반화된 실패 문구로 응답한다. 계정·IP 조합 속도 제한과 실패 감사를 적용하고 비밀번호·토큰을 로그에 남기지 않는다.
- 비밀번호 제품 정책은 최소12자·최대128자이며 공백을 포함한 긴 암호문을 허용한다. 길이 검증을 해시 처리보다 먼저 하고 값·실패 원문을 로그에 남기지 않는다. 지원 길이를 묵시적으로 절삭하는 해시 구현은 사용하지 않는다.
- 비밀번호는 Spring Security의 버전 식별 가능한 단방향 해시를 사용하도록 설계한다. 실제 알고리즘·비용·Unicode 길이 처리는 선택 JDK와 자원에서 검증한다.
- 초대·재설정 토큰은 암호학적 난수256bit, 일회성·목적별 분리·해시 저장을 적용한다. 초대24시간·재설정30분의 제품 유효기간을 채택하며 법정 수치가 아니다. tenant·계정·목적이 다르면 사용할 수 없다.
- 초대 수락 때 기존 사원·이메일과의 결속을 확인한다. 토큰 소비와 비밀번호 설정·계정 활성화를 한 트랜잭션으로 처리한다.
- 운영자는 별도 로그인·세션 경로와 계정 저장소를 쓴다. 운영자 로그인으로 고객사 세션을 발급하거나 고객사 업무 승인자를 가장하지 않는다.

개발 단계 초대·재설정은 실제 수신자에게 보내지 않는 모의 메일 경로로 검증한다. 파일럿은 별도 승인한 메일 채널의 발신자·링크·실패·재발급·유출 방지를 검증한 뒤 개방한다. 운영 화면에서 비밀번호·재설정 토큰을 조회하는 기능을 만들지 않는다. 이번 문서 작업은 메일 채널 연결·외부 API 사용을 수행하지 않는다.

### 합성 로컬 데모 예외 (2026-10-26)

사용자 요청으로 `local`과 `local-demo`를 함께 명시한 개발 화면에서는 회사코드를 받지 않고 `admin / admin`만 받는다. 서버가 예약 합성 고객사·계정·사원을 선택하며 정상 DB 해시 검증과 정확한 `EMPLOYEE`·`ATTENDANCE_ADMIN` 역할 확인을 거친다. 별도 명시 CLI로만 자료를 준비하고 일반 비밀번호 정책·회사코드 인증·운영자 분리·RLS·CSRF·속도 제한·세션 현재성·자기 승인 차단은 유지한다. 프로필 경계·회수/충돌 시 미복원 계약은 [로컬 데모 설계](local-demo-login.md), 실제 결과는 [최종 보안 재검사](../quality/security-runtime-recheck.md)를 따른다. 이 공개 계정은 외부 배포·실고객 자료용이 아니다.

## 3. 역할과 객체 범위

| 주체 | 허용 범위 | 주요 차단 |
| --- | --- | --- |
| 직원 | 본인 기록·신청·잔여·결과 | 타인 ID 대입·대리 출퇴근·원천 수정 |
| 승인자 | 현재 지정된 대기 신청, 승인 검토에 필요한 대상 자료 | 자기 승인·재할당 전후 오래된 권한·범위 밖 팀원 조회 |
| 근태 담당자 | 소속 고객사의 조직·설정·기초 잔여·현황·감사·검토 출력 | 승인 우회·자기 승인·타 고객사·원천 덮어쓰기 |
| 대표 | 자기 회사 근무·신청 현황의 안전한 읽기 | 관리자 변경·원장 조정·재집계·감사·관리자 Excel, 미지정/자기 승인·타 고객사 |
| 서비스 운영자 | 고객사 상태·최초 담당자 연결·운영 감사 | 근태 일괄 조회·XLSX·대리 승인·일반 요청의 DB 관리 역할 |

직원·승인자·담당자 겸임은 허용하되 모든 결정에서 대상 사원과 작성자 모두를 승인자와 비교한다. 본인 신청은 별도 유효 승인자에게 배정해야 한다. 담당자 자신의 기초 잔여 등록·증감도 다른 담당자가 처리한다. 담당자가 대체 승인자를 지정할 때 사유·권한·대상·변경 전후를 기록하고 대기 건만 명시적으로 재할당한다. 자동 대결과 운영자 지원 열람은 후속이다. 마지막 활성 담당자를 제거하기 전에 대체 담당자를 연결한다.

퇴사·계정 비활성·고객사 이용 중지·역할 회수·비밀번호 재설정 시 `auth_version`을 갱신하고 기존 세션을 무효화한다. 매 요청에 상태·개정을 확인하며 XLSX를 만들기 직전에도 권한을 재확인한다. 취소된 권한으로 이미 열린 화면의 버튼을 눌러도 서버에서 거부한다.

2026-10-27 [권한 확장 1단계](../quality/identity-access.md)는 대표 `COMPANY_REPRESENTATIVE`와 별도 `CompanyReadAccess`를 추가한다. 공통은 필수이며 관리자/대표는 겸임 가능하고 APPROVER는 독립 기능이다. 회사 읽기는 공유 잠금과 현재 계정·재직·역할·세션을 진입/반환 전에 검증하며 기존 관리자 쓰기 경계를 확장하지 않는다. 본인 정보는 principal 대상만 조회한다. 대표 회사 목록은 자유 사유·이메일·IP·정정 원문·계산 증빙을 제공하지 않는다. 상세 스키마·HTTP·실제 검증은 연결 문서를 따른다.

### 조직·사원 배치와 조직장 2단계 구현 계약

2026-10-27 착수, 2026-10-28 `Asia/Seoul` 기준 [실행 계획](../superpowers/plans/2026-10-27-react-org-sheet.md)과 [조직 관리 계약](org-management.md#react-조직사원-시트조직장조직도-2단계-계약)을 따른다. 아래는 구현 경계이며 전체 검증·로컬 V12 반영의 수행 사실은 [별도 보고서](../quality/org-sheet-heads.md)로 확인한다. 1단계 결과를 새 코드·이미지의 동일 검증으로 옮기지 않는다.

- 조직·사원 bulk와 조직장 배정/종료는 현재 관리자만 변경한다. `tenant_id`는 principal에서 정하며 요청·헤더의 임의 tenant나 역할을 권한 근거로 신뢰하지 않는다. 배치 입력은 폼/업무별 JSON 필드 allowlist, 중복 JSON 키·행 ID·미지원 작업·행 수·현재 버전 검증을 거친다. CSRF와 기존 세션 현재성 검증을 유지한다.
- `OrgCommands.executeBatch`는 기존 변경과 같은 테넌트 독점 잠금 안에서 현재 권한·세션을 검사하고 재전송을 판정한다. 최종 조직 그래프·관리자 재직 상태를 검증한 뒤 업무·세션 회수·행/루트 감사를 하나의 트랜잭션으로 저장한다. 감사나 후속 행 실패는 앞선 행과 세션 개정도 롤백한다. 역할을 추가하거나 비밀번호·초대/승인 관계를 일괄 편집하는 API로 확대하지 않는다.
- 루트 감사의 명령 해시에는 정규화 입력·순서·클라이언트 행 ID·버전·사유를 포함한다. 같은 주체·명령·입력만 원래 배치/행 결과를 복원하고 다른 입력·주체는409다. 성공 재전송도 현재 관리자 권한을 요구하며 권한을 잃은 작성자에게 결과 조회를 허용하지 않는다. 감사 UI는 배치/행의 허용된 식별자·버전만 투영한다.
- V12 조직장 이력은 tenant 복합 PK/FK·명시 SQL 조건·FORCE RLS·중첩 exclusion과 최소 열 UPDATE를 사용한다. 앱의 DELETE나 기존 V1~V11 수정은 허용하지 않는다. 같은 시작일 교체·종료는 superseded 이력으로 보존하며 과거 원본을 삭제하지 않는다.
- 조직장 배정은 관리·APPROVER·회사 전체 조회 권한을 자동 부여하지 않는다. 현재 및 적용일의 재직 적격성과 현재 결재 자격을 따로 판단하며, 조직장 변경으로 기존 신청의 지정 승인자·원장·계산을 변경하지 않는다. 새 결재선 해석은 후속이다.
- 조직도는 관리자/대표의 `CompanyReadAccess` 공유 읽기와 반환 전 현재 권한 검증을 사용한다. 조직장 관리·시트 문맥·프로필도 기존 관리자/본인 권한과 공유 읽기를 유지하며 저장·쓰기 잠금 승격을 하지 않는다. 회사 응답은 이메일·자유 사유·계정/세션·감사 원문을 제외하고 본인 프로필의 대상은 principal에 고정한다.

409/422의 편집·비활성 예정·명령/행 식별자 보존과 최신 원본 비교는 권한 검증을 대체하지 않는다. 인증 만료·권한 회수 때 편집값·사유를 URL에 붙여 전달하거나 자동 재제출하지 않는다. 새 코드·본인 연도별 모달·월간 현황·운영 공개·보안 전수 검사 및 장시간 부하는 이 구현 계약의 완료 주장에 포함하지 않는다.

### Phase 6 조회 중 권한 회수 경계 (2026-10-25)

`BusinessCommands.read`와 `OrgCommands.read`는 조회 시작 전과 자료 반환 직전에 현재 계정·고객사·재직·인증 개정·필수 역할을 다시 확인한다. 시작 때 허용됐더라도 DB 잠금 대기나 자료 조회 중 권한 회수가 커밋되면 결과를 반환하지 않고 403으로 거부한다. 본인 출퇴근 조회와 담당자의 예외 정정 스냅샷 조회에 같은 기준을 적용한다. 조회 공급자는 읽기 전용이며 저장·외부 호출을 수행하지 않는다. 변경 명령은 기존 테넌트 잠금과 명령 재검증 경계를 유지한다.

회귀 테스트 `AttendanceReadBoundaryIT`는 별도 트랜잭션이 테넌트 잠금을 보유한 상태에서 본인·담당자 조회를 시작하고, 해당 트랜잭션의 잠금에 실제 대기하는 것을 PostgreSQL에서 확인한다. 계정 또는 필수 역할 회수를 커밋한 후 두 조회 모두 자료를 반환하지 않아야 한다. 단순 지연 시간에만 의존해 동시성 통과를 판단하지 않는다.

### Phase 6 공유 조회·독점 변경 잠금

출퇴근 스냅샷과 근로시간의 일·월·상세 조회는 같은 테넌트 키의 트랜잭션 공유 advisory lock을 사용한다. 같은 고객사의 조회끼리는 함께 실행할 수 있고, 조회 중에는 해당 키의 독점 변경 명령이 기다리므로 일정·재직·원천·효력·결과를 서로 다른 변경 시점에서 섞어 읽지 않는다. 조직·직원·출퇴근·승인·재집계·출력 생성 등 쓰기는 기존 `OrgCommands.execute`·`BusinessCommands.execute`의 독점 잠금을 먼저 획득한다. 쓰기 안에서 스냅샷을 읽어도 이미 보유한 독점 잠금은 트랜잭션 종료까지 유지된다.

공유·독점 잠금의 충돌과 트랜잭션 종료 시 자동 해제는 [PostgreSQL 18 advisory lock 공식 문서](https://www.postgresql.org/docs/18/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS)를 따른다. 구현은 같은 해시 키의 `pg_advisory_xact_lock_shared`와 `pg_advisory_xact_lock`을 사용하며 세션 단위 잠금으로 바꾸지 않는다.

읽기 경계에서 변경 명령으로 승격하거나 외부 호출을 수행하지 않는다. 변경이 필요하면 읽기 트랜잭션을 끝내고 별도 명령에서 현재 권한·버전·입력 근거를 다시 검사한다. `TenantReadConcurrencyIT`는 실제 월 조회와 일 조회 각각 두 개를 동시에 끝낸 뒤 트랜잭션을 유지한다. 실제 사원 변경 명령이 두 조회의 PostgreSQL backend PID에 차단되고, 하나만 종료했을 때는 계속 대기하며, 둘 다 종료한 후에만 변경·감사가 한 번 성공하는 것을 확인한다.

## 4. DB 역할과 RLS

| 역할 경계 | 설계 권한 |
| --- | --- |
| 일반 애플리케이션 | 필요한 테이블의 최소 CRUD, 소유자 아님, 슈퍼유저 아님, BYPASSRLS 없음 |
| 로그인 전 최소 조회 | 레지스트리 최소 필드·자격/토큰 전용 접근만. 일반 업무 저장소를 노출하지 않음 |
| 운영 메타데이터 | 고객사 상태·온보딩·운영 감사만, 고객사 근태 테이블 권한 없음 |
| 마이그레이션·소유자 | Flyway와 구조 관리 전용, 일반 웹 프로세스에서 자격 정보를 사용하지 않음 |
| 슈퍼유저·BYPASSRLS | 일반 앱·배치·출력 경로에 부여하지 않음 |

RLS는 조회 허용 조건과 새 행·변경 행 검증 조건 모두 테넌트 일치를 요구하고 컨텍스트 누락·빈 값·비정상 값은 거부한다. 모든 테넌트 업무 테이블의 적용 목록을 관리한다. 테이블 소유자에는 FORCE RLS 적용 여부까지 검증하되 소유자·슈퍼유저·BYPASSRLS의 우회 특성을 보안 대책으로 착각하지 않는다. PostgreSQL의 기본 거부·소유자·우회 역할·정책 결합 특성은 [공식 RLS 문서](https://www.postgresql.org/docs/18/ddl-rowsecurity.html)에 근거한다.

RLS만으로 객체 권한·자기 승인·민감 열람을 해결하지 않는다. SQL에는 명시적 tenant 조건과 허용 사원·조직·신청 범위를 함께 둔다. JOIN 양쪽·서브쿼리·일괄 연산·집계·XLSX에도 같은 원칙을 적용한다. 복합 FK로 다른 고객사의 사원·일정·원장을 참조하는 연결을 막는다. 제약 위반 메시지로 다른 고객사 행의 존재가 노출되지 않게 일반화한다.

## 5. 트랜잭션·커넥션 풀·작업 범위

1. 서비스가 인증된 테넌트·행위자·권한 범위를 입력으로 받고 트랜잭션을 연다.
2. 첫 업무 쿼리 전에 해당 트랜잭션 커넥션에 로컬 테넌트 컨텍스트를 둔다.
3. MyBatis 조회·명령·감사·원장은 같은 트랜잭션과 커넥션을 사용한다. 자동 커밋 업무 쿼리를 금지한다.
4. 로컬 컨텍스트는 커밋·전체 롤백에서 끝난다. 요청 스레드의 메모리 컨텍스트도 종료 경로에서 해제한다.
5. 예외·타임아웃·취소·초기화 실패 경로에서도 전체 롤백한다. 상태를 확인할 수 없는 커넥션은 풀로 정상 반환하지 않는다.
6. 중첩 트랜잭션·새 트랜잭션·비동기 전환은 컨텍스트 상속을 가정하지 않고 새로 검증·설정한다.

로컬 설정의 수명은 [PostgreSQL SET 문서](https://www.postgresql.org/docs/18/sql-set.html)를 근거로 삼았다. 세이브포인트 이전·이후 설정과 부분 롤백의 영향을 검증한다. 실패를 잡고 같은 트랜잭션을 계속 쓰거나 세션 수준 설정으로 대체하지 않는다. MyBatis 캐시는 테넌트·권한·버전 구분 없이는 활성화하지 않으며 초기에는 요청 간 업무 데이터 캐시를 두지 않는다.

배치·재집계·향후 비동기 작업은 서버가 확정한 고객사와 작업 목적·요청자 범위를 가진다. 고객사별 별도 트랜잭션을 열고 한 커넥션에서 테넌트 값을 바꾸며 순회하지 않는다. 세션이 없는 시스템 작업도 최소 범위의 서비스 주체를 명시한다. 작업 실행 때 고객사·사용자·권한의 현재 상태를 재확인한다.

Mapper 계약은 인증된 `TenantScope`와 조회 대상 범위를 필수 입력으로 둔다. tenant 없는 조회·ID 단독 변경·전역 export 전용 우회 Mapper를 만들지 않는다. pre-auth 범위와 일반 업무 범위는 타입·호출 경로를 분리한다. 입력 필터의 SQL 조각·정렬 문자열은 허용 목록으로만 선택하며 바인딩 없이 연결하지 않는다.

## 6. 허용 IP 출퇴근

IP 일치는 허용 네트워크에서 요청했다는 신호다. 현장 실제 근로·본인 존재를 보증하지 않으며 로그인·권한 검증을 대체하지 않는다.

- MVP 신뢰 경로는 브라우저 → Caddy → 백엔드다. 방화벽·바인딩 등 운영 통제로 백엔드 직접 접근을 차단해야 한다.
- 기본 출처는 프록시가 관측한 연결 주소다. 인터넷에서 받은 `Forwarded`·`X-Forwarded-For`를 그대로 신뢰하지 않는다.
- 앞단 CDN·로드밸런서를 추가하면 명시적으로 허용한 프록시 주소만 신뢰하고 우측부터 신뢰 체인을 검증한다. 불명·모순·손상된 체인은 허용하지 않는다.
- Caddy의 신뢰 프록시 동작은 [공식 reverse_proxy 문서](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)를 따른다. 실제 설정 파일은 이번에 만들지 않는다.
- IPv4·IPv6·IPv4-mapped IPv6를 같은 비교 규약으로 정규화한다. IP 파싱 실패·호스트명·포트 혼합·모호한 값은 거부한다.
- 허용 값은 정규화된 CIDR로 관리한다. 문자열 접두사 비교를 사용하지 않는다. 공인망·사설망·IPv6 범위와 NAT 변경을 구분한다.
- 허용 CIDR 변경은 근태 담당자만 수행하고 사유·처리자·적용 시각·전후 값을 감사한다. 전체망에 가까운 범위는 위험도를 표시하고 의도 재확인 절차를 설계한다.
- 명령은 서버 수신 시각과 당시 유효 CIDR 식별자를 기록한다. 클라이언트가 보낸 IP·허용 여부는 저장 근거가 아니다.
- IP 실패 때 기록 저장 완료를 표시하지 않는다. 네트워크 재확인·본인 내역 조회·정정 신청 경로를 제공하며 인증을 자동 우회하지 않는다.
- 통신 지연·공유기 교체·재택·모바일망 전환으로 실패할 수 있다. QR·GPS 임시 우회를 추가하지 않고 고객사 승인 정정으로 처리한다.

## 7. 웹·세션·출력 방어

MVP는 파일 업로드를 지원하지 않는다. 기본·local 프로필 모두 `spring.servlet.multipart.enabled=false`로 Servlet multipart 자동설정을 중지하고 `MultipartResolver`·`MultipartConfigElement`를 등록하지 않는다. 일반 URL-encoded 폼·CSRF·htmx·검토용 Excel 다운로드는 기존 계약을 유지한다. 파일 업로드를 추가할 때에는 parser·크기/개수·임시 파일·정리·인가 경계를 별도로 설계하고 검증한 뒤 이 설정을 재검토한다. 자동설정 미등록과 모든 MIME 요청의 HTTP 차단을 같은 의미로 주장하지 않는다.

- 로그인·로그아웃·초대 수락·재설정과 모든 상태 변경에 CSRF를 적용한다. htmx도 동일 토큰을 전송한다. GET은 업무 상태를 변경하지 않는다.
- Spring Security의 CSRF 기본 방어와 템플릿 통합은 [공식 문서](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)를 따른다. 편의를 위한 전체 비활성화는 금지한다.
- 세션 쿠키는 HTTPS 전용·HttpOnly·SameSite=Lax·제한된 경로를 적용하고 로그인 시 세션 식별자를 갱신한다. 제품 정책으로 유휴30분·로그인 후 최대12시간을 적용하고 remember-me는 제공하지 않는다. htmx 사용 중에도 절대 만료를 연장하지 않는다.
- 본문·사유·이름은 기본 이스케이프한다. 사용자 제공 HTML·스크립트·htmx 속성을 실행하지 않는다. CSP와 허용 출처를 검증한다.
- 고객사 개인정보 화면·부분 HTML·다운로드 응답에는 비저장 캐시 정책을 적용한다. htmx history 저장, localStorage·IndexedDB·서비스워커에 개인정보를 보관하지 않는다.
- 로그아웃·권한 회수 후 뒤로 가기·부분 요청·오래된 URL에서 자료가 재노출되는지 검증한다. PWA는 후속이며 오프라인 기록 큐가 없다.
- XLSX는 담당자 범위·필터·결과 버전·생성 시각·미확정 표시를 보존한다. 타 고객사·권한 범위 밖 출력은 차단하며 담당자는 자기 고객사의 허용 필터 범위 전체를 출력할 수 있다.
- XLSX에서 이름·사유 등 문자열은 수식이 아닌 텍스트로 기록하며 시트명·파일명·셀 길이를 검증한다. 다운로드 링크를 추측 가능한 공개 URL에 두지 않는다.
- Actuator는 외부 공개 화면과 분리하고 상태·설정·환경·덤프·메트릭 정보의 허용 범위를 제한한다.

## 8. 개인정보·감사와 보존

최소 사번·이름·업무용 이메일·소속·재직·근태만 수집한다. 주민등록번호·건강·생체·위치·급여 정보는 수집하지 않는다. 휴가·정정 사유에서 불필요한 민감정보를 입력하지 않도록 안내하고 자유문을 XLSX 기본 열에서 제외한다.

감사는 성공·실패·권한 변경·기초 잔여 조정·대체 지정·승인·출력에 대해 주체·대상·시각·요청 ID·사유를 남긴다. 비밀번호·토큰·쿠키·전체 요청 본문·불필요한 IP 원문은 남기지 않는다. 출퇴근의 검증 IP 증빙은 제한된 테이블·권한에만 두고 일반 로그에 복제하지 않는다. 감사 열람 자체도 감사 대상이다.

법정 보존 의무와 업무 목적별 보존·파기 기간은 [계산 규칙의 법령 검증 범위](../rules/calculation.md)와 별도로 개인정보 검토가 필요하다. 기간을 임의로 확정하거나 무기한 보존하지 않는다. 파일럿 전 접근권한·백업 암호화·복원·파기·사고 대응·초대 전달 채널을 구체화한다. 실제 개인정보를 테스트에 사용하지 않는다.
