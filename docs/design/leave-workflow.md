# 종일 연차 원장·독립 승인·출퇴근 정정 구현 계약

2026-11-18부터 연차의 오전·오후 신청도 같은 승인·취소 경로를 사용한다. 중간 승인, 반일 중복, 원장 0.5일 처리 기준은 [반차 업무 명세](../superpowers/specs/2026-11-18-attendance-codes-half-day.md)를 따른다.

[연장근무 사전신청·취소](../superpowers/specs/2026-11-18-overtime-requests.md)도 신청서별 순차결재를 사용한다. 최종 승인 분과 출퇴근 실적은 담당자의 연장근무 신청현황에서 대조한다.

2026-11-18 이후 [신청서 전용 결재선](../superpowers/specs/2026-11-18-request-form-approval-routing-design.md)에 단계가 여럿이면 아래의 승인 차감·취소 복원·정정 반영은 최종 결정에서 실행한다. 중간 승인 뒤에는 현재 담당만 다음 결재자로 바뀌며, 작성자는 최종 결정 전까지 철회할 수 있다.

> 2026-10-28 업무 확장 4단계: [근태코드 상세 계약](code-management.md)에 따라 기존 종일 연차·정정에 대상일 기준 불변 정책 버전을 연결한다. 새 제출에서 `effective_from` 우선·동일일 최고 `revision`을 고정하며 기간 중 버전이 달라지면 분리 신청422다. 승인에서는 저장된 버전의 지원 규칙과 기존 일정·잔여·재직 등을 재검증한다. 이후 코드 비활성·정책 변경은 기존 대기 승인·완료 이력·취소를 막지 않으며 취소는 원신청 버전을 승계한다. 원장 차감/복원·효력·정정·CALC-1은 그대로다. 신규 유형은 초안만 지원하며 유급 구분은 계산을 추가하지 않는 메타데이터다. [실행 계획](../superpowers/plans/2026-10-28-react-codes.md)과 [실제 결과](../quality/code-management.md)를 구분한다. 연도별 본인 조회·모달 작성은 다음 단위다.

> 2026-10-28 업무 확장 3단계의 [1단계 결재선·조직장 결재](approval-routes.md)는 아래 신청·결정·원장 처리를 재사용한다. 사원별 명시 결재선→기존 지정 승인자→오늘 소속 조직 결재선 순으로 해석하며, 상위 경로가 부적격이면 제출을 차단한다. 새 경로의 최초 해석은 신청별 불변 스냅샷으로 저장하고 기존 배정 참조와 XOR로 구분한다. 설정·소속·조직장 변경은 대기를 자동 이동하지 않으며 명시 재할당만 현재 담당자를 바꾼다. 원신청·기승인·취소·효력·원장과 원천 이력은 보존한다. [실행 계획](../superpowers/plans/2026-10-28-react-approval-routes.md)의 검증 항목과 [실제 결과](../quality/approval-routes.md)를 구분한다.

2026-10-24 연속 MVP 위임에 따라 [신청 규칙](../rules/workflow.md), [계산](../rules/calculation.md), [데이터 모델](data-model.md)을 구현한다. 새 정책을 법적 의무로 확정하지 않는다.

## 불변 원장과 상태

- leave_bucket의 기준일·사용가능기간(양끝포함)·발생근거를 담당자가 등록한다. 본인 기초·증감은 다른 담당자가 처리한다. 정수DAY만 허용하며 무근거/음수·승인 사용량을 침해하는 감액은 거부한다.
- leave_ledger는 OPENING/ADJUSTMENT/USE/RESTORE 추가만 한다. 현재 잔여는 원장 합계이며 PENDING은 예약·차감하지 않는다. 만료묶음의복원은이력을보존하고사용가능량과구분한다.
- approval_request는 LEAVE_DAY/ATTENDANCE_CORRECTION/CANCEL_LEAVE 원문을 불변 보존하고 PENDING에서 APPROVED/REJECTED/WITHDRAWN으로만 전이한다. 대상/작성자와 승인자가 같을 수 없다. 지정관계·현재 재직/역할·version을 다시 검증한다.
- 연차는 단일묶음·최대366일 기간의 날짜별 현재일정/캘린더를 참조하며 소정일1DAY,확정비근로일/휴일0,미확인차단이다. 같은날PENDING/유효APPROVED 중복을 차단한다. 승인직전 입력과량이바뀌면 PENDING 유지·철회재신청을 안내한다.
- 취소심사중 원신청은 유효하다. 취소승인만원USE행을정확히한번역분개하고원효력CANCELED로표시한다. 원APPROVED이력은유지한다. 시작전본인취소,과거/퇴사자취소는근거있는담당자예외경로와독립승인을요구한다.
- 정정은 KEEP/SET/CLEAR와현재사실개정·스냅샷 fingerprint에결속한다. 출퇴근시각/실제휴게는서울시각·밀리초이고새미래시각·역전·구간밖휴게는거부한다. 원천은갱신하지않는다. 대기정정최대1건,새승인정정은이전현재효력만SUPERSEDED로바꾼다. 정정취소는없다.
- 정정제출/철회/반려는review만증가,승인은input/review를갱신하고근거있는실제구간을새사실에결속한다. 연차효력변경도영향일재집계필요를같은트랜잭션에남긴다.

## 권한·동시성과 화면

직원은본인,승인자는현재할당신청판단범위,담당자는고객사설정/예외/명시재할당만가능하다. 담당자역할만으로승인권한을얻지않는다. BusinessCommands의현재계정·역할·동일tenant잠금·명령재시도·감사를재사용하고관리원장은OrgCommands로처리한다.

신청/날짜상세/정정상세/효력/결정이력·원장은7개FORCE RLS표로분리한다. 요청상태·효력·원장·감사·개정은하나의트랜잭션이다. 유일참조로이중차감·복원·정정효력·대기취소를차단한다. 모든SQL에tenant조건·복합FK를적용한다.

본인신청목록/연차신청/정정신청,지정승인함/상세·결정·철회·취소,담당자기초잔여/원장/대기재할당/예외신청을서버렌더링한다. CSRF·안전한404·422입력보존·409최신조회안내를유지한다. 실제첨부·메일·월마감·자동발생·자동대결은추가하지않는다.

검증은WF01~WF21을따른다. 특히동시잔여소비·승인/철회·재할당경합·원장오류시전체롤백·현재효력/과거이력·테넌트/자기승인차단을실제PostgreSQL로검증한다.

화면의 일반 취소 버튼은 원작성 계정·본인 대상·승인 유효·예정 시작 전 조건으로 제한한다. 당일에는 현재 일정 시작 시각을 기준으로 판단하며 최종 권한·시각·효력 검증은 서비스가 다시 수행한다. 담당자 예외 취소 버튼은 별도 조건으로 유지한다.

일반 취소 시작 기준은 첫 실제 차감일의 예정 시작이다. 범위 앞부분에0DAY인 휴일/비근무일이 있더라도 그 범위 시작일만으로 버튼을 조기에 숨기지 않는다. 서비스의 최종 취소 검증과 같은 기준을 사용한다.

시각 표시 후속 검토에서 일반 취소 실행·승인에도 범위 시작일 조기 판정이 남아 있음을 확인했다. 서버도 첫 실제 차감일을 기준으로 시작 여부를 판단하도록 맞춘다. 앞부분0DAY가 지난 범위라도 첫 차감일 전이면 일반 취소 심사가 가능하며, 첫 차감일이 이미 지났거나 당일 예정 시작 정각 이후면 기존 담당자 예외 경로를 유지한다.

## Phase 6 사원 선택 검증

기초 잔여 관리의 사원 선택은 해당 고객사 전체 사원을 사번·ID 순으로 제공한다. 사원 관리 목록의 `50개 + 다음 페이지 확인용 1개` 조회를 선택 상자에 재사용하지 않는다. 담당자가 마지막 사원을 선택한 뒤 기초 등록·예외 정정으로 이어갈 수 있어야 하며, 입력 오류로 화면을 다시 표시할 때도 선택 대상과 근거 입력을 보존한다. 사원 목록의 기존 검색·50개 페이지 계약은 유지한다.

`EmployeeAdminMapper.options(tenantId)` → `EmployeeService.options(actor)` → 기초 잔여 화면으로 연결한다. 서비스는 현재 담당자 권한을 확인하고 SQL의 명시적 tenant 조건과 RLS를 유지한다. 사원 선택 목록은 권한 부여가 아니므로 기초 등록·예외 정정의 대상·재직·자기 처리 제한은 기존 명령에서 다시 검증한다. 과거 이력 검토를 위해 비활성·퇴사 사원을 임의로 제외하지 않는다.

수용 사례는 합성300명 고객사에서 마지막 사원 선택·기초 등록, 오류422 이후 선택·근거 보존, 다른 고객사 사원의 비노출·404와 일반 직원403이다. 다른 화면의 근로시간 대상·승인자 후보는 이미 전체 후보를 조회하므로 이번 수정으로 그 계약을 바꾸지 않는다.
