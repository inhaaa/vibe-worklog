# 1단계 결재선·조직장 결재 계약

2026-11-18에 [신청서코드별 순차결재](../superpowers/specs/2026-11-18-request-form-approval-routing-design.md)를 추가했다. 이 문서의 사원별·조직별 선정 순서는 신청서에서 ‘기존 배정 사용’을 선택할 때 적용한다. 전용 결재선은 제출일의 조직장으로 최초 경로를 고정하며, 팀장 승인 뒤 실장 결재가 남으면 신청은 대기 상태다.

> 2026-11-26 [결재 알림](../superpowers/specs/2026-11-26-approval-notifications-design.md): 결재 이력을 쓰는 `LeaveWorkflowService.history()`가 같은 트랜잭션에서 `tna.notification`(V43)에 받는 사람별 알림을 만든다. 결재선 해석·결정 규칙은 바꾸지 않는다.

> 2026-10-29 화면 공통화: 결재선 편집·불변 버전·사원/조직 배정 이력 표는 [WorklogSheet](../superpowers/specs/2026-10-29-common-sheet-design.md)를 사용한다. 지정 사원·조직장 해석, 저장·충돌·명령·자기 승인 차단은 그대로다. 정의 편집의 정렬·필터는 현재 페이지에만 적용하고 전체 배정/버전 이력은 불러온 전체 목록임을 구분한다.

2026-10-28 사용자가 승인한 [업무 확장 3단계](../superpowers/specs/2026-10-26-worklog-service-design.md#6-결재선과-결재)의 상세 계약이다. 기존 [신청·승인](leave-workflow.md)과 [계정·직접 승인자](account-access.md), [조직장](org-management.md)의 업무·권한 경계를 유지한다. 구현 순서는 [실행 계획](../superpowers/plans/2026-10-28-react-approval-routes.md), 실제 검증과 미실시 범위는 별도 품질 보고서에 기록한다.

## 결재선 정의와 적용

관리자는 결재선 코드·이름·사용 상태와 `지정 사원` 또는 `신청 대상자 소속 조직장`을 관리한다. 코드 저장 후 변경과 물리 삭제는 제공하지 않는다. 이름·담당 방식·지정 사원 변경은 새 불변 버전으로 남긴다. 조직장·대표·관리자라는 이유만으로 APPROVER를 자동 부여하지 않는다.

정의 시트는 검색·50행 페이지·조회/입력/선택 삭제/저장/취소를 제공한다. 저장된 행의 삭제는 비활성 처리이며 이전 버전·배정·신청은 보존한다. 변경1~50행과 감사는 고객사 독점 잠금 아래 한 트랜잭션으로 저장한다. 실패하면 전체를 롤백하고409/422에 편집·식별자·삭제 예정·최신 원본을 보존한다. 동일 commandId/입력은 기존 결과를 복원하며 상이 입력은409다. 재전송에도 현재 관리자 자격이 필요하다.

사원 또는 조직을 선택해 특정 불변 버전을 적용일별로 배정한다. 정의의 최신 버전 생성은 기존 배정을 자동 교체하지 않는다. 배정의 대상은 정확히 하나이며 같은 대상의 유효 구간은 중첩될 수 없다. 적용일은 서울 오늘 이후, 구간은 시작 포함·종료 제외다. 당일 교체는 이전 행을 superseded로 보존하고 과거부터 이어진 구간은 적용일에 닫는다. 이후 예약과 공백은 보존하며 해제도 원본 삭제 없이 효력을 종료한다.

## 신규 신청의 해석

선택 순서는 다음과 같다.

1. 오늘 유효한 명시 사원별 결재선
2. 기존 사원별 지정 승인자
3. 오늘 소속 조직의 결재선

존재하는 상위 설정이 공석·비활성·부적격이면 하위 설정으로 우회하지 않고422와 재지정 안내를 반환한다. 조직장은 신청 대상자의 현재 소속 조직에서만 찾으며 상위 조직이나 대체 담당자를 추정하지 않는다. 대상 근무일이 과거·미래여도 제출 당시 서울 오늘 기준 설정을 해석한다.

실제 결재자는 같은 고객사의 현재 활성·재직·초대 수락 완료 계정과 APPROVER가 필요하다. 대상 사원 또는 작성자 계정과 같으면 제출을 차단한다. 대표의 본인 신청과 관리자의 대리 예외 작성에도 독립성을 적용한다. 과거·퇴사 대상의 예외 신청 가능 여부는 기존 업무 계약을 유지한다.

새 결재선 경로는 배정 ID/버전·불변 결재선 버전·소속/조직·조직장 배정/버전·실제 결재자·해석 시각을 신청별 불변 스냅샷으로 저장한다. 기존 직접 지정 경로는 기존 approver_assignment ID/버전을 계속 사용한다. 두 경로를 임의 변환하거나 가짜 legacy 배정을 생성하지 않는다.

결재선 이름은 불변 버전의 이름이다. 소속 조직·사원의 식별자와 배정 버전은 당시 값으로 고정하되 표시 이름은 해당 식별자의 현재 이름을 사용한다. 과거 이름 원문을 복원하는 기능은 제공하지 않는다.

## 대기와 기존 이력

결재선·조직장·소속·직접 승인자 변경은 새 제출에 적용한다. 대기 신청의 실제 담당자를 자동 이동시키거나 완료 결정·원장·효력을 갱신하지 않는다. 결재자 부재는 관리자의 기존 명시 재할당으로 처리하고 신청 버전·전후 담당자·사유를 남긴다. 최초 스냅샷/legacy 참조는 재할당 후에도 보존한다.

결정 시 현재 지정자·현재 계정/세션·APPROVER·재직·자기/작성자 독립성·신청 버전을 다시 검증한다. 종일 연차 승인 차감·취소 승인 복원·정정 효력·동시성·철회·반려는 기존 서비스가 담당한다. 새 결재선은 계산·잔여·원천 기록을 변경하지 않는다.

`/approvals`는 지정 대기함이며 `/approvals/completed`는 본인이 승인·반려한 결정 이력을 조회한다. 작성자 철회는 본인이 처리한 결재로 세지 않는다. 본인 프로필은 현재 해석되는 경로/실제 담당/차단 사유를, 신청 상세는 제출 당시 해석과 현재 실제 담당·재할당 이력을 구분해 보여준다.

## V13과 DB 경계

기존 마이그레이션을 수정하지 않고 네 테이블을 추가한다.

| 대상 | 계약 |
| --- | --- |
| approval_route | 고객사 코드 유일·고정, 현재 이름·active·version |
| approval_route_version | route/revision 유일, 이름·방식·직접 지정 사원·등록 근거 불변 |
| approval_route_assignment | EMPLOYEE/ORGANIZATION 대상 XOR, 불변 버전 참조, 기간 중첩 차단, 종료/교체 이력 |
| approval_route_snapshot | 신청당1개, 해당 신청/배정/버전·소속·조직장·실제 결재자 고정 |

모든 행은 tenant 복합 PK/FK·명시 SQL tenant 조건·FORCE RLS를 갖는다. 앱은 정의와 배정의 명시적 변경 열만 UPDATE할 수 있고 버전·스냅샷은 INSERT/SELECT만 가능하다. DELETE/TRUNCATE는 부여하지 않는다. 기존 신청의 legacy 배정 참조 두 열 UPDATE 권한도 회수하며 실제 재할당 열은 유지한다.

approval_request에는 nullable route_snapshot_id를 추가하고 기존 배정 ID/버전의 NOT NULL을 경로 XOR 검사로 대체한다. legacy 두 값은 함께 존재하거나 함께NULL이어야 한다. 신청 `(tenant_id,route_snapshot_id,id)`가 스냅샷 `(tenant_id,id,request_id)`를 참조하는 FK만 지연 검사한다. 스냅샷에서 신청을 참조하는 FK는 즉시 검사하며 같은 회사의 다른 신청 스냅샷 재사용도 차단한다. 신청과 스냅샷은 같은 트랜잭션에서 함께 생성한다.

설정 화면은 관리자만 접근하고 대표·일반 직원·운영자는 접근할 수 없다. APPROVER의 결재 조회는 실제 배정/본인 결정 범위이며 회사 전체 권한이 아니다. 새 조회도 공유 잠금과 반환 전 현재 권한 확인을 유지한다. 프론트 메뉴 표시와 서버 인가는 별도로 검증한다.
