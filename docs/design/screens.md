> 2026-10-28 업무 확장 4단계: React 공통코드 그룹/상세 시트와 별도 근태코드 시트의 현재 계약은 아래 [4단계 화면 계약](#공통코드근태코드-4단계-구현-계약)·[상세 명세](code-management.md)를 따른다. 정책 버전·신청 가능 상태·제출 당시 정책을 구분한다. 실제 검증·DB 반영·공개 데모 통합은 [별도 결과](../quality/code-management.md)에 기록한다. 본인 연도별 조회·모달과 월간 화면 개선은 후속이다.

> 2026-10-28 업무 확장 3단계 이력: React 결재선 정의 시트·사원/조직 배정·결재 대기함/본인 처리 이력·현재 경로와 신청 당시 해석의 화면 계약은 아래 [3단계 계약](#결재선조직장-결재-3단계-구현-계약)과 [상세 명세](approval-routes.md)를 따른다. 당시 검증과 기본 DB 반영은 [별도 실행 결과](../quality/approval-routes.md)로 구분한다. 당시 권한/코드 시트·본인 연도별 모달·월간 그래프·운영 수용은 후속으로 남겼다.

> 2026-10-27 착수·2026-10-28 기준 업무 확장 2단계 이력: React 조직·사원 시트, 조직장 배정 이력, 회사 조직도와 본인 조직장 표시의 구현 계약은 아래 [2단계 화면 계약](#조직사원-시트조직장조직도-2단계-구현-계약)과 [실행 계획](../superpowers/plans/2026-10-27-react-org-sheet.md)을 따른다. 당시 전체 검증·기본 DB 반영·실제 화면 확인 결과는 [별도 보고서](../quality/org-sheet-heads.md)에 기록한다. 아래 1단계와 초기 SSR/단건 설명도 당시 이력이며, 당시 새 결재선·코드·본인 연도별 모달·월간 그래프·운영 수용은 후속으로 남겼다.

## 1. 상태와 화면 원칙

초기 기준일: 2026-10-24. [PRD](../prd.md)의 MVP 화면·요청 기준선을 보존하며, 2026-10-26 승인된 [A안 워크스페이스](ui-redesign-proposal.md)의 소개·홈·개인 달력·직원 목록과 공통 shell 계약을 반영했다. 기존 기획 URL의 구현 차이는 후속 상세 명세·현재 controller를 따른다. 실행·검증 현황은 [PRD](../prd.md)·[개발 안내](../development/local.md)·[워크스페이스 UI 품질 보고](../quality/workspace-ui.md)를 따른다. [데이터 모델](data-model.md), [승인 규칙](../rules/workflow.md), [계산 규칙](../rules/calculation.md), [보안 설계](security.md)를 함께 따른다.

같은 날 후속 결정은 흰 배경·파란 강조의 업무 테마와 기존 공통 shell·소개·일정·직원 목록을 유지하고 홈만 하루 흐름 배치로 변경하는 것이다. 범위는 [홈 적용 계획](../superpowers/plans/2026-10-26-dayflow-home.md), 이번 변경의 실제 검증과 이미지 이력은 [홈 품질 보고](../quality/dayflow-home.md)를 따른다. A안 검증 이력은 이전 보고서에 그대로 보존한다.

2026-10-26 추가 승인한 전체 목표는 [사용자·관리 업무 확장 설계](../superpowers/specs/2026-10-26-worklog-service-design.md)를 따른다. 내 정보·대표 회사 읽기 1단계, 조직·사원 시트/조직장/조직도 2단계, 결재선 3단계와 공통/근태코드 4단계는 상단의 단위별 기록으로 구분한다. 권한 시트의 부분 일괄 변경, 본인 연도별 모달과 월간 현황 개선은 후속이며 전체 목표를 구현 완료로 간주하지 않는다. 기존 단건·소속·신청·결재 경로는 유지한다.

- PC·모바일 온라인 반응형 웹을 제공한다. PWA·오프라인 저장·앱 설치·다중 고객사 전환 UI는 후속이다.
- 기본은 서버 렌더링 HTML이며 htmx는 같은 화면의 목록·폼·처리 결과를 부분 갱신한다. 별도 공개 REST/JSON API는 MVP 범위가 아니다.
- 현재 고객사·본인·역할을 항상 확인할 수 있어야 한다. 역할 메뉴 숨김과 서버 권한 검증을 함께 적용한다.
- 소개·공통 shell은 승인한 밝은 워크스페이스를 적용한다. 로컬 데모 진입은 [두 프로필·기존 정상 인증](local-demo-login.md)을 사용하며 일반 로그인은 유지한다. 역할 선택 UI로 권한을 바꾸지 않는다.
- 시각에는 `Asia/Seoul`, 근무일에는 날짜를 표시한다. 자정 통과·월·연도 경계는 생략하지 않는다.
- 산정 불가 `null`은 `검토 필요`로 표시한다. 실제 0시간·미완료·대기·오래된 결과를 다른 문구로 구분한다.
- 소정 일정·원천 기록·승인 정정·실제 근로 판단·휴가·결과를 구분해 보여 주고 원천을 편집하는 버튼은 제공하지 않는다.
- 법정 적합·급여 확정 같은 보증 문구를 사용하지 않는다. 검토용 XLSX와 후속 급여 연계를 구분한다.

## 3. 핵심 화면의 정보 순서

### 결재선·조직장 결재 3단계 구현 계약

관리자에게 `결재선 관리`와 `결재선 배정` 메뉴, 현재 APPROVER에게 `결재 대기함`과 `내가 처리한 결재`를 제공한다. 대표만 있는 계정은 결재 설정 화면에 접근할 수 없다. 대표가 APPROVER를 함께 가진 경우에도 실제 지정된 신청만 처리한다.

| 경로·모델 | 입력·표시와 처리 |
| --- | --- |
| GET `/admin/approval-routes?q&page`, `approvalRoutes` | 코드·이름 검색, 정의50행 시트와 버전 이력·적격 지정 사원 후보 |
| POST `/admin/approval-routes/bulk` | `commandId`, `reason`, 변경분1~50행 JSON. 조회/입력/삭제/저장/취소, 저장된 코드 불변·삭제는 비활성 예정 |

정의 변경은 새 불변 버전을 만들고 기존 배정을 자동 교체하지 않는다. 409/422에는 편집·비활성 예정·행/명령 식별자와 최신 원본을 보존하며 명시 확인 후에만 새 버전 기준으로 재시도한다. 배정 폼도 입력과 사유를 유지하고 충돌한 대상 버전은 명시 확인으로 갱신한다. 현재 저장된 배정을 그대로 조회한 상태는 미저장으로 표시하지 않으며 입력 버튼은 작성 내용을 지우지 않고 초점을 옮긴다. 메뉴·검색·페이지 이동 시 미저장 손실 확인과 공통 전송 잠금을 유지한다.

신청 해석은 사원 명시 결재선→기존 직접 지정→오늘 소속 조직 결재선 순이다. 공석·비활성·자기/작성자 결재·현재 자격 부재는 우회하지 않고 제출을 차단한다. 제출 당시 해석과 대기 담당자는 이후 설정 변경에도 유지하고 담당자가 신청 상세에서 명시 재할당한다. 상세의 결재선 이름은 불변 버전명이고 조직·사원 표시명은 당시 식별자의 현재 이름이다. 기존 신청·결정·원장·계산은 변경하지 않는다. [상세 계약](approval-routes.md)과 [실행 계획](../superpowers/plans/2026-10-28-react-approval-routes.md)을 따른다.

### 조직·사원 시트·조직장·조직도 2단계 구현 계약

조직·사원 목록은 기존 검색·필터·50행 페이지에서 native table 편집을 제공한다. `조회 / 입력 / 삭제 / 저장 / 취소` 도구 모음과 행/필드 변경 표시를 두고 고정 코드·사번은 읽기 전용으로 표시한다. 저장된 행의 삭제는 물리 삭제가 아닌 비활성 예정이며, 미저장 신규 행만 화면에서 제거한다. 기존 사원 상세·계정/역할·소속·근무 배정 연결은 유지한다. 소속·조직장·근무 문맥은 읽기 전용이며 시트로 이력을 덮어쓰지 않는다.

배치는 기존 CSRF 폼으로 `commandId`, `reason`, `rows` JSON 배열을 전송한다. `rows`는 전체 페이지가 아닌 변경분이며 `clientRowId`는 UUID 문자열이다. 성공303 이후 목록을 재조회한다.409/422는 편집·비활성 예정·명령/행 ID·사유·필드 오류를 유지하고 현재 페이지를 벗어난 편집 대상도 최신 원본과 비교한다. 첫 오류로 초점을 옮기며409는 명시 확인 전 자동 덮어쓰기하지 않는다. 수정·재확인 후에는 새 명령,503 등 결과 불명확 상태에서 같은 내용 재시도는 원래 명령을 사용한다. 미저장 조회·검색·페이지/메뉴·브라우저 이동에는 손실 확인을 적용한다.

조직장은 서울 오늘 이후 적용일과 조직 version을 제출하며 동일일 교체·미래 예약·종료를 구분한다. 재직 부적격과 결재 자격 부재는 별도 문구로 표시하고 배정만으로 권한을 부여하지 않는다. 기존 신청의 결재자도 이동하지 않는다. 긴 표는 내부 가로 스크롤, 조직 트리는 native `details`/`summary`와 키보드·레이블을 사용한다. 대표 조직도는 변경 폼·자유 사유·이메일·계정/세션 정보를 포함하지 않는다.

상세 원자성·스키마·권한은 [조직 관리 2단계 계약](org-management.md#react-조직사원-시트조직장조직도-2단계-계약)을 따른다. PC/모바일·오류/충돌·세션·실제 DB 반영은 [실행 계획](../superpowers/plans/2026-10-27-react-org-sheet.md)의 검증 대상이며 수행 결과는 [별도 보고서](../quality/org-sheet-heads.md)로 구분한다.

### 소개·공통 shell과 조회 연결

`local`+`local-demo`에서 GET `/`·`/login`은 `/demo`로 안내하고 입장 버튼은 hidden `email=admin`·`password=admin`과 Thymeleaf CSRF로 기존 POST `/login`을 제출한다. 성공 목적지는 `/me/today`, 실패·로그아웃 목적지는 기존 `/login`이며 소개로 이어질 때 `error`·`logout` 플래그만 전달한다. 기본·`local` 단독은 기존 회사코드·이메일·강한 비밀번호 로그인을 유지한다.

인증된 SSR 업무 화면은 공통 sidebar/header/main을 사용한다. 실제 principal의 `EMPLOYEE`·`APPROVER`·`ATTENDANCE_ADMIN`에 따라 메뉴를 표시하고 관리자 단독 역할의 기존 관리 접근도 유지한다. 현재 고객사·본인 정보는 인증 tenant로 읽고 현재 권한을 재확인하며 redirect·부분 fragment에 공통 identity 모델을 붙이지 않는다. 외부 JS는 모바일 메뉴만 제어하고 업무 읽기·변경은 기존 SSR/폼으로 처리한다. 기존 CSRF·명령 ID·버전·선택 사원/월 복귀 연결을 보존한다.

개인 달력은 `month=YYYY-MM`·`date=YYYY-MM-DD`를 받는다. 월이 없으면 선택 날짜의 월 또는 서울 기준 현재 월, 날짜가 없으면 현재 월의 오늘 또는 선택 월 첫날을 사용한다. 선택 날짜가 월 밖이면 거부한다. 일정·휴일·출퇴근·실제 근로 확인과 신청/승인/취소 효력을 기존 본인 읽기로 조합하며 예정 근무·휴게를 실근로로 확정하지 않는다.

근태 캘린더는 월요일부터 시작하는 흰 날짜 격자와 아래쪽 선택일 상세로 구성한다. 예정 근무는 가는 실선, 휴일 정보 미확인은 점선, 유효한 승인 연차는 녹색 배경과 문구로 표시한다. 일반 클릭은 상세 날짜를 바꾼다. 날짜 우클릭, `⋯`, `Shift+F10`은 해당 날짜의 같은 신청 메뉴를 열고, `Esc`는 열었던 위치로 초점을 돌려준다. 상세의 `이 날짜로 신청`도 같은 메뉴를 연다.

메뉴는 `GET /me/requests/new?year=YYYY&kind=LEAVE_DAY|ATTENDANCE_CORRECTION&date=YYYY-MM-DD`로 공통 신청서를 연다. 종일 연차에는 같은 날짜를 시작일·종료일에 채우고 정정에는 대상일을 채운다. 기존 서울 기준 날짜 검증에 따라 지난 날짜의 연차와 미래 날짜의 정정은 메뉴에서 제한 사유를 표시한다.

직원 목록은 `q`·0부터 시작하는 `page`·`organizationId`·`status=all|active|inactive`·`employeeId`를 받는다. 현재 소속은 서울 기준 오늘 유효한 배정이고 활성은 입사/퇴사일과 별개다. 최대50명과 다음 페이지 존재 여부를 표시하며 요약 수는 **현재 검색·필터·페이지 범위**만 집계한다. 선택 상세는 현재 tenant와 표시 페이지 안의 사원만 허용한다. 검색/페이지/선택 연결과 원래 등록 폼·사원 상세 수정·계정/역할/승인자·일정 배정 경로를 유지한다.

### 오늘 출퇴근

홈은 실제 저장된 본인 이름·오늘 snapshot·원장 잔여·대기/최근 신청·주간 날짜별 상태를 표시한다. 시안의 인명·연차8일·32시간을 업무 값으로 고정하지 않으며 자료가 없으면 미등록·미배정·미확인으로 안내한다.

홈(`/me/home`)의 '오늘 근무' 위젯은 출퇴근 위젯이다([설계](../superpowers/specs/2026-11-16-home-clock-widget-design.md)). 일정 한 줄(`09:30 ~ 15:30` 또는 서버 일정 문구)과 `출근`·`퇴근` 버튼을 보이고, 버튼은 `eventKind`·`commandId`·`returnTo=home`으로 POST `/me/attendance/events`에 보낸다. 오늘 그 구분의 원래 기록이 있으면 버튼은 비활성이고 기록 시각을 `HH:mm:ss`로 보인다. 퇴근은 출근 없이도 누를 수 있다. `clockError`가 있으면 위젯 안에 403 "허용된 네트워크에서만 출퇴근을 기록할 수 있습니다.", 409 "오늘 이미 기록했습니다.", 그 밖은 "기록하지 못했습니다. 잠시 후 다시 시도해 주세요."를 보인다. 확인 문구·타임라인·기록 상세 링크는 유지한다.

기존 공통 shell 안에 큰 서울 기준 날짜·본인 이름 → 하루 흐름 타임라인과 출퇴근·확인할 일 → 7일 주간 띠 → 최근 신청 → 접이식 원천·현재 반영 비교와 실제 근로·휴게 확인을 배치한다. 주간 날짜는 기존 본인 달력의 `month`·`date`로 연결한다. 소개·일정·직원 목록과 다른 업무 화면의 디자인·공통 메뉴는 유지한다.

타임라인은 근무일에 존재하는 예정 근무·휴게 시작/종료와 현재 반영 `effectiveEvents`를 서울 시각으로 정렬하고 예정·현재 반영을 제목과 설명으로 구분한다. 없는 시각을 0시로 채우지 않고 같은 시각·중복 항목도 보존한다. 접이식 비교는 원천과 현재 반영 기록을 분리하며 정정 때문에 원천을 덮어쓰지 않는다. 타임라인의 정렬·기록 존재는 실제 근로·휴게·지각·연장·완료 판정이 아니다.

확인할 일은 일정 미배정·기초 연차 미등록·본인 대상 대기 신청 등 현재 자료에서 확인할 상태를 안내한다. 실제 근로·휴게 확인 링크는 현재 반영 IN·OUT이 모두 있고 `confirmation == null`일 때만 제공한다. 이는 확인 화면으로 가는 링크이며 근무가 완료됐다는 판정이나 자동 확인 저장이 아니다. 기존 원천 상세·실제 근로 확인 폼과 환경 정보의 상태 fragment·htmx 갱신을 접이식 영역에 보존한다.

현재 고객사·근무일·시간대·적용 일정·마지막 서버 저장 결과·네트워크 상태·처리 메시지·내역/정정 연결을 계속 제공한다. 출근/퇴근은 기존 POST 폼·CSRF·명령 ID·서버 시각·권한 및 허용 IP 검증을 사용한다. 브라우저가 표시한 현재 시각은 참고이며 저장 시각은 서버 응답으로 교체한다. 요청 중 버튼을 잠가도 서버 중복 검증은 별도로 수행한다.

퇴근 후 현재 사실 개정의 출퇴근 구간과 예정 휴게를 보여 주고 실제 근로·휴게가 같은지 본인이 확인한다. 일치 확인은 검토 개정만 갱신하고 재집계 필요를 표시한 뒤, 같은 요청에서 그날이 속한 주를 자동 계산한다. 다르면 정정 신청으로 실제 구간을 제출하며, 확인 전 실근로를 정상 확정하지 않는다.

통신 실패면 `처리 여부 확인 필요`를 표시하고 기존 명령 키로 재확인한다. 저장 성공 응답을 받기 전 완료로 표시하지 않는다. IP 거부 때 우회 버튼·임의 시각 제출은 제공하지 않는다. 날짜 변경 후에도 이전 기록과 근무일을 명확히 표시한다.

### 신청·승인 상세

원신청 식별·종류 → 대상 날짜/사원 → 기존/요청 값 → 사유 → 기준 일정·잔여·입력 버전 → 현재 승인자 → 상태/결정 이력 → 업무 효과 → 취소/재신청 연결 순이다. 승인 시각·승인자의 당시 역할을 표시하되 비밀번호·IP 원문은 노출하지 않는다.

버튼은 PENDING에서 지정 승인자의 승인/반려, 작성자의 철회만 허용한다. APPROVED 연차는 예정 시작 전 별도 취소 요청을 제출하고 이미 시작·사용·퇴사한 건은 담당자 예외 경로로 심사한다. 취소 대기는 `원승인 유효·취소 심사 중`, 취소 승인은 `원승인 이력 유지·현재 효력 CANCELED`로 표시한다. 승인된 출퇴근 정정에는 취소 버튼이 없고 현재 유효 개정을 참조하는 새 정정으로 변경한다. 이전 정정은 APPROVED 이력·SUPERSEDED 효과로 남긴다. 반려 후 재신청은 새 ID이며 원문을 편집하지 않는다.

승인자 부재는 담당자의 대체 지정과 대기 건 재할당으로 해결한다. 화면에 자기 승인 예외나 운영자 강제 승인 동작을 제공하지 않는다. 최신 상태가 바뀌면 로컬 화면을 강제로 성공 처리하지 않고 다시 조회하게 한다.

### 현황·검토 출력

필터 → 기준 시각/시간대 → 완료·검토 필요·대기·오래됨 건수 → 일 결과와 주·월 요약 → 선택 결과의 입력·정책·규칙 버전 → 정정/재집계 → 검토용 XLSX 순이다. 주간 법정 판정에 월 밖 날짜가 필요하면 자료 부족을 표시한다. 예정 휴게와 확인된 실제 휴게를 분리한다. 퇴근 후 실제 근로·예정 휴게 일치 확인은 사실 개정에 결속하고 사실 입력이 바뀌면 재확인을 요구한다. 실제 근로·휴게에 영향을 주는 대기 정정은 현재 정상 확정을 보류하고 이전 산정값을 참고 이력으로 표시한다.

XLSX에는 고객사·필터·기간·생성 시각·시간대·단위·결과 버전·미확정/오래됨·검토용 표시를 포함한다. 기본 데이터 열은 사번·이름·소속·근무일·일정·유효 출퇴근·확인 휴게·근로량·휴가·예외·정책/규칙/결과 버전이다. 확인된 일8시간 초과량 `over_8h_millis`와 주40시간 초과 참고량 `over_40h_millis`를 각각 표시하고 법정 가산 최종값 `legal_overtime_millis`는 MVP 미지원 null로 남긴다. 야간·휴일 등 중첩 분류를 더해 총 실근로를 만들지 않는다. 자유 사유·이메일·IP·민감 감사 원문은 기본 열에 넣지 않는다. 근로량은 밀리초 정본 열과 사람이 읽는 표시를 제공하며 분 단위 절삭 합산을 하지 않는다.

## 6. HTTP 오류·부분 갱신 계약

| HTTP | 의미·대표 코드 | 사용자 처리 |

| 429 | RATE_LIMITED | 재시도 시점 안내, 우회 제공 없음 |
| 500·503 | INTERNAL_ERROR / TEMPORARILY_UNAVAILABLE | 요청 ID·처리 확인 경로, 중복 재시도 방지 |

전체 HTML과 부분 HTML의 상태 코드·업무 의미는 동일하다. htmx의 기본 4xx 처리에 의존하지 않고 폼 오류 fragment를 안전하게 표시하는 응답 처리 계약을 검증한다. 부분 요청의 세션 만료는 로그인 문서가 작은 영역에 삽입되지 않게 전체 화면 이동으로 처리한다. 부분 응답으로 권한 오류를 성공 상태로 바꾸지 않는다.

## 7. 모바일·접근성·수용 검증

핵심 버튼은 좁은 화면에서도 누를 수 있고 레이블·키보드·포커스·오류 연결을 제공한다. 긴 표는 필수 열 우선 카드 또는 가로 스크롤로 보여 주며 상태를 색만으로 구분하지 않는다. htmx 갱신은 처리 중·완료·오류를 보조기술에 전달한다. 파일 다운로드와 관리자 대량 목록도 모바일에서 상태를 확인할 수 있어야 한다.

화면 수용 검증은 JS 비활성 폼, 부분 오류 표시, 로그인 만료, 연속 클릭·동일 키 재시도, 타 고객사 ID·권한 회수, 취소 대기 표시, 미확정 null/0 구별, 날짜 경계·주 자료 부족, XLSX 필터·버전·단위 일치를 포함한다. 확인 저장·정정 제출이 스스로 사실개정 충돌을 만들지 않음, 사실변경 뒤 재확인, 검토개정만 바뀐 결과의 오래됨도 확인한다. 초기 기획 당시 실행하지 않은 수용 항목과 후속 실제 검증을 구분하며, A안의 실제 수행 범위·통과 수·브라우저 증거는 [A안 품질 보고](../quality/workspace-ui.md)에 보존한다. 하루 흐름 홈의 실제 수행 범위·결과와 새 이미지의 검증 여부는 [홈 품질 보고](../quality/dayflow-home.md)에 별도로 기록하며 이전 이미지의 취약점 검사·지속 부하 결과를 새 이미지에 그대로 적용하지 않는다.

감사 목록은50건 고정·시각/ID 내림차순이며 before/after 커서를 함께 보내지 않는다. 같은 시각과 새 기록이 있어도 이전/다음 범위는 키셋으로 찾으며 전체 원장의 고정 스냅샷으로 표현하지 않는다. 상세는 개인정보/비밀정보가 없는 타입 검증 업무 요약만 전개하고 명시적 참조 해제를 값 누락과 구분한다. 목록과 상세 모두 열람 감사 저장 실패 시 결과를 정상 반환하지 않는다.

표시 구현은 `SeoulTimeDisplay`를 공통으로 사용한다. 화면의 날짜는 ISO, Instant는 서울 `uuuu-MM-dd HH:mm:ss`(화면은 초까지만 표시, 저장·계산은 밀리초 유지), 새 XLSX는 밀리초·`+09:00`을 유지한다. HTML 입력/hidden 값과 저장된 Instant·근무일·원천·이전 XLSX 스냅샷은 바꾸지 않는다. 실제 휴게 JSON은 구간의 날짜·시각만 보여 주며 손상 근거를 원문으로 반사하지 않는다.

## 공통코드·근태코드 4단계 구현 계약

관리자 메뉴에서 공통코드는 운영 관리, 근태코드는 근태 설정에 별도로 노출한다. 대표·공통·결재 기능 권한만으로 두 화면을 사용할 수 없다. 화면 숨김과 별도로 현재 관리자·tenant 검증을 적용한다. 실제 검증·이미지/DB 반영은 [4단계 결과](../quality/code-management.md)를 따른다.

| 경로 | React 화면·동작 |
| --- | --- |
| GET `/admin/common-codes?q&page&groupId&codeQ&codePage` | 그룹 검색/시트와 선택 그룹 상세코드 검색/시트. 각각50행·독립 명령 |
| POST `/admin/common-code-groups/bulk` | 그룹 변경분1~50행 원자 저장 |
| POST `/admin/common-codes/bulk` | 같은 그룹의 상세코드 변경분1~50행 원자 저장 |
| GET `/admin/attendance-types?q&page` | 최신 등록 정책 시트와 적용일·버전별 불변 이력 |
| POST `/admin/attendance-types/bulk` | 근태코드 변경분1~50행·새 정책 버전 원자 저장 |

각 시트는 조회·입력·삭제·저장·취소를 제공한다. 새 행 삭제는 화면 제거, 저장된 공통코드 삭제는 비활성 예정, 저장된 근태코드 삭제는 `enabled=false` 후속 정책 예정이다. 저장 후 코드와 시스템유형은 불변이며 시스템 소유 공통그룹·상세코드는 읽기 전용이다. 다른 공통 시트에 미저장 편집이 있는 상태에서 저장하면 손실 확인을 제공한다.

409/422는 편집/삭제 예정·명령/행 ID·사유·필드 오류를 유지하고 검색 밖 편집 대상의 최신 원본과 정책 이력도 제공한다. 충돌은 최신값과 편집값을 비교한 뒤 명시 확인한다. 503에서 같은 내용의 처리 여부를 재확인할 때 원래 명령 ID를 유지한다. 오류 초점·레이블·처리 중 잠금·미저장 이동 보호는 기존 React 폼 계약을 따른다.

근태 시트는 **최신 등록 정책(미래 예약 포함)**을 편집하며 실제 신청은 대상일 이하 가장 늦은 적용일·동일일 최고 revision을 사용한다. 이력에는 적용기간·동일일 대체 관계·근거·등록자·사유·서울 시각을 표시한다. 새 비활성 버전 뒤에도 이후 예약 정책은 보존한다. 시스템 연차·정정만 신청에 연결하며 신규 코드는 초안/신청 불가 사유를 표시한다. 유급 구분은 메타데이터이고 인정시간·급여 계산은 추가하지 않는다.

신청 상세는 제출 당시 고정된 코드·이름·revision·적용일·단위·유급 구분·차감·근거를 보여 준다. 이 단계에서 본인 연도별 현황이나 모달 작성 흐름은 추가하지 않는다. 세부 DTO·오류/원자 저장 계약은 [코드 관리 상세](code-management.md)를 따른다.
