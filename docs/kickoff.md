# vibe-attendance 프로젝트 시작 문서

## 1. 문서 목적 및 현재 상태

이 문서는 국내 중소기업 대상 근태관리 SaaS 개인 프로젝트의 방향, 설계 원칙, 기능 후보와 후속 의사결정을 정리한다. 제품 기획과 업무 규칙 명세의 출발점이며 구현 명세나 법률 검토 완료 문서가 아니다.

- 기준일 및 프로젝트 시작일: **2026-10-23**
- 현재 단계: **Phase 0 — 초기 문서 정리 및 기획·설계 준비**
- 이번 산출물: `docs/kickoff.md`, `README.md`, `AGENTS.md`, `CLAUDE.md`
- 이번 범위: 문서 작성과 검토. 소스코드, 프로젝트 골격, DB·SQL, 실행 환경, 배포는 생성하거나 실행하지 않는다.

문서의 상태 표기는 다음 의미로 사용한다.

| 표기 | 의미 |
| --- | --- |
| 확정 방향 | 현재 프로젝트에서 채택한 목표·제약·설계 원칙. 구현 완료를 뜻하지 않는다. |
| 권장안·후보 | 검토할 방안이며 MVP 또는 v1에 포함된다는 뜻이 아니다. |
| 미정 | 후속 단계에서 결정할 항목. 이 문서에서 임의로 확정하지 않는다. |
| 검증 필요 | 공식 자료 확인이나 실험이 필요한 항목. 최신성·적합성·법적 해석을 보장하지 않는다. |

기술 버전과 법령 세부 기준은 이번 작업에서 외부 조회하지 않았다. 버전의 출시·지원 상태, 조문, 적용 대상, 시행일, 휴가 일수와 계산 기준을 검증된 사실로 취급하지 않는다.

공개 법령, 공식 자료와 일반적인 HR 업무 지식을 기반으로 독립적으로 개발한다. 특정 회사 시스템을 복제하지 않으며, 해당 회사의 비공개 소스코드·문서·운영 데이터는 사용하지 않는다.

AI는 기획, 설계, 코드 작성, 테스트, 문서 검토를 지원한다. AI가 생성한 결과는 개발자가 검토하고 검증한다. 이 개발 방식은 제품 자체에 AI 기능을 탑재한다는 의미가 아니다.

## 3. 제품 정의 및 타깃 고객

**상시근로자 10~300명 규모의 국내 중소기업을 주요 고객으로 하는 웹 기반 근태관리 SaaS**를 목표로 한다. 서비스 지원 최소 규모는 5인 이상 사업장으로 설정한다. 이 수치는 제품의 대상 범위이며, 개별 법령의 적용 여부를 일괄 판정하는 기준이 아니다.

확정 방향은 다음과 같다.

- 여러 고객사가 하나의 애플리케이션을 사용하는 멀티테넌트 서비스로 운영한다.
- 고객사별 독립 설치를 전제로 하지 않는다. 고객사 수가 늘어도 가능한 한 동일한 애플리케이션을 유지한다.
- 고객사별 설정은 허용하되, 고객사별 별도 코드 개발과 개별 기능 커스터마이징은 지양한다.
- PC와 모바일 브라우저를 지원하는 반응형 웹을 지향하며 PWA를 계획한다.
- 1인 개발·운영에 맞게 복잡도를 줄이면서 개인정보 보호, 계산 정확성, 데이터 격리를 핵심 품질로 다룬다.

단일 애플리케이션은 코드와 서비스 운영 방식에 관한 결정이다. **단일 서버로 모든 고객을 수용할 수 있다는 가정은 확정하지 않는다.** 고객사 수, 동시 사용자, 출퇴근 집중, 집계·출력 작업을 반영한 부하 테스트로 검증한다.

업무 복잡도는 사원 수뿐 아니라 지원 근무제와 예외 정책에 크게 좌우된다. 고객 수용 범위를 정하기 전에 지원 근무제와 지원하지 않는 시나리오를 명확히 정의한다.

### 기술 선택 원칙

- 초기 구조는 업무 도메인별 모듈형 모놀리식으로 구성한다. MSA와 Kubernetes는 초기 범위에서 제외한다.
- Thymeleaf와 htmx를 사용하며 React/Vue SPA는 초기 범위에서 제외한다.
- MyBatis 기반 SQL 중심으로 데이터에 접근하고 업무 계산은 Java 서비스 계층에서 처리한다.
- 핵심 업무 규칙을 DB 저장 프로시저에 구현하지 않는다. DB 제약·트랜잭션·RLS는 정합성과 보안을 위한 장치로 사용한다.
- DB 스키마 변경은 Flyway로 버전 관리한다.
- 기존 공통 기능과 표준 기능을 우선 재사용하고 신규 의존성은 필요성·유지보수·호환성을 검토한다.
- 상용 라이선스 의존성을 최소화하며, 오픈소스도 버전별 라이선스와 사용 조건을 확인한다.

공식 문서와 릴리스 정보를 검증해 버전 조합을 결정한 뒤 Phase 4의 프로젝트 생성을 진행한다. 계획 버전을 사용할 수 없거나 호환되지 않으면 근거와 대안을 기록하고 기술 결정을 갱신한다.

## 6. 시스템 아키텍처

```text
직원·승인자·근태 담당자·서비스 운영자의 웹 브라우저
                         ↓ HTTPS
                        Caddy
                         ↓
       Spring Boot 단일 애플리케이션
       Thymeleaf 화면 · htmx 응답 · 인증 · 업무 로직
                         ↓
                  PostgreSQL 공유 DB
```

애플리케이션 하나가 화면과 업무 로직을 함께 처리한다. 실제 운영 배치, 연결 보안, 프로세스·인스턴스 수는 후속 설계와 부하 검증에서 정한다.

### 멀티테넌시와 데이터 격리

고객사별 데이터 격리는 시스템의 핵심 보안 요구사항이다.

- 고객사는 하나의 DB를 공유하며 고객사 업무 데이터에 `tenant_id`를 적용한다.
- 로그인한 사용자의 인증 정보와 검증된 소속·권한에서 테넌트를 식별한다. 요청 본문·URL·헤더로 전달된 `tenant_id`를 신뢰하지 않는다.
- 업무 SQL의 명시적인 테넌트 조건과 PostgreSQL RLS를 함께 적용한다. 조회뿐 아니라 등록·수정·삭제, 조인, 집계, Excel 출력에도 격리 원칙을 적용한다.
- 일반 애플리케이션 DB 계정과 관리·마이그레이션 계정을 분리한다. 테이블 소유자, 슈퍼유저, RLS 우회 권한 등의 영향을 검토하고 일반 요청에 관리 계정을 사용하지 않는다.
- 커넥션 풀 재사용 시 테넌트 컨텍스트가 다른 요청으로 누출되지 않도록 한다. 트랜잭션 범위의 컨텍스트 설정과 종료·실패 시 처리 방식을 검토한다.
- 테넌트 정보가 없거나 검증되지 않은 요청을 허용하지 않는 방향으로 설계한다. 배치·재집계·비동기 작업에도 명시적인 테넌트 범위를 적용한다.
- 서비스 운영자 권한은 고객사 권한과 분리한다. 운영자라는 이유로 전체 고객사 데이터 접근을 자동 허용하지 않으며 필요한 접근 범위와 감사 정책을 별도 설계한다.
- 다른 고객사의 식별자 접근, 요청 테넌트 변조, 테넌트 조건 누락, 커넥션 재사용·실패 경로, 운영자 접근에 대한 차단 테스트를 필수로 둔다.

RLS의 실제 정책과 권한 구성은 공식 문서 검증 및 보안 설계 단계에서 정한다. 이 문서는 SQL이나 DB 계정을 생성하지 않는다.

### 사용자 역할

| 역할 | 책임의 초안 |
| --- | --- |
| 직원 | 본인 출퇴근 기록, 근태·휴가 신청, 내역·잔여 휴가·근로시간 조회 |
| 승인자 | 허용된 범위의 신청 승인·반려와 팀원 현황 확인 |
| 근태 담당자 | 고객사 내 설정, 집계, 정정 이력, 마감 및 관리 업무 |
| 서비스 운영자 | 고객사·요금제·사용량 등 SaaS 운영 |

세부 권한, 복수 역할, 조직 범위와 운영자 지원 접근 절차는 후속 명세에서 확정한다.

### 시간 관리

- 기본 업무 시간대는 `Asia/Seoul`로 둔다.
- 실제 출퇴근 시각과 근무일을 분리한다. 저장·표시·집계의 시각 처리 방식은 인터페이스와 데이터 설계에서 일관되게 정의한다.
- 자정을 넘기는 근무의 근무일 귀속, 휴게·야간·휴일 구간의 경계는 지원 근무제별로 정의한다.
- 법정 기준과 회사 정책의 적용 시작일·종료일, 규칙 버전과 산정 근거를 관리하여 과거 결과를 재현할 수 있게 한다.

## 7. 핵심 설계 원칙

### 7.1 원천 데이터 보존

출퇴근 원천 기록은 원칙적으로 직접 수정·삭제하지 않고 정정 이력을 추가한다. 원천 기록, 정정 신청·승인, 산정 결과를 구분하며 근무 스케줄·출퇴근 기록·승인된 신청을 바탕으로 결과를 산정한다.

정정 사유, 처리자, 처리 시각과 변경 전후의 관계를 추적할 수 있어야 한다. 이 원칙은 무기한 보관을 의미하지 않는다. 자료 유형별 법정 보존 대상·기간, 개인정보 보유 근거, 파기 또는 익명화 정책을 함께 검토한다. 구체적인 기간은 **검증 필요**다.

### 7.2 업무 규칙과 데이터 분리

계산 알고리즘은 Java 코드와 테스트로 관리한다. 근로시간 관련 기준, 법정 휴가 기준, 공휴일, 가산율, 적용 시작·종료일, 규칙 버전은 적절한 데이터 구조로 관리할 수 있도록 설계한다.

법정 기준과 고객사 정책의 관계 및 설정 가능한 범위를 명세한다. 기준 변경을 기존 데이터 전체에 즉시 덮어쓰지 않는다. 과거 결과에 적용한 규칙·기준·입력의 근거를 남기고, 재집계가 필요한 경우 적용 범위와 승인 절차를 정한다. 법령 변경의 소급 적용 여부는 사안별 공식 자료와 법률 검토가 필요하다.

### 7.3 근태 집계의 정확성

근태 계산을 제품의 가장 중요한 기능으로 취급한다. 다음 항목은 각각 입력값, 기대 결과, 경계 조건을 포함한 테스트 케이스로 검증할 수 있어야 한다.

| 계산 대상 | 명세·검증할 시나리오의 예 |
| --- | --- |
| 소정근로시간·실근로시간 | 스케줄과 실제 기록의 차이, 누락·중복 기록, 근무일 귀속 |
| 휴게시간 | 휴게 구간의 중첩, 실제 근로와의 구분, 구간 경계 |
| 연장·야간·휴일근로 | 구간 분할, 자정·휴일 경계, 유형 중첩, 적용 기준일 |
| 연차·반차·시간 단위 휴가 | 발생·사용·잔여량, 근무시간과 휴가 구간의 관계, 단위·반올림 |
| 출퇴근 정정 | 승인 전후 산정, 이력 재현, 마감 데이터 변경 영향 |
| 근무제별 산정 | 지원 근무제의 기준 기간·예외·자정 통과, 미지원 시나리오 처리 |

표는 테스트 주제이며 법정 수치나 산식을 확정하지 않는다. 실제 기준을 검증한 뒤 테스트 기대값을 확정한다. 계산 변경 시 단위·경계·회귀 테스트를 먼저 작성하고 구현한다.

### 7.4 데이터 정합성

- 신청과 승인 상태 전이, 처리 권한과 승인 시점을 명세한다.
- 중복 신청 및 기간 중복을 검증하고 동시 신청·동시 승인에 대한 경쟁 조건을 제어한다.
- 승인 취소와 출퇴근 정정은 이력 및 집계에 미치는 영향을 함께 관리한다.
- 월 마감 후 변경 권한, 잠금 범위, 재집계·재마감·재정산 절차를 정의한다.
- 트랜잭션·DB 제약·동시성 제어를 활용하되 구체적인 수단은 업무 규칙과 인터페이스를 정한 후 선택한다.

마감과 재정산 정책은 미정이다. 위 항목은 설계 요구사항이며 특정 상태도나 잠금 방식을 확정한 것은 아니다.

### 7.5 보안과 개인정보 보호

- 업무에 필요한 최소 개인정보만 수집한다. 주민등록번호, 계좌번호, 진단명 등 초기 업무에 불필요한 정보는 수집하지 않는 방향으로 설계한다.
- 역할별 접근 권한, 고객사별 데이터 격리, 인증·비밀번호 재설정·세션 보안을 적용한다.
- 출퇴근·정정·승인·마감·권한 변경과 운영자 접근 등 중요 행위에 감사 로그를 남기도록 설계한다. 로그 자체의 개인정보·비밀정보 노출과 보존·열람 권한도 통제한다.
- 비밀정보는 환경변수로 주입하고 저장소에 실제 값을 기록하지 않는다. 운영 데이터와 테스트 데이터를 분리한다.
- 보안 설정을 개발 편의로 임의 완화하지 않는다. CSRF 등 브라우저 보안과 htmx 요청의 인증·권한 처리를 함께 검토한다.
- PWA 사용 시 개인정보 화면의 캐시, 로그아웃 후 잔존 데이터와 공용 기기 사용을 검토한다.

## 9. 업무 도메인 구조

다음은 향후 Java 패키지를 나눌 설계 초안이다. 실제 구현 단계에서 조정하며 이번 단계에서는 패키지나 빈 소스 파일을 생성하지 않는다.

| 도메인 | 책임 초안 |
| --- | --- |
| `common` | 인증, 권한, 멀티테넌시, 감사 로그, 공통 기능 |
| `org` | 회사, 부서, 사원 |
| `schedule` | 근무유형, 근무 스케줄, 휴일 |
| `clock` | 출퇴근 원천 기록과 관련 처리 |
| `request` | 근태 신청과 승인 |
| `leave` | 연차 및 휴가 |
| `worktime` | 근로시간 계산, 집계, 월 마감 |
| `console` | SaaS 서비스 운영자 관리 기능 |

MyBatis Mapper XML은 업무 도메인별로 분리한다. 비즈니스 로직과 데이터 접근 로직을 분리하고 도메인 간 인터페이스·스키마를 먼저 정의한다. DB 변경 이력은 Flyway로 관리한다. `common`에는 실제로 공유하는 기능을 두며 근태 업무 규칙을 무분별하게 모으지 않는다.

## 10. 인프라 및 운영 계획

개발·운영 환경은 **로컬 개발 → VPS 데모 및 파일럿 → 운영 환경 검토 → 정식 서비스** 순서로 확장한다. 초기 실행 환경은 Docker Compose 기반 애플리케이션·PostgreSQL 구성을 계획하고, 외부 HTTPS 진입에 Caddy를 사용한다.

기존 VPS의 다른 개인 프로젝트를 고려하여 기존 컨테이너·포트·프록시 설정을 임의 변경하지 않는다. 환경 구성 전 현황과 자원·네트워크 충돌을 확인한다. 이번 단계에서는 Docker 실행, 서버 접속, 기존 서비스 접근, 배포를 수행하지 않는다.

| 운영 주제 | 후속 설계·검증 사항 |
| --- | --- |
| HTTPS·접근 통제 | 인증서, 프록시 신뢰 범위, DB 비공개 접근, 관리 접근 분리 |
| 환경변수·비밀정보 | 주입·보관·교체 방식, 실제 값의 저장소·로그 유출 방지 |
| 백업·복구 | 서버 외부 저장소 백업, 접근 통제, 보존 정책, 정기 복구 테스트 |
| 상태·오류 관측 | Actuator 헬스체크, 로그·오류 모니터링, 감사 로그 접근 통제 |
| 성능·용량 | 출퇴근 집중 요청, 고객사별 데이터 증가, 월 집계·Excel 출력의 부하 테스트 |
| 데이터 보호 | 운영·테스트 분리, 보존·파기, 백업·로그·외부 서비스의 저장 위치 |
| 업데이트 | OS·컨테이너·의존성 보안 업데이트, 변경 검증과 장애 복구 절차 |

유료 고객의 개인정보를 처리하기 전에는 국내 리전 사용 여부와 국외 이전 관련 법적 요건을 검토한다. 현재 VPS가 운영에 적합한 리전·보안 수준을 갖췄다고 가정하지 않는다. 유료 운영 인프라와 국내 리전 이전 시점은 미정이며 백업·로그·모니터링 경로도 검토 대상에 포함한다.

## 11. 법령 및 공식 자료 검토 대상

이 절은 조사 범위다. **조문 번호, 적용 대상, 시행일, 휴가 일수와 계산 기준은 모두 공식 검증 후 명세한다.** 법령 전체 분석이나 계산 로직 구현은 이번 범위에 포함하지 않는다.

### 후속 조사 및 명세 원칙

- 국가법령정보센터의 현행 법령과 시행 예정 개정, 부칙·경과 규정 및 적용 대상·시점을 구분한다.
- 상시근로자 수, 대상 근로자, 근무제 도입 요건 등 실제 적용 조건을 확인한다. 제품의 최소 지원 규모만으로 모든 규칙을 적용하지 않는다.
- 법령 원문과 공식 설명자료의 성격을 구분한다. 해석이 필요한 부분은 공식 질의·전문가 검토 대상으로 남긴다.
- 기준마다 출처 URL, 관련 조문, 확인일, 시행일·적용 기간, 대상, 예외, 규칙 버전과 테스트 사례를 연결하여 기록한다.
- 과거 근태에는 당시 적용 기준을 재현하고, 개정의 과거 결과 반영 여부는 법적 근거와 재정산 정책을 검토한 뒤 결정한다.
- 검증하지 못한 내용은 `검증 필요`로 유지하며 법정 기준값이나 테스트 기대값을 추정해 확정하지 않는다.

## 12. 사업화 전 검토사항

다음 항목은 사업화 및 실제 고객 데이터 처리 전에 확인할 검토 과제다. 요금이나 운영 인프라, 법적 적합성을 이 문서로 확정하지 않는다.

- 경쟁 서비스 분석, 핵심 고객 문제, 차별점과 파일럿 고객 후보
- 지원 근무제·고객사 설정 범위·미지원 업무의 명확한 안내
- 요금제·가격·사용량 기준, 계약·약관, 고객 지원·장애 대응 범위
- 개인정보 처리 주체·위탁 관계, 처리방침·안내·동의 등 필요한 절차의 적용 여부
- 최소 수집, 자료별 보존·파기, 정보주체 요청 처리와 감사 접근 정책
- 국내 리전과 국외 이전 요건, 운영·백업·로그·모니터링의 실제 데이터 흐름
- 테넌트 격리·권한 검증, 계산 회귀 검증, 성능 측정, 백업 복구와 장애 대응 준비
- 의존성·이미지·외부 자료의 라이선스, 상용 서비스 이용 조건
- 법령 해석과 계산 규칙의 공식 검증 및 필요 시 전문가 검토

파일럿에서도 실제 개인정보를 사용할지 먼저 결정하고, 사용하는 경우 처리 범위와 보호 조치를 사전에 검토한다. 공개 법령에 기반한 독립 개발 원칙은 사업화 이후에도 유지한다.
