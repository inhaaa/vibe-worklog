# 공개 제품 조사와 파일럿 검증 계획

## 1. 목적과 조사 상태

| 항목 | 내용 |
| --- | --- |
| 기준일·조회일 | 2026-10-24, Asia/Seoul |
| 대상 | 국내 사업장용 근태 SaaS 시프티, flex, 샤플의 공개 공식 자료 |
| 조사 방법 | 공식 제품·요금·도움말 페이지를 웹 검색 및 직접 열람 |
| 작성 범위 | 제품 비교, 고객 문제 가설, MVP 범위의 간극, 향후 검증 계획 |
| 현재 상태 | 기획·규칙·설계 문서 작성 중. 제품 구현과 파일럿 실행은 미착수 |
| 내부 근거 | [PRD](../prd.md), [kickoff](../kickoff.md), [README](../../README.md) |

이 문서는 공개 설명에서 확인한 내용을 정리한다. 구독 가입, 유료 체험, 영업 문의, 고객 인터뷰, 실제 제품 조작과 계산 검증은 수행하지 않았다.
제품별 기능은 공급사의 공개 설명이며, 실제 계약에서의 제공 여부·정확성·지원 수준을 독립 검증한 결과가 아니다.
공식 페이지에 있는 법률 준수·부정 기록 방지·효율 향상 표현도 공급사의 주장이다. 이 문서는 법률 적합성이나 보안 효과를 보증하는 사실로 채택하지 않는다.
시장 규모, 유료 전환율, 고객의 지불 의사나 경쟁 제품 대비 우월성은 이번 조사로 확인하지 않았다.

## 4. 고객과 문제 가설

우리 제품의 주요 대상은 **상시근로자 10~300명 국내 사업장**, 최소 지원 규모는 **5인 이상**이다.
이는 제품의 지원 범위이며 개별 노동관계 법령의 적용 기준을 한 번에 정하는 숫자가 아니다.
초기에는 당일 한 구간 고정 근무와 단순 승인으로 핵심 흐름을 검증할 수 있는 조직을 우선한다.
특정 업종의 수요, 고객 규모별 구매 비중과 현재 도구 사용 현황은 현장 조사 전이다.

| 가설 ID | 검증할 문제 | 반증·수정 조건 |
| --- | --- | --- |
| H01 | 기록·신청·승인이 분리되면 담당자가 같은 사실을 반복 대조할 수 있음 | 기존 도구만으로 연결이 충분하고 전환 이유가 없다면 가설 약화 |
| H02 | 직원이 상태·잔여 근거를 직접 확인하면 담당자 문의를 줄일 수 있음 | 문의의 주원인이 화면 정보가 아닌 규정 해석·조직 문화라면 가치제안 수정 |
| H03 | 정정·정책·승인 이력에서 집계 근거를 찾는 기능이 담당자에게 유용할 수 있음 | 실제 업무가 최종 합계만 요구하거나 기존 서비스로 충분하면 우선순위 재검토 |
| H04 | 여러 고정 템플릿과 적용일 배정으로 초기 고객의 핵심 일정을 표현할 수 있음 | 반차·교대·자정 통과가 매일 필수이면 현재 파일럿 대상과 맞지 않음 |
| H05 | 좁은 기능과 동일 코드 운영으로 1인 개발·운영 부담을 통제할 수 있음 | 고객별 개별 개발·상시 수동 개입이 필요하면 범위나 사업화 판단 재검토 |

위 표는 인터뷰나 실사용 데이터에서 도출한 결과가 아니다. 수요·시간 절감·지불 의사는 검증 전 가설이다.

## 5. 우리 MVP의 선택과 간극

경쟁 제품은 더 넓은 근무제·휴가·승인·연동 기능을 공개한다. 우리 MVP는 확정된 흐름의 검증 범위를 좁힌다.

| 항목 | 우리 MVP의 기획 결정 | 간극과 검증할 점 |
| --- | --- | --- |
| 일정 | 여러 고정 템플릿·사원별 적용일, 당일 한 구간 | 교대·선택적·탄력적 근무 등이 필수인 고객은 초기 적합 대상에서 제외 |
| 기록 | 허용 IP 우선, 온라인 반응형 웹 | IP가 현장 존재·본인임을 보장하지 않음. 실제 허용망과 정정 경로 검증 필요 |
| 승인 | 1단계 지정, 직원·승인자 겸임 가능, 자기 승인 금지 | 복잡한 승인선·자동 대결을 요구하면 현재 범위와 불일치 |
| 연차 | 종일, 기초 잔여 근거·조정 이력, 승인 시 차감 | 반차·시간차·자동 발생은 후속. 기초 값의 적정성은 별도 검증 |
| 대기 연차 | 잔여를 예약·차감하지 않고 대기량 별도 표시 | 다른 신청 승인 후 잔여가 부족할 수 있음을 이해하는지 확인 |
| 검토 출력 | C03 일반 검토용 xlsx 포함 | 원천·정정·정책·미해결 표시와 화면의 일치 확인. 급여 확정 출력 아님 |
| 추가 근무·마감 | C02 추가 근무 신청, C04 월 마감은 후속 | 미지원 근로를 무시하거나 정상 집계로 숨기지 않고 확인 필요로 드러내야 함 |
| 모바일 | 온라인 반응형 웹 포함, C05 PWA는 후속 | 설치·오프라인 기록·네이티브 앱 요구가 핵심이면 적합성 재검토 |

위 결정은 구현 완료를 뜻하지 않는다. 상세 정책은 [계산 규칙](../rules/calculation.md), [신청·승인 규칙](../rules/workflow.md), [아키텍처](../design/architecture.md)와 [보안 설계](../design/security.md)에서 구체화한다.
가치제안은 **고정 근무의 기록→신청→승인→검토를 연결하고 결과의 근거를 확인하도록 돕는 것**이라는 가설로 둔다.
근거 추적과 단순 운영이 고객에게 중요한지는 따로 검증한다. 1인 운영의 단순함 자체가 고객의 구매 이유로 입증된 것은 아니다.
낮은 가격, 쉬운 도입, 더 정확한 계산, 유일한 감사 기능을 경쟁 우위로 확정하지 않는다.

## 6. 파일럿 선정·제외 조건

아래는 향후 후보를 평가할 조건이다. 실제 파일럿 고객·연락처·도입 일정은 없다.

### 선정 조건

- 제품 지원 규모에 맞으며 고정 근무·종일 연차·1단계 승인으로 평가할 업무를 구성할 수 있다.
- 여러 고정 템플릿과 적용일, 기초 잔여의 근거를 설명할 담당자가 있다.
- 승인자가 둘 이상 필요한 관계를 구성해 자기 신청을 타인이 검토할 수 있다.
- 허용 IP 기반 온라인 기록을 검토할 수 있고, 실패 시 정정 절차를 수용한다.
- 기존 업무를 즉시 폐기하지 않고 검증된 기준과 대조할 수 있다.
- 현재 미지원 범위와 잠정 집계를 이해하고 모의자료 검증부터 참여할 의사가 있다.

### 제외·보류 조건

- 교대·자정 통과·하루 여러 구간, 반차·시간차, 복잡한 승인선이 핵심 일상 업무다.
- GPS·생체·출입 장비, 급여 자동 계산, 오프라인 기록이나 개별 코드 개발이 필수다.
- 제품만으로 노동관계 법령 준수나 급여 확정을 보증받아야 한다.
- 실제 개인정보·근태 자료를 보호 조치와 처리 범위 검토 없이 즉시 올려야 한다.
- 운영 장애 대응·복구·보안 검증이 끝나기 전 유료 운영을 요구한다.

제외는 해당 고객이나 업종의 업무가 불필요하다는 판단이 아니다. 현재 MVP로 안전하게 검증하기 어려운 범위를 구분하는 것이다.

## 7. 모의 검증부터 시작하는 순서

1. **문서 시나리오 대조:** 아래 흐름을 직원·승인자·담당자 관점에서 설명하고 누락·오해를 기록한다.
2. **모의자료 사용성 검증:** 향후 구현과 기본 검증 후 가짜 인물·기록만 사용해 PC·모바일 흐름을 평가한다.
3. **후보 인터뷰:** 별도 실행 요청과 대상자 참여 절차를 정한 뒤 질문지로 실제 문제와 지원 범위를 확인한다.
4. **실제 파일럿 판단:** 처리 범위·보호 조치·계약·운영 준비·기준선을 검토하고 별도로 결정한다.

현재는 1단계를 위한 계획 문서다. 2~4단계가 실행되거나 승인된 실제 데이터 처리로 간주하지 않는다.
모의 시나리오의 회사명은 **견본회사 A·B**로만 표기하며 실고객이 아니다. 직원도 사원 A01 같은 합성 식별자를 사용한다.
연락처를 수집하거나 실명·이메일·급여·휴가 사유를 자료로 요청하지 않는다. 문제 가설 확인에 원본 인사 문서는 필요하지 않다.
모의자료 규모는 두 테넌트와 각 10개 합성 사원으로 시작하는 설계상 표본이다. 실제 300명 부하나 시장 대표성을 입증하지 않는다.

| 시나리오 | 확인할 행동 | 기대 판단 |
| --- | --- | --- |
| P01 이용 준비 | 합성 사원·템플릿·적용일·승인 관계·기초 잔여 설정 | 필수 근거 누락을 알아보고 무근거 값으로 확정하지 않음 |
| P02 기록과 실패 | 허용망 출퇴근, 비허용망 실패, 재시도·중복 요청 | 성공·실패·확인 필요를 구분하고 중복 반영하지 않음 |
| P03 정정 | 누락 정정 신청, 사유·전후 값 검토, 타 승인자 처리 | 원천을 보존하며 결과에서 정정·승인 이력을 찾음 |
| P04 종일 연차 | 대기 신청 둘, 한 건 승인 후 다른 건 잔여 부족 | 대기를 예약 잔여로 오해하지 않고 승인 시 재검증 |
| P05 권한 | 자기 승인, 다른 담당 범위, 견본회사 B 자료 접근 시도 | 모두 정책대로 차단. 일부 성공으로 평균 처리하지 않음 |
| P06 일정 경계 | 적용일 변경, 월·연도 경계와 자정 통과 기록 제시 | 당시 정책 근거와 미지원·미해결 표시를 구분 |
| P07 검토와 출력 | 월 현황에서 근거 조회 후 검토용 xlsx 대조 | 같은 시점·권한의 값·상태·버전이 일치하며 확정 급여로 오인하지 않음 |

수치 계산 기대값은 공식 근거와 [계산 규칙](../rules/calculation.md)에 맞춰 먼저 정의한다. 이 표만으로 근로시간의 법정 기대값을 확정하지 않는다.

## 8. 설계상 지표와 판단 목표

모든 목표는 **실데이터와 기준선이 없는 설계상 목표**다. 현재 성과나 출시 수용을 선언하는 수치가 아니다.

| 지표 | 측정 방법 | 초기 목표·판단 |
| --- | --- | --- |
| 핵심 흐름 완료 | 역할별 P01~P04·P07, 안내 개입 여부·실패 이유 기록 | 최소 5명의 모의 평가에서 시나리오 완료율 90% 이상을 탐색 목표로 설정 |
| 상태 이해 | 대기·승인·반려·확인 필요·잔여 의미를 평가자가 설명 | 설명 질문 정답률 90% 이상 목표. 오해는 UI·정책 개선 항목으로 기록 |
| 근거 추적 | 선택 결과에서 원천·정정·승인·정책을 찾는 시간 측정 | 지정 5개 사례 모두 2분 이내 확인 목표 |
| 계산·출력 정합성 | 확정된 기준 사례와 화면·xlsx 전수 대조 | 모든 필수 사례 일치가 통과 조건. 오차 평균으로 합격 처리하지 않음 |
| 권한·격리·중복 | P02·P05와 별도 자동 검증 | 필수 차단·중복 반영 방지 사례 전부 통과가 조건 |
| 담당자 대조 부담 | 동일 합성 사례의 현재 방식·제안 흐름 소요 시간과 문의 수 기록 | 먼저 기준선 수집. 사전 절감률 약속 없이 증가·감소와 원인 확인 |
| 운영 부담 | 평가 중 수동 데이터 보정·지원 개입·설정 난점 기록 | 원천 직접 수정이나 고객별 코드 분기 없이 복구 가능한지 확인 |

표본이 작으므로 완료율과 시간만으로 시장 수요·법률 적합성·대규모 성능을 입증하지 않는다.
보안·정합성 필수 실패, 지원 범위 오해, 미해결 근로의 정상 표시가 발생하면 실제 데이터 파일럿 진행을 보류하고 원인을 먼저 해결한다.

## 9. 향후 인터뷰 질문지

아래 질문은 실제 인터뷰 결과가 아니다. 개인정보와 회사 내부 자료를 받지 않고 업무 흐름·빈도·판단 근거를 묻는 용도다.

1. 현재 기록·신청·승인·월 검토를 어떤 순서와 도구로 처리하는가?
2. 같은 내용을 두 번 입력하거나 담당자가 재확인하는 지점은 어디인가?
3. 누락·정정을 누가 발견하고 누가 근거를 확인하는가?
4. 최근 일반적인 사례에서 직원이 처리 상태를 몰라 다시 문의하는 이유는 무엇인가?
5. 고정 템플릿과 적용일로 표현되지 않는 근무는 얼마나 자주 필요한가?
6. 종일 연차만 지원하면 어떤 업무가 막히는가? 반차·시간차는 도입의 필수 조건인가?
7. 기초 잔여는 어떤 기준일과 자료로 검증하며, 담당자가 바뀌어도 근거를 찾을 수 있는가?
8. 승인자가 부재하거나 본인이 신청할 때 실제로 누가 검토하는가?
9. 최종 합계에서 원천·정정·정책까지 확인해야 하는 상황은 무엇인가?
10. 검토용 xlsx의 필수 항목과 미확정 표시를 어떻게 해석하는가?
11. 현재 도구로 충분히 해결되는 일은 무엇이며, 전환하지 않을 이유는 무엇인가?
12. 유료 도입을 검토하기 전에 필요한 기능·지원·보안·계약 조건은 무엇인가?

답변 유도나 기능 선호 투표만으로 가설을 확정하지 않는다. 실제 사례의 빈도·영향·현재 대안과 반증을 함께 기록한다.
