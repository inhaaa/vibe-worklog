# MVP 신청·승인·정정 업무 규칙

2026-11-18 확장에서는 종일·오전·오후 연차가 신청서별 결재선을 따르고 최종 승인 시에만 1일 또는 0.5일이 반영된다. 아래 표의 정수 단위는 최초 MVP 기준이다. [연차 단위·중복·취소 규칙](../superpowers/specs/2026-11-18-attendance-codes-half-day.md)

## 1. 범위와 결정 근거

| 항목 | 기준 |
| --- | --- |
| 기준일 | 2026-10-24 |
| 제품 근거 | [PRD](../prd.md)의 D04·D05·D07·D11, F07~F12 |
| 결정 권한 | 사용자의 D01~D05 선택과 남은 기획·설계에 대한 자율 진행 위임 |
| 성격 | 구현 전 제품 정책. 법정 휴가권·임금·근로 사실을 제한하는 법률 해석이 아님 |
| 관련 명세 | [계산 규칙](calculation.md), [보안 설계](../design/security.md), [데이터 모델](../design/data-model.md) |

MVP는 종일 연차와 출퇴근 정정에 같은 1단계 승인 흐름을 사용한다. 추가근무 전용 신청, 일괄 승인, 자동 대결, 공식 월 마감은 후속이다. 실제 초과·야간·휴일 기록은 신청 기능의 제공 여부와 무관하게 보존한다.

## 2. 역할과 승인 관계

| ID | 결정 |
| --- | --- |
| W01 | 직원은 본인 신청·철회·취소 요청과 본인 이력 조회를 수행한다. 타인 대신 작성하는 예외 정정은 담당자 경로로 구분한다. |
| W02 | 근태 담당자는 자기 고객사의 사원·일정·휴가 기초 잔여와 승인 관계를 관리한다. 담당자 역할만으로 신청을 승인하거나 원천 기록을 바꾸지 못한다. |
| W03 | 사원마다 같은 테넌트의 활성 승인자 한 명을 지정한다. 승인자는 지정된 사원의 신청만 처리하며 부서 전체 접근이 자동 부여되지 않는다. |
| W04 | 직원·승인자·담당자 역할의 겸임은 허용한다. 모든 경로에서 신청 대상자 또는 신청 작성자와 승인자가 같으면 차단한다. 다른 고객사 계정을 이용한 우회도 허용하지 않는다. |
| W05 | 최초 담당자는 운영자가 회사 관계와 연락 경로를 별도로 확인한 후 연결한다. 확인 근거·주체·시각을 남기며 공개 가입만으로 고객사 관리자 권한을 부여하지 않는다. |
| W06 | 운영자는 고객사 이용 상태와 최초 담당자 연결만 관리한다. 고객사 업무 조회·정정·승인 권한은 기본 제공하지 않는다. 지원 접근이 필요하면 별도 기능·동의·감사 설계 후 도입한다. |

고객사에는 자기 신청을 타인이 심사할 수 있도록 서로 다른 두 명 이상의 승인 가능한 사용자가 필요하다. 적합한 승인자가 없으면 신청은 대기하며 운영자 승인이나 자기 승인으로 우회하지 않는다. 마지막 활성 담당자의 비활성화·권한 제거는 대체 담당자 연결 후 허용한다.

승인자는 본인에게 할당된 신청의 판단에 필요한 일정·원천·관련 신청만 조회한다. 사유에 불필요한 건강 정보나 제3자의 개인정보를 입력하지 않도록 안내한다. 첨부파일 업로드는 MVP에서 제공하지 않는다.

## 3. 신청 내용과 상태

신청에는 대상 사원, 종류, 대상 날짜, 요청 값, 사유, 작성자, 제출 시각, 버전, 지정 승인 관계의 버전을 기록한다. 종일 연차는 날짜별 소정근로일을 식별하며 휴일·일정 미배정일을 임의의 차감일로 넣지 않는다. 기간 선택은 같은 휴가 부여 묶음의 유효기간 안에서만 허용한다. 경계를 넘으면 묶음별로 나눠 신청한다.

신청은 제출 후 내용을 수정하지 않는다. 대기 중 철회하고 새 신청을 만들거나, 처리 후 별도 취소·정정 요청을 만든다. 재신청에는 이전 신청 식별자를 연결한다. 임시저장 기능은 MVP에 포함하지 않는다.

```text
PENDING → APPROVED
PENDING → REJECTED
PENDING → WITHDRAWN
APPROVED(종일 연차) + 별도 취소 요청(PENDING)
  → 취소 요청 APPROVED: 원신청 효력 취소, 이력 보존
  → 취소 요청 REJECTED/WITHDRAWN: 원신청 효력 유지
```

승인 후 취소 요청은 종일 연차에만 제공한다. 승인된 출퇴근 정정은 취소하지 않고 현재 유효 버전을 참조하는 새 정정 신청으로만 변경한다.

원신청의 처리 상태와 현재 효력은 구분한다. 승인 이력은 취소 후에도 APPROVED로 남고, 승인된 취소 요청의 연결로 현재 효력을 CANCELED로 표시한다. 최종 상태를 다시 PENDING으로 되돌리지 않는다.

| 행위 | 주체와 조건 | 효과 |
| --- | --- | --- |
| 제출 | 활성 직원 또는 사유를 남긴 담당자, 같은 고객사 대상, 유효한 승인 관계 | PENDING 생성. 연차 잔여 차감·예약 없음 |
| 승인 | 현재 할당 승인자, 활성 권한, 자기 승인 아님, 상태·버전 일치 | APPROVED와 잔여 원장·정정 효력을 한 트랜잭션으로 반영 |
| 반려 | 현재 할당 승인자, PENDING, 사유 필수 | REJECTED. 잔여·집계 미반영 |
| 철회 | 작성자, PENDING | WITHDRAWN. 사유·시각 보존, 동일 요청 반복은 한 번만 반영 |
| 재신청 | 새 입력 검증, 이전 신청 연결 | 새 식별자·PENDING. 이전 기록 유지 |
| 취소 요청 | 승인되어 현재 유효한 원신청, 다른 유효 취소 요청 없음 | 별도 PENDING 생성. 심사 중 원승인·차감·집계 효력 유지 |
| 취소 승인 | 독립 승인자, 원신청 현재 효력·취소 요청 상태·버전 재검증 | 원신청 효력 취소, 실제 원장 차감량을 한 번만 복원, 영향 기간 재집계 |

잔여 부족·일정 변경 등으로 승인 검증이 실패하면 신청은 PENDING에 남긴다. 실패를 반려로 자동 변환하지 않고 원인과 재검토 방법을 표시한다. 명시적 반려에는 별도의 사유와 이력을 남긴다.

## 4. 승인자 부재·변경과 계정 상태

1. 담당자가 같은 고객사의 다른 적격 승인자를 선택하고 사유·적용 시각·이전 관계를 남긴다.
2. 새 신청은 새 관계를 사용한다. 기존 대기 신청은 자동 이동하지 않으며, 담당자가 대상 건을 확인해 명시적으로 재할당한다.
3. 재할당 시 자기 승인 조건을 다시 확인하고 신청 버전을 올린다. 이전 승인자의 열린 화면에서는 기존 버전으로 처리할 수 없다.
4. 승인자 퇴사·비활성화·권한 제거 후에는 기존 세션으로도 처리를 차단한다. 대기 신청은 보존하고 담당자에게 재할당 필요로 표시한다.
5. 신청 대상자가 비활성화되어도 기록을 삭제하지 않는다. 새 신청·일반 승인은 차단하고 과거 자료 정정이 필요하면 담당자 예외 경로를 사용한다.

자동 위임, 기간별 대결, 다단계 승인, 운영자 대리 승인, 이메일·메신저에서의 직접 승인은 후속이다. 담당자의 재할당은 승인 자체가 아니며 이력을 남겨야 한다.

## 5. 종일 연차와 기초 잔여

### 기초 등록과 차감

- 담당자는 사원·기준일·유효기간·일수·발생 근거의 참조·등록 사유를 입력한다. 원본 인사 문서나 민감한 상세 사유를 업로드하지 않는다.
- 담당자가 확인한 기초 잔여와 증감 조정은 0.5일 단위로 입력한다. 이보다 작은 값은 반올림하지 않고 오류로 표시한다. [잔여 이관·조정 명세](../superpowers/specs/2026-11-18-leave-balance-batch.md)
- 등록과 증감 조정은 기존 값을 덮어쓰지 않는 원장 항목이다. 등록자·변경 전후 잔여·근거·시각을 보존한다. 기초 등록 자체는 법정 발생·소멸의 정확성을 보증하지 않는다.
- 미래 일정이 확정된 소정근로일마다 종일 연차 1 DAY를 산정한다. 신청량과 승인 시 검증량이 달라지면 승인하지 않고 철회·재신청을 안내한다.
- 유효기간이 다른 기초 묶음을 하나의 신청에서 혼합 사용하지 않는다. 자동 발생·소멸·이월은 후속이며 유효기간이 지난 미사용분을 자동 삭제하지 않는다.
- PENDING은 예약·차감하지 않고 대기량과 현재 잔여를 나란히 표시한다. 현재 잔여가 곧 모든 대기 신청의 승인 가능량은 아니다.
- 승인 시 원장 최신 잔여·유효기간·일정·중복 신청을 재검증한다. 부족하면 차감과 승인 모두 하지 않는다. 음수 잔여와 무근거 증액은 허용하지 않는다.
- 담당자 본인의 기초 등록·증액·감액은 다른 담당자가 수행한다. 담당자 한 명만 있는 경우 먼저 다른 담당자를 지정한다. 변경 후 이미 승인된 사용량보다 작아지는 감액은 차단하고 정정 근거부터 검토한다.

### 철회·취소·과거 정정

예정된 연차 시작 전에는 작성자가 취소 요청하고 지정 승인자가 심사한다. 승인 전까지는 사용 예약의 업무상 효력과 원장 차감이 유지된다. 미승인 취소를 이유로 직원이 출근했다는 실제 기록을 숨기지 않는다.

연차 시작 시각이 지났거나 이미 사용한 날짜, 퇴사자의 과거 건은 담당자가 사실·근거·대상 기간을 확인해 예외 취소·정정을 신청하고 다른 적격 승인자가 심사한다. 직원은 본인 정정 필요를 담당자에게 전달할 수 있다. 과거라는 이유만으로 사실 기록을 소거하거나 법적 권리를 차단하지 않는다.

취소 승인 시 원래 차감 원장 항목을 참조해 정확히 같은 양을 복원한다. 현재 일정으로 차감량을 새로 계산해 복원하지 않는다. 유효기간이 지난 묶음에 복원되면 사용 가능 잔여로 자동 노출하지 않고 근거 검토 대상으로 표시한다. 법정 소멸·이월 판단은 별도 검증 사항이다.

## 6. 출퇴근 정정과 계산 결과

- 원천 이벤트는 수정·삭제하지 않는다. 정정 신청에 기존 근거 식별자·대상 근무일·제안 시각·사유·작성자·버전을 남긴다.
- 정정은 서버가 관측한 실제 기록을 대신하는 값과 구분한다. 승인된 정정 값에서 원천·신청·승인 이력을 역추적할 수 있어야 한다.
- 누락된 퇴근을 다음 날 신청해도 자정 자동 퇴근이나 이전 이벤트 삭제로 처리하지 않는다. 정상 지원 경계 밖이면 REVIEW_REQUIRED를 유지한다.
- 같은 사원·근무일의 PENDING 정정은 최대 한 건, 현재 효력 있는 승인 정정도 최대 한 건이다. 새 정정 승인 시 이전 정정의 현재 효력만 SUPERSEDED로 바꾸고 APPROVED 처리 이력은 유지한다. 승인된 정정을 바꾸려면 현재 유효 버전을 참조하는 새 정정 신청을 만든다.
- 근로 유무·시간에 영향을 주는 대기 정정이 있으면 비근로일·연차일 무기록을 포함해 해당 일·주·월은 확인 필요로 표시한다. 과거 0시간 결과는 이력으로 남기되 현재의 정상 확정값처럼 제공하지 않는다.
- 종일 연차와 실제 근로가 같은 날에 존재하면 사실 기록을 보존하고 확인 필요로 표시한다. 연차를 자동 취소하거나 실근로를 0으로 바꾸지 않는다.
- 소급 일정 변경·연차 취소·정정 승인은 영향받는 일·주·월을 재계산 대상으로 표시한다. 이전 결과는 유지하고 입력 스냅샷·규칙 버전·새 결과 버전·변경 사유를 추가한다.

월별 조회와 집계는 제공하지만 공식 월 마감·잠금·재마감·급여 재정산은 제공하지 않는다. 과거 변경에는 기간 제한을 임의의 일수로 두지 않되 담당자 근거 검토와 독립 승인을 요구한다. 향후 법정 보존 기간이 지나 파기된 원천은 복구 가능한 것처럼 표시하지 않는다.

사실 입력 개정 `input_revision`과 검토 개정 `review_revision`을 구분한다. 대기 정정 제출·철회와 근로·휴게 확인 증거 저장은 사실 입력을 바꾸지 않고 검토 개정 및 재집계 필요 표시만 갱신한다. 정정 승인 시에는 사실 개정을 갱신하고 실제 구간 증거가 있으면 새 사실 개정에 결속한다. 정정의 base 개정·확인 증거는 사실 개정에 대조하며 결과 최신성은 두 개정을 모두 검사한다. 자기 제출·확인 저장 자체로 기존 base가 불일치하는 구조를 만들지 않는다.

계산은 승인과 같은 긴 트랜잭션에서 외부 작업으로 실행하지 않는다. 승인 원장·정정 효력·감사·재집계 필요 표시를 원자적으로 기록하고, 결과 갱신 전에는 기존 결과를 '재집계 필요'로 표시한다. MVP에서는 사용자의 재집계 요청으로 처리할 수 있으며 스케줄러나 메시지 브로커를 필수 구성으로 추가하지 않는다.

## 7. 중복·동시성과 실패 복구

| 위험 | 필수 처리 |
| --- | --- |
| 더블클릭·네트워크 재전송 | 같은 테넌트·사용자·행위의 요청 식별자로 한 번만 반영. 같은 식별자에 다른 본문을 보내면 충돌 |
| 같은 날짜의 연차 중복 | PENDING과 현재 유효 APPROVED의 날짜가 겹치면 제출 차단. 철회·반려·승인 취소된 건은 이력을 보존하며 새 신청 가능 |
| 두 승인자의 동시 처리 | 신청 현재 상태·버전을 잠금 또는 낙관적 조건으로 검사. 한 전이만 성공하고 나머지는 최신 상태 안내 |
| 같은 잔여의 동시 소비 | 사원·기초 묶음별 원장 잔여 검증과 차감을 직렬화. 신청별 유일 차감 참조 보장 |
| 승인과 철회·취소 경합 | 동일 상태·효력의 버전을 확인. 먼저 유효하게 커밋한 전이만 성공 |
| 승인과 재할당·퇴사 경합 | 승인 관계·계정 버전을 같은 트랜잭션에서 재검증. 이미 비활성화된 권한의 승인 차단 |
| 정정 승인과 소급 일정 변경 | 입력 버전 충돌을 검출하고 재검토. 이전 계산 결과를 최신으로 표시하지 않음 |
| 중간 DB 오류 | 상태·원장·효력·감사·재집계 표시 전체 롤백. 부분 차감·유령 승인 금지 |
| 승인 후 화면 응답 유실 | 재요청으로 같은 결과를 확인. 상태를 되돌리거나 다시 차감하지 않음 |
| Excel과 재집계 경합 | 동일 조회 스냅샷과 버전으로 출력하거나 데이터 변경을 알리고 재시도. 화면과 다른 값을 확정본처럼 출력하지 않음 |

실제 잠금·인덱스·트랜잭션 코드는 구현 단계에 작성한다. 테넌트 경계를 넘는 조회·잠금·원장 참조는 허용하지 않는다.

## 9. 남은 검증과 변경 관리

제품의 상태 전이·권한·중복 처리 정책은 이 문서로 채택한다. 법정 휴가 발생·소멸·퇴직 정산·임금 판단, 자료별 보존·파기, 실제 파일럿 적합성과 운영 리전은 별도 검증 사항이다. 사용자 권리와 관련된 불명확한 해석을 제품 기본값으로 확정하지 않는다.

구현 전에는 WF01~WF21과 계산·테넌트 격리 사례를 테스트로 먼저 작성한다. 정책을 바꾸면 관련 PRD 결정·이 문서·데이터 및 화면 계약·테스트 기대값을 같은 작업 단위에서 갱신한다. 실제 구현과 자동 테스트 실행은 이번 문서 작업에 포함하지 않는다.
