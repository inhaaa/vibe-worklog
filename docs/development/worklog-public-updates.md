이번 변경은 반복 작업 지침을 개발·배포 두 브랜치에 기록한 문서 작업이다. 새 메뉴 배포나 서버 변경을 실행한 기록이 아니다. 배포할 때마다 아래 조건을 실제 확인하고 결과를 남긴다.

모든 Compose 명령은 `-p worklog-demo`, 절대 경로의 `--env-file`과 `-f`를 명시한다. 전역 Docker 정리·전체 서비스 재시작·`down -v`·다른 프로젝트 명령을 실행하지 않는다. 일반 메뉴 배포에 DNS·Caddy 변경은 필요하지 않다. 공유 VPS의 여유 메모리·디스크를 확인하고 WorkLog 전용 CPU·메모리 제한 빌더를 사용한다. 자원 부족이나 기존 서비스 이상이 있으면 배포를 시작하지 않는다.

## 1. 개발 결과와 공개 보안 통합

1. 변경 메뉴의 명세·테스트·문서를 마무리하고 검증된 커밋 SHA를 고정한다. 미완성 변경이나 다른 작업의 dirty 파일을 배포하지 않는다.
2. 전용 공개 배포 브랜치에서 검증된 개발 커밋과 공개 데모 보안 변경을 통합한다. 개발 브랜치 전체를 검증 없이 공개 소스로 대체하지 않는다. 통합 커밋과 앱·migrate 이미지의 불변 ID를 기록한다.
3. `public-demo` 단독 프로필, 운영자 비활성, 가상 자료 안내, 정상 CSRF 로그인, Secure 쿠키, 공유 데모 계정 보호, tenant/RLS·역할·세션 경계를 유지한다. 새로운 일괄 변경 API도 공유 계정 보호를 우회할 수 없어야 한다.
4. 관련 Java·PostgreSQL 통합 테스트, 프론트 테스트·타입·빌드와 공개 배포 계약 검증을 실행한다. DB·권한 변경은 기존 자료 보존과 격리·동시성 회귀를 포함한다. 로컬 전용 컨테이너 검사와 공개 서버의 포트·rootfs 계약을 구분한다.

2026-10-28 준비 시점의 개발 `main`은 `ecf6dfc`·V13이고 공개 런타임은 `180689d`·V10이었다. 다음 통합에서는 신규 사원 시트 일괄 저장(`OrgBulkService.employees`)에도 공개 공유 사원 보호를 연결하고 우회 거부 테스트를 추가해야 한다. 이 차이는 아직 통합·배포되지 않았다. 최신 상태는 매번 Git과 실제 서버에서 다시 읽는다.

## 2. 배포 전 기록과 이미지 준비

- 정상 서버 접속을 사용한다. 임시 Docker 관리 연결은 연결 권한이 필요할 때만 해당 범위에서 만들고 작업 후 마운트·네트워크·권한 해제를 실제 검사한다. 현재 임시 연결은 해제된 상태다.
- 기존 사이트의 기대 응답과 모든 기존 서비스의 이름·ID·시작 시각을 저장한다. PriceSys의 인증 요구 응답도 정상 기준으로 구분한다.
- WorkLog의 현재 이미지 ID, 스키마 이력, 컨테이너·포트·볼륨·리소스 제한과 Caddy 설정 해시를 기록한다. `.env` 내용, 전체 inspect와 보간된 Compose 설정은 로그·채팅·Git에 남기지 않는다.
- 소스 아카이브의 SHA256을 대조하고 `/srv/worklog` 안에서 준비한다. 기존 `.env`와 DB 볼륨을 덮어쓰지 않는다. 후보 소스·이미지와 이전 이미지를 함께 보존한다.
- WorkLog 전용 제한 빌더로 필요한 app·migrate 이미지만 준비한다. 일반 메뉴 변경에서 DB 이미지를 재빌드하거나 실행 중인 DB를 교체하지 않는다.

## 3. 스키마 변경 유무에 따른 반영

### 기존 스키마를 유지하는 메뉴 변경

새 마이그레이션이 없고 후보 앱이 현재 스키마와 호환됨을 검증한 경우에만 이 경로를 사용한다. 서버 `.env`의 `WORKLOG_IMAGE_TAG`를 검증한 통합 커밋 SHA로 지정하되 다른 비밀값·프록시 설정은 보존한다. 상위 셸의 같은 이름 환경변수가 이전 태그를 덮어쓰지 않는지 확인하고, Compose가 선택한 후보 앱 이미지의 revision label·실제 ID를 준비 기록과 대조한 뒤 명시한 앱 하나만 교체한다. 아래 명령은 이미지가 미리 준비되고 기존 서버 설정이 보존된 상태에서 실행한다.

```sh
docker compose -p worklog-demo --env-file /srv/worklog/source/deploy/worklog/.env -f /srv/worklog/source/deploy/worklog/compose.yaml config --quiet
docker compose -p worklog-demo --env-file /srv/worklog/source/deploy/worklog/.env -f /srv/worklog/source/deploy/worklog/compose.yaml up -d --no-deps --no-build --pull never app
```

기동 성공만으로 완료 처리하지 않는다. 아래 공개 검증을 통과한 뒤 현재 배포 SHA와 이미지 ID를 확정한다. 실패 시 보존한 이전 앱 이미지로 같은 앱만 복귀시키고 재검증한다.

### 새 Flyway 마이그레이션을 포함한 메뉴 변경

V11~V13 같은 새 이력이 있으면 앱 교체만 실행하지 않는다. 변경 전후 스키마·권한과 이전 앱의 호환성을 먼저 정한다. 적용된 과거 마이그레이션을 수정하거나 bootstrap·sample-data SQL을 다시 실행하지 않는다.

1. 전용 임시 DB에서 신규 이력과 기존 합성 자료·RLS·공유 계정 보존을 검증한다. WorkLog DB 백업을 만들고 독립된 전용 DB에서 실제 복원 검증을 마친다. 덤프·서버 비밀값은 서버의 접근 제한 경로에 보관한다.
2. WorkLog 앱만 중지해 변경을 차단하고 최종 백업을 만든다. 현재 세션·시작 시각과 스키마 이력을 기록한다. 다른 서비스는 계속 가동한다.
3. 확인된 WorkLog DB에 별도 migration 역할·migrate 이미지로 새 이력을 실행하고 종료0·최종 이력·기존 자료·권한 보존을 확인한 뒤 후보 앱만 시작한다. 웹앱에는 관리 비밀번호를 전달하지 않는다.
4. 실패 시 스키마 상태부터 확인한다. 마이그레이션이 적용된 DB에 이전 앱 이미지만 무조건 되돌리지 않는다. 검증한 호환 경로 또는 WorkLog 앱 중지 상태의 전용 DB 복원을 사용한다. 복원이 필요하면 최종 백업 이후 방문자 입력 손실 범위를 보고하고 확인한 뒤 실행한다.

## 4. 공개 검증과 완료 기록

- WorkLog HTTPS health·소개·가상 자료 안내·CSRF 로그인/로그아웃·Secure/HttpOnly/SameSite 쿠키와 변경 메뉴를 확인한다. 공개 공유 계정 보호·미인증 업무 접근·운영자/관리 진단 경로 차단도 확인한다.
- 앱의 loopback 단일 게시·DB 비공개·기존 자료 보존을 확인한다. 프록시 신뢰·포트·인증 변경이 있으면 해당 경계의 실제 HTTP 검증을 추가한다.
- 기존 PriceSys·demo·portfolio의 HTTP와 컨테이너 ID/시작 시각을 배포 전 기록과 대조한다. 동시에 발생한 외부 변경은 원인을 추정하거나 되돌리지 말고 시각·증거를 구분해 보고한다.
- 배포 SHA·이미지 ID·스키마 버전·실행 시각(Asia/Seoul)·실제 통과 항목·미실시 항목을 배포 결과 문서와 README에 기록한다. 사용한 임시 관리 연결의 해제까지 확인한다.

이 절차는 개발 작업의 완료 단계로 수행한다. 상시 자동 감시·예약·Git push 트리거를 설치한 것은 아니다. 저장·커밋만으로 배포가 끝났다고 표현하지 않으며 접속·검증에 필요한 조건이 없으면 현재 공개 버전을 유지하고 남은 조건을 보고한다.
