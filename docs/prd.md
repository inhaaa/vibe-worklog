## 2. 제품 목표와 검증할 문제

### 제품 정의와 대상

국내 중소기업을 대상으로 직원의 출퇴근·신청과 관리자의 승인·집계를 연결하는 웹 기반 멀티테넌트 SaaS를 지향한다.

- 주요 고객: 상시근로자 10~300명 사업장
- 서비스 지원 최소 규모: 5인 이상 사업장. 개별 법령의 적용 여부와는 별도로 판단한다.
- MVP 검토 대상: 고정된 근무 요일·시간을 운영하고 단순한 승인 흐름으로 핵심 업무를 검증할 수 있는 사업장
- 운영 방향: 동일 애플리케이션과 공유 DB, 고객사별 설정, 고객별 별도 코드 개발 지양
- 이용 환경: PC·모바일 온라인 반응형 웹. PWA·오프라인 출퇴근은 후속 범위

파일럿 고객이나 특정 업종은 아직 선정하지 않았다. 다음은 고객 조사로 확인할 **문제 가설**이며 시장 조사 결과가 아니다.

| 문제 가설 | 제안하는 제품 가치 | 검증 방법 |
| --- | --- | --- |
| 출퇴근·신청·승인 정보가 분리되면 확인과 대조가 반복될 수 있음 | 원천 기록과 신청·승인·결과의 연결 | 고객 인터뷰와 실제 업무 흐름 비교 |
| 누락·정정·잔여 휴가를 확인할 때 담당자 문의가 반복될 수 있음 | 본인 조회와 처리 상태의 가시성 | 파일럿에서 문의·수작업 대조 사례 수집 |
| 집계 결과의 변경 근거를 추적하기 어려울 수 있음 | 적용 정책과 정정·승인 이력 추적 | 담당자가 결과에서 근거까지 확인하는 사용성 검증 |

[공식 경쟁 제품 조사](research/market.md)는 수행했다. 고객 인터뷰·제품 체험·차별점 실증은 수행하지 않았다. 특정 서비스보다 우수하거나 업무 시간이 일정 비율 줄어든다고 주장하지 않는다.

### 목표와 비목표

- 목표: 직원의 기록·신청부터 승인·확인·집계까지 하나의 흐름을 검증한다.
- 목표: 계산 근거, 미처리 항목과 오류 가능성을 사용자에게 드러낸다.
- 목표: 테넌트 격리와 최소 권한, 원천 기록 보존을 제품의 기본 조건으로 유지한다.
- 비목표: 모든 근무제·법정 휴가·사업장 예외를 한 번에 자동화하거나 급여 계산 시스템을 완성하는 것.
- 비목표: 법률 적합성을 자동 보증하거나 미확정 집계를 급여 확정 자료로 제공하는 것.

AI는 개발을 지원하는 도구이며 제품 내 AI 기능은 이번 범위에 제안하지 않는다.

## 3. MVP 대안과 선택 결과

아래 모든 대안에서 인증·권한, 테넌트 격리, 원천·정정·감사 이력과 계산 검증은 공통 필수 조건이다.

| 대안 | 범위 | 장점 | 제약·부담 |
| --- | --- | --- | --- |
| A. 핵심 업무 연결 — D01 선택 | 고정 근무 중심의 출퇴근, 휴가·정정 신청, 승인, 휴가 잔여 이력, 일·주·월 현황 | kickoff의 핵심 흐름을 검증하면서 지원 규칙을 좁힐 수 있음 | 일정·인증·승인·휴가의 세부 정책과 조건부 기능은 따로 결정해야 함 |
| B. 출퇴근 기록 우선 | 고정 근무, 출퇴근·정정과 내역 조회부터 검증 | 초기 기능과 계산 범위를 더 줄일 수 있음 | 휴가·승인·관리자 집계의 연결 가치를 충분히 검증하기 어려움 |
| C. 운영 업무 확대 | A에 반차·추가 근무 신청·Excel 출력·월 마감·연차 자동 발생 등을 추가 | 더 넓은 관리 업무를 검증할 수 있음 | 법령·상태 전이·정산·동시성 관련 선결정과 검증 부담 증가 |

**D01은 A안인 핵심 업무 연결형 MVP로 확정했다.** 출퇴근 → 휴가·정정 신청 → 승인 → 일·주·월 현황을 연결하는 기능 묶음을 채택한다. 조건부 후보는 별도로 검토하여 C03 일반 검토용 Excel 다운로드만 MVP에 포함하고, C02 추가근무 신청·C04 월 마감·C05 PWA는 후속으로 둔다. v1은 검증된 MVP 이후의 별도 범위다. 일정 관리 수준과 정상 지원 범위는 D02 B안, 허용 IP 기반 출퇴근 인증 우선 지원은 D03 A안으로 별도 확정했다. D04 A안으로 1단계 지정 승인자, 직원·승인자 겸임 허용과 자기 승인 차단을 채택했다. D05 A안으로 종일 연차·근거와 조정 이력이 있는 기초 잔여 등록·승인 시 차감을 채택했으며, C01 반차·시간 단위 휴가·자동 발생과 QR은 후속 후보로 둔다. 세부 신청·승인·취소·정정은 [신청·승인 규칙](rules/workflow.md)을 따른다. 시간·법령·보안의 검증 범위는 각 후속 명세에서 구분한다.

### 고정 근무의 지원 범위와 미정 기준

- 고객사별 여러 고정 템플릿을 사원에게 적용일로 배정한다. 정상 지원은 당일 시작·종료하는 하루 한 근무 구간으로 한정하며 모든 직원에게 같은 요일·시각을 강제하지 않는다.
- 사원별 적용 일정, 근무 요일, 시작·종료 시각, 휴게 구간, 휴일과 적용일을 식별할 수 있어야 한다.
- 고객별 요일·시각·예정 휴게를 설정한다. 법정 일반 기준과 제품 계산 단위는 계산 규칙에서 분리하며, 회사별 실제 적용 근거를 확인한다.
- 소정 일정과 실제 근로 판단 자료를 구분한다. 체류시간 전체를 실근로로 자동 간주하지 않고, 실제 근로·휴게 확인 전에는 실근로를 null로 둔다. 확인 증거는 당시 입력 개정에 결속한다.
- 자정 통과·야간·휴일·일정 외 기록은 예외 식별 대상으로 제안한다. 미지원이라는 이유로 기록을 버리거나 자정에 자동 퇴근시키지 않는다.
- 시차출퇴근, 선택적·탄력적 근로시간제, 교대, 간주·재량근로는 후속 검토 후보로 둔다. 기존 제품 후보 목록은 유지한다.

고정 근무 중심의 MVP 방향은 D01, 일정 관리 수준과 정상 지원 범위는 D02 B안으로 확정했다. 세부 기준은 [계산 규칙](rules/calculation.md)을 따른다. 실제 휴게·근로 확인, 밀리초 정본·절삭 없음, 월요일 주 경계와 회사 정책 일치 확인, 한국 날짜별 월 집계를 채택한다. 성인 통상 고정근로자 일반 규정 밖의 예외와 자정 귀속은 확인 필요로 분리한다.

## 4. 사용자 역할과 권한 제안

역할의 이름은 kickoff를 따르며 다음 책임·권한 범위를 MVP 정책으로 채택한다. 역할을 보유했다는 사실과 접근할 수 있는 고객사·사원·조직 범위를 함께 확인한다.

| 역할 | 주요 목적 | 권한 제안 | 자동 허용하지 않을 행위 |
| --- | --- | --- | --- |
| 직원 | 본인 기록과 신청·결과 확인 | 본인 출퇴근, 휴가·정정 신청, 신청 상태·휴가 잔여·일·주·월 현황 조회 | 타인 기록 조회·신청, 원천 기록 덮어쓰기, 본인 역할 변경 |
| 승인자 | 담당 범위의 신청 처리 | 지정된 대상의 신청 조회·승인·반려, 필요한 팀원 현황 확인 | 고객사 전체 접근, 자기 승인, 지정 범위 밖 승인 |
| 근태 담당자 | 소속 고객사의 설정과 검토 | 조직·사원·일정·휴일·승인 관계 설정, 휴가 기초 정보·조정 이력, 현황·정정 이력 확인 | 원천 기록 직접 변경, 승인 우회, 타 고객사 접근 |
| 대표 | 자기 회사 현황 확인 | 회사 근무·신청의 안전한 읽기. 실제 지정 결재는 별도 APPROVER 기능과 기존 배정 검증 | 관리자 설정·재집계·원장 조정·감사·관리자 Excel, 미지정/자기 승인, 타 고객사 접근 |

역할 겸임은 허용하되 대상자·작성자는 자기 신청을 승인할 수 없다. 사원별 지정 승인자 한 명을 두고 담당자가 사유·이력을 남겨 재지정한다. 대기 건은 명시적으로 재할당하며 자동 대결은 후속이다. 담당자는 고객사 범위, 승인자는 지정 대상, 직원은 본인 범위만 접근한다. 운영자에게 고객사 업무 조회·대리 승인 권한을 주지 않는다.

| F09 | 신청 승인·반려 | 1단계 지정 승인자, 직원·승인자 겸임 허용과 자기 승인 차단, 처리 상태·이력, 담당자 재할당·대기 중 철회·별도 취소 요청 | D04, D05, D07 |
| F10 | 기본 계산·집계 | 고정 일정·실제 기록·승인된 신청과 정책을 근거로 계산, 미해결 항목 표시, 일·주·월 집계 | D02, D06, D07 |
| F11 | 근태 담당자 검토 | 대상 사원의 누락·승인 대기·정정·휴가·집계 상태를 일별·월별로 확인 | D06, D07 |
| F12 | 감사·변경 근거 조회 | 권한·일정·기초 잔여·정정·승인·운영자 행위의 주체·시각·변경 근거 확인 | D11, D12 |
| F13 | 일반 검토용 Excel 다운로드 | 권한 범위의 일·월 현황을 .xlsx로 출력. 대상 기간·생성 시각·계산 버전·확인 필요 상태 표시, 개인정보 최소화 | D08, D12 |

F07은 등록 근거·기준일을 확인하고 조정 사유·처리자·이력을 남겨 기초 잔여를 등록한다. 법정 연차 발생 기준의 검증을 대체하지 않는다. 잔여는 승인 시 차감하며 대기 신청은 차감·예약하지 않고 별도로 표시한다. 승인 시 잔여 재검증과 동시성 제어로 중복·초과 차감을 방지한다. 반차·시간 단위 휴가·자동 발생은 후속 후보이며 자동 소멸·이월·사용 촉진도 기존 후속 후보로 유지한다. 정수 DAY, 같은 기초 묶음의 유효기간 내 소정근로일에 한정한다. 취소 승인 시 원차감량만 한 번 복원하며 법정 발생·소멸의 적정성은 별도 검증한다.

F09는 대기 중 작성자 철회, 승인 후 별도 취소 요청을 지원한다. 취소 심사 중 원승인은 유효하다. 이미 시작·사용한 연차와 과거 정정은 담당자 근거 검토 및 독립 승인으로 처리한다. 승인·원장·효력·감사·재집계 필요 표시를 원자적으로 반영하며 원천·이전 결과는 보존한다.

MVP 본인 현황은 일·주·월 목록과 상태 표시 중심이다. 상세 화면·반응형 동작·입출력 계약은 [화면 설계](design/screens.md)를 따른다. 풍부한 캘린더와 시각화 대시보드는 후속 사용성 검증 후 검토한다.

### 기존 초기 제외 방향 유지

급여·급여세액 계산, 네이티브 모바일 앱, GPS 출퇴근, 생체인식·출입 장비 연동, 복잡한 교대근무 자동 편성, 외부 전자결재 연동, 고객사별 개별 코드 커스터마이징, 다국어 지원은 초기 제외 방향을 유지한다.

급여 연계용 근태 Excel 출력은 계산 기능과 구분하여 후속 후보로 남긴다. MSA·Kubernetes·React/Vue SPA는 기존 기술 범위에서 제외한 방향을 유지한다.

## 6. 핵심 사용자 시나리오와 수용 기준

아래 기준은 **설계 기준선에서 정한 제품 검증 목표**다. 목표 자체와 실행 성적은 구분하며, 이후 구체화한 상태·계산 규칙과 지원 MVP의 로컬 시나리오 검증은 연결 명세·위 최신 기록을 따른다. 실제 고객 수용 결과를 뜻하지 않는다.

### S01. 고객사와 직원의 최초 이용 준비

- 역할·연결 기능: 서비스 운영자, 근태 담당자, 직원 / F01~F04
- 흐름: 고객사·최초 담당자 연결 → 최소 조직·사원 등록 → 일정·승인자 지정 → 초대 수락·로그인.
- 수용 기준: 검증된 고객사 소속만 업무에 접근한다. 만료·재사용된 초대는 허용하지 않으며 초대 대상과 다른 소속으로 등록되지 않는다.
- 예외 기준: 일정·승인자 등 필수 설정이 빠지면 필요한 항목을 안내한다. 값을 추정해 정상 이용 준비가 끝났다고 표시하지 않는다.

### S02. 정상 출퇴근과 기록 확인

- 역할·연결 기능: 직원 / F05, F06
- 흐름: 로그인 → 허용 IP 기반 출퇴근 인증 → 출근 또는 퇴근 → 처리 결과 확인 → 퇴근 후 실제 근로·예정 휴게 일치 확인 또는 정정 → 본인 내역 조회.
- 수용 기준: 다른 고객사·직원으로 기록할 수 없다. 실제 시각과 근무일을 구분하고 `Asia/Seoul` 기준으로 표시한다.
- 예외 기준: 연속 클릭·통신 재시도·동시 요청으로 유효 기록이 중복 반영되지 않는다. 통신 실패 시 성공 여부를 확인할 경로를 제공하고 미저장 기록을 저장 완료로 표시하지 않는다. 서버 수신 시각을 채택하고 commandId로 같은 명령 재시도를 식별한다. 다른 내용의 같은 키는 충돌로 처리한다.

### S03. 퇴근 누락 또는 오입력 정정

- 역할·연결 기능: 직원, 승인자, 근태 담당자 / F08~F12
- 흐름: 본인 누락·오류 확인 → 정정 값·사유 제출 → 권한 있는 승인자 검토 → 결과·이력 확인.
- 수용 기준: 승인 전에는 유효 산정 입력이 바뀌지 않지만 대기 정정이 영향을 주는 일·주·월에는 확인 필요를 표시한다. 승인 후에는 원천 기록을 보존하고 승인된 정정과 결과의 연결을 확인할 수 있다.
- 예외 기준: 출근 없는 퇴근, 중복 정정, 이미 처리된 신청, 과거 기간 정정은 정책에 따라 안내·통제한다. 누락 시각을 임의 생성하지 않는다.

### S04. 종일 연차 신청과 잔여 확인

- 역할·연결 기능: 직원, 승인자, 근태 담당자 / F07, F09
- 흐름: 근거·기준일이 있는 잔여 조회 → 기간 선택·신청 → 승인·반려 → 상태·사용·잔여 내역 확인.
- 수용 기준: 신청 중·승인·취소 내역을 구분하고 대기량은 차감·예약 없이 별도로 표시한다. 승인 시 잔여를 재검증하고 한 번만 차감한다. 동시 승인으로 중복·초과 차감되지 않아야 한다.
- 예외 기준: 기초 잔여나 적용 정책이 미확인인 경우 확정 잔여량처럼 표시하지 않는다. 소정근로일만 신청하며 같은 기초 묶음의 유효기간 경계를 넘으면 신청을 나눈다. 중복·잔여 부족은 차단하고 취소 승인 시 원차감량만 복원한다.

### S05. 승인·반려와 철회·취소

- 역할·연결 기능: 직원, 승인자 / F09
- 흐름: 담당 신청 조회 → 권한·현재 상태 확인 → 승인 또는 반려 → 신청자 확인. 승인 전 작성자 철회와 승인 후 별도 취소 요청을 지원한다.
- 수용 기준: 1단계 지정 승인자가 처리하며 직원·승인자 겸임을 허용한다. 자기 신청 승인과 지정 범위 밖 처리는 차단한다. 동시 처리 시 한 번만 유효하게 반영하고 뒤늦은 처리자에게 현재 결과를 안내한다.
- 예외 기준: 취소가 승인되는 경우 잔여량·집계는 정책에 따라 한 번만 반영하며 이전 승인 이력을 보존한다. 부재·퇴사 시 담당자가 적격 승인자로 명시 재할당한다. 취소 심사 중 원승인은 유효하며 이미 시작·사용한 연차는 담당자 예외 신청과 독립 승인이 필요하다.

### S06. 본인 주·월 현황과 담당자 검토

- 역할·연결 기능: 직원, 승인자, 근태 담당자 / F06, F10, F11
- 흐름: 대상 기간·접근 가능한 사원 선택 → 일별 상세와 합계 확인 → 누락·승인 대기·정정 필요 내역 확인.
- 수용 기준: 상세와 합계가 일치하고 적용한 일정·정책·기준 버전을 추적할 수 있다. 승인자는 허용된 대상만, 직원은 본인만 조회한다.
- 예외 기준: 미처리·범위 밖 근무·검증되지 않은 산정 항목이 남으면 잠정 결과와 확인 필요 이유를 표시한다. 월별 조회를 월 마감 또는 급여 확정으로 표현하지 않는다.

### S07. 일정 밖 근무·자정 통과 기록

- 역할·연결 기능: 직원, 근태 담당자 / F05, F08, F10, F11
- 흐름: 일정 외 시각이나 자정 통과 기록 발생 → 원천 보존 → 확인 필요 표시 → 정정·업무 검토.
- 수용 기준: 기록 전체와 발생 시각을 보존한다. 승인 신청이 없다는 이유로 실제 기록을 삭제하거나 추가 근로를 자동으로 0으로 만들지 않는다.
- 예외 기준: 자정·월말·연말 경계에서 임의 분할·자동 퇴근·정상 확정 처리를 하지 않는다. 근무일 귀속과 연장·야간·휴일 분류·실근로 판정은 D02·D06의 검증된 규칙을 따른다.

### S08. 권한 변경·퇴사 후 접근 차단

- 역할·연결 기능: 근태 담당자, 직원 / F02, F03, F12
- 흐름: 재직·역할·담당 범위 변경 → 이후 요청의 권한 재평가 → 허용된 정보만 조회.
- 수용 기준: 직원이 자신의 권한을 올릴 수 없다. 비활성 계정·퇴사자의 접근과 기존 세션·초대·재설정 수단의 사용을 확정 정책에 따라 차단한다.
- 예외 기준: 접근 차단이 과거 근태·승인 이력의 삭제로 이어지지 않는다. 매 요청의 상태·권한 개정 검사로 기존 세션도 차단하며, 구체 정책은 보안 설계를 따른다.

### S09. 고객사 간 접근과 운영자 접근 통제

- 역할·연결 기능: 모든 역할 / F01~F13, N01, N02
- 흐름: 요청의 고객사·사원 식별자 변조 또는 다른 고객사 요청과 연결 자원 재사용 상황을 검증한다.
- 수용 기준: 화면·조회·신청·승인·집계·이력과 검토용 출력에서 다른 테넌트의 데이터에 접근하거나 영향을 줄 수 없다. 운영자에게 고객사 업무 데이터 접근이 자동 부여되지 않는다.
- 예외 기준: 테넌트가 확인되지 않거나 RLS 컨텍스트 설정에 실패하면 접근을 차단한다. 실패·종료 뒤 커넥션을 다른 테넌트가 재사용해도 이전 컨텍스트가 적용되지 않는다.

### S10. 과거 정책 변경과 기간 결과 재확인

- 역할·연결 기능: 근태 담당자 / F04, F07~F12
- 흐름: 일정·기준·승인 상태 변경 → 영향 기간 확인 → 과거 결과와 변경 근거 확인.
- 수용 기준: 과거 결과는 당시 입력·적용일·규칙 버전으로 설명할 수 있다. 기준 변경이 과거 기간 전체에 무분별하게 소급되지 않는다.
- 예외 기준: 과거 변경은 담당자의 근거 검토·독립 승인 후 영향 기간을 재집계하고 새 결과 버전을 추가한다. 이전 결과는 보존한다. C04 공식 월 마감·재마감은 후속이다.

## 7. 업무 상태와 계산의 제안 경계

### 신청 상태와 효력

```text
PENDING → APPROVED / REJECTED / WITHDRAWN
승인된 종일 연차 원신청 + 별도 취소 요청(PENDING)
취소 심사 중: 원승인 효력 유지
취소 승인: 원신청 효력 CANCELED + 원장 한 번 복원
```

상태·권한·동시성·실패 복구는 [신청·승인 규칙](rules/workflow.md)의 W01~W06·WF01~WF21을 따른다. 제출 후 본문은 변경하지 않고 철회·연결 재신청으로 처리한다. 승인된 출퇴근 정정은 취소하지 않고 최신 유효 버전을 참조한 새 정정으로만 변경한다. 임시저장·일괄 승인·자동 대결·공식 월 마감은 후속이다. 이 계약의 종일 연차·정정·철회·취소·재할당과 원장 원자성은 Phase 5~6에서 구현·로컬 회귀 검증했으며 [품질 보고서](quality/phase6-report.md)와 위 최신 실행 기록을 따른다.

### 계산에서 지켜야 할 구분

- 근무 스케줄, 실제 출퇴근, 확인된 휴게, 승인된 휴가·정정, 적용 정책을 각각 구분한다.
- 추가 근무의 신청·승인 시간과 실제 근로 판단을 분리한다. 신청 승인만으로 실근로가 확정되거나 미승인만으로 실제 근로가 사라지지 않게 한다.
- 기본안에서 자동 계산할 수 없는 항목은 확인 필요 상태와 근거를 표시한다. 단순 체류시간·예정시간을 검증된 법정 근로시간으로 표기하지 않는다.
- 결과에는 대상 기간, 적용 기준·버전, 미해결 항목과 산정 근거를 연결한다. 재계산은 불변 입력 스냅샷·규칙 버전·결과 새 버전으로 기록하며 이전 결과를 보존한다.
- 공식 근거와 C01~C34 계산 사례를 [계산 규칙](rules/calculation.md)에 기록했다. 일 8시간·주 40시간 초과 참고량과 야간·휴일 분류는 실제 근로에 따라 표시하되 법정 가산 대상 최종값은 MVP에서 자동 확정하지 않는다.

문서의 처리 원칙을 실행 가능한 테스트로 검증하기 전 실데이터 변경 기능을 완성된 운영 기능으로 제공하지 않는다.

### D02 결정: 고정 일정의 관리 수준

**선택 상태: 확정 — B안 여러 고정 템플릿 + 사원별 적용일 배정.** 결정일은 2026-10-23이며, 근거는 사용자의 명시적 선택이다. 정상 지원은 당일 시작·종료하는 하루 한 근무 구간이다. 아래 대안 비교는 검토 이력으로 유지하며 모든 직원의 요일·시각이 같다고 가정하지 않는다.

| 선택지 | 장점 | 단점·부담 |
| --- | --- | --- |
| A. 회사 내 단일 고정 일정 | 설정·배정·검증 범위가 가장 작음 | 사원별 일정 차이가 있는 고객의 수용 범위가 좁아지고 기존 사원별 일정 제안을 축소 |
| B. 여러 고정 템플릿 + 사원별 적용일 배정 | 일정 차이를 수용하면서 매일 편성하는 기능을 줄일 수 있음 | 배정 누락·기간 중복·변경 적용일·과거 일정 추적의 검증 필요 |
| C. 일별·복수 구간·자정 통과·교대까지 정상 지원 | 다양한 근무 패턴 수용 가능 | 편성·구간 중첩·휴가 연계·근무일 귀속과 회귀 검증 부담 증가 |

**선택 결과: B.** 고객사별 여러 고정 템플릿을 사원에게 적용일로 배정한다. 정상 지원은 당일 시작·종료하는 하루 한 근무 구간으로 한정한다. 시차출퇴근·유연근무·교대근무의 정상 지원까지 채택한 것은 아니며, 실제 요일·시각과 세부 계산 기준은 확정하지 않는다.

- 휴게 검토안: 예정 휴게를 등록하되 실제 차이를 확인·정정할 경로를 두는 방식을 우선 검토한다. 예정 휴게의 일괄 자동 공제나 휴게 시작·종료의 별도 기록 채택은 미정이다.
- 기록 보존 경계: 정상 산정 범위 밖의 복수 기록·일정 외 근무·자정 통과도 보존하고 확인 필요로 표시한다. 미지원 기록 삭제·임의 날짜 분할·자동 퇴근으로 처리하지 않는다.
- 선택 후에도 미정: 실제 요일·시각·시간 수, 신뢰할 기록 시각, 휴게 확인·공제, 배정 누락·중복, 소급 변경, 주·월 경계, 근무일 귀속·반올림. 법령·계산 항목은 D06과 함께 검증한다.
- 결정 근거: D02 결정 당시 사용자가 B안과 당일 시작·종료하는 하루 한 근무 구간의 정상 지원을 명시적으로 선택하고 세부 계산 기준·D03~D05 미정 유지와 구현 미착수를 요청했다. 이후 D03~D05는 아래 별도 결정으로 갱신했다.

### D03 결정: 출퇴근 인증 방식

**선택 상태: 확정 — A안 허용 IP 기반 출퇴근 인증 우선 지원.** 결정일은 2026-10-23이며, 근거는 사용자의 명시적 선택이다. QR은 후속 후보로 둔다. 아래 대안 비교는 검토 이력으로 유지하며, 세부 보안 정책은 확정하지 않는다.

| 선택지 | 장점 | 단점·부담 |
| --- | --- | --- |
| A. 허용 IP 우선 | 직원의 기록 흐름이 단순하고 QR 게시·갱신 운영이 필요 없음 | 허용 대역 변경·프록시 신뢰 경로 관리 필요. 셀룰러·재택 등 정상 이용이 막힐 수 있고 공유망·VPN의 한계 존재 |
| B. 회전 QR 우선 | 사업장 공용망에 의존하지 않는 흐름으로 셀룰러 이용을 검토할 수 있음 | QR 게시 기기·담당자와 스캔·만료·재사용 처리가 필요. 사진·실시간 공유와 대리 기록 가능성을 제거하지 못함 |
| C. 고객사별 선택 또는 병행 | 고객사별 환경 차이를 수용할 여지가 큼 | 두 방식의 설정·보안·예외·테스트 부담 증가. OR 방식과 AND 방식도 별도 정책 결정 필요 |

**선택 결과: A.** MVP에서 허용 IP 기반 출퇴근 인증을 우선 지원한다. QR과 고객사별 복수 방식 선택·병행은 이번 채택에 포함하지 않으며, 향후 필요성을 별도로 검토한다. IP 우선 지원이 파일럿의 공용망·접속 환경 적합성이나 세부 보안 구성이 검증됐다는 의미는 아니다.

- 파일럿 준비 검토: 직원의 PC·Wi-Fi·셀룰러 이용, 공용망과 관리 담당자, 재택·외근·다중 사업장의 필요 범위. 고정 근무 사업장이라는 사실만으로 안정적인 공용망이 있다고 가정하지 않는다.
- 공통 보안 조건: 로그인한 사용자·검증된 소속으로 기록 대상을 결정하고 중복 반영을 차단한다. IP·QR 어느 방식도 본인이나 실제 현장 존재를 보증한다고 표현하지 않는다.
- 세부 설계 경계: 클라이언트가 보낸 IP 헤더를 그대로 신뢰하지 않는다. 접속 IP를 판단할 신뢰 경로와 구체적인 프록시 설정은 후속 설계에서 검증한다.
- 유지되는 미정: 허용 대역·등록 및 변경 권한, 프록시 신뢰 정책, VPN·셀룰러·재택·다중 사업장 등 예외 정책, 재시도 식별, 인증 실패의 안내·정정과 감사 정보 범위. 구체 보안 구성은 Phase 3~4에서 공식 자료로 검증한다.
- QR 후속 검토: 게시 기기·운영 방식, 토큰 만료·회전 주기·사용 단위는 미정이다. 여러 직원의 공용 QR 정상 사용과 동일 사용자 재사용은 구분하되 아직 구현 정책으로 채택하지 않는다.
- 결정 근거: D03 결정 당시 사용자가 A안 우선 지원과 QR 후속 후보를 명시하고 세부 보안 정책·D04~D05 미정 유지와 구현 미착수를 요청했다. 이후 D04·D05는 아래 별도 결정으로 갱신했다.

### D04 결정: 승인 단계와 권한 범위

**선택 상태: 확정 — A안 1단계 지정 승인자.** 결정일은 2026-10-23이며, 근거는 사용자의 명시적 선택이다. 직원·승인자 겸임은 허용하되 자기 승인은 차단한다. 대체 승인·취소 등 세부 정책은 미정이며 아래 대안 비교는 검토 이력으로 유지한다.

| 선택지 | 장점 | 단점·부담 |
| --- | --- | --- |
| A. 1단계 지정 승인자 | 책임과 상태 흐름이 단순하고 핵심 신청 검증에 집중 가능 | 승인자 부재·퇴사·본인 신청을 처리할 다른 승인 경로 필요 |
| B. 고정 2단계 승인 | 팀의 확인과 담당자의 검토를 분리할 수 있음 | 처리 지연, 중간 반려·철회·승인자 변경의 상태 규칙 증가 |
| C. 고객사별 자유 승인선 | 다양한 조직의 순서·조건·대결 요구를 수용 가능 | 설정 화면·조직 변경·조건 분기·권한·회귀 검증 부담이 큼 |

**선택 결과: A.** 지정된 승인자가 1단계로 처리한다. 직원·승인자 역할의 겸임을 허용하되 자기 신청은 스스로 승인할 수 없다. 사원·조직별 승인 대상 범위와 다른 승인자를 지정하는 구체적인 방식은 아직 정하지 않았다. 근태 담당자의 설정 권한이 승인 권한을 자동 포함하지 않도록 하는 기존 경계는 유지한다.

- 대체 승인 미정: 부재·퇴사·자기 신청을 처리할 다른 고객사 내부 승인자의 지정 주체·조건·유효 기간·처리 범위는 아직 정하지 않았다. 정책 미정 상태에서 자동 대결·운영자 대리 승인을 임의로 허용하지 않으며 자기 승인은 차단한다.
- 취소 등 상태 정책 미정: 승인 전 철회와 승인 후 취소 요청을 구분하는 안은 검토 중이다. 허용 시점·권한·재신청·취소 심사 중 원래 승인 효력 등은 미정이며, 이력 보존과 중복 반영 방지는 기존 요구사항으로 유지한다.
- 선택 후에도 미정: 사원·조직별 대상 범위, 지정·대체 권한과 유효 기간, 권한 변경의 적용 시점, 부재·퇴사, 재신청, 취소 심사 중 원래 승인 효력, 과거·마감 기간 변경. 취소·정정·재집계는 D07과 함께 결정한다.
- 결정 근거: D04 결정 당시 사용자가 A안 1단계 지정 승인자, 직원·승인자 겸임 허용과 자기 승인 차단을 선택하고 대체 승인·취소 등 세부 정책과 D05 미정 유지·구현 미착수를 요청했다. 이후 D05는 아래 별도 결정으로 갱신했다.

### D05 결정: 휴가 단위·기초 잔여·반영 시점

**선택 상태: 확정 — A안 종일 연차 우선 + 근거·조정 이력이 있는 기초 잔여 등록 + 승인 시 차감.** 결정일은 2026-10-24이며 근거는 사용자의 명시적 선택이다. 반차·시간 단위 휴가·자동 발생은 후속 후보이며 세부 계산·취소 정책은 미정이다. 아래 대안 비교는 검토 이력으로 유지한다.

| 휴가 단위 선택지 | 장점 | 단점·부담 |
| --- | --- | --- |
| A. 종일 연차 우선 | 기간·차감 단위를 좁혀 신청 → 승인 → 잔여 확인을 검증 가능 | 반차가 필수인 파일럿에는 부족 |
| B. 종일 연차 + 반차 | 부분 휴가의 실제 사용 흐름까지 검증 가능 | 오전·오후 구간, 일정·휴게와 차감량의 관계 명세 필요 |
| C. 시간 단위 휴가까지 지원 | 더 다양한 부분 휴가에 대응 가능 | 최소 단위·반올림·구간 중복·환산·집계와 동시성 검증 부담 증가 |

**휴가 단위 선택: A.** 이번 MVP는 종일 연차를 우선 지원하고 반차·시간 단위 휴가는 후속 후보로 둔다. 반차를 고정된 시간 수로 임의 정의하지 않는다. 다른 법정 휴가의 필요성과 미지원 업무 처리 경계도 별도로 확인한다.

| 잔여 부여 방식 | 장점 | 단점·부담 |
| --- | --- | --- |
| 검증된 기초 잔여 등록 + 조정 이력 — 선택 | 자동 발생 규칙의 범위를 늘리지 않고 근거·기준일·등록자·사용·조정 이력을 검증 가능 | 고객사 담당자의 기초 자료 검증과 등록 업무 필요. 자동화가 없다는 이유로 법적 적정성 검증이 생략되지 않음 |
| 법정 발생·이월·소멸 자동화 | 반복 등록을 줄일 여지가 있음 | 적용 대상·기간·입퇴사·기준일·예외·개정과 회귀 사례를 먼저 공식 검증해야 함 |

| 신청량 반영 방식 | 장점 | 단점·부담 |
| --- | --- | --- |
| 승인 시 차감 — 선택 | 잔여 반영을 승인 시점에 집중할 수 있음 | 대기 신청끼리 잔여를 선점하지 않아 최종 승인 때 부족할 수 있음. 대기량 별도 표시와 승인 시 재검증·동시성 제어 필요 |
| 대기 신청량 예약 후 승인 시 사용 확정 | 이미 신청한 양을 반영한 가용량을 안내하고 초과 예약을 통제 가능 | 반려·철회 시 해제, 장기 대기, 승인자 부재, 취소·재처리의 상태 관리 부담 증가 |

**선택 결과: 종일 연차 + 근거·조정 이력이 있는 기초 잔여 등록 + 승인 시 차감.** 대기 신청은 차감·예약하지 않고 별도로 표시하며 대기 예약 대안은 이번 MVP에 채택하지 않는다. 승인 시 잔여를 재검증하고 동시 승인에서도 중복·초과 차감을 방지한다. 자동 발생은 후속 후보로 두고 기초 잔여의 법적 적정성 검증은 별도로 수행한다.

- 취소·변경 경계: 취소가 승인되는 경우 복원·집계 반영은 한 번만 수행하고 이력을 남긴다. 취소 요청만으로 즉시 잔여를 복원하거나 원래 승인 효력을 바꾸는 정책은 확정하지 않는다.
- 선택 후에도 미정: 기초 잔여의 구체적인 검증 방법, 차감량·중복·잔여 부족 처리, 휴일 포함·연도 경계·재직 변경, 취소 허용 시점·권한·복원량·심사 중 효력. 마감 이후 변경과 재집계는 D07과 함께 결정한다.
- 결정 근거: 사용자가 종일 연차 우선, 근거·조정 이력이 있는 기초 잔여 등록과 승인 시 차감을 선택했다. 반차·시간 단위 휴가·자동 발생은 후속 후보로 두고 세부 계산·취소 정책은 미정으로 유지한다. 문서 검증 후 이번 변경만 커밋하며 실제 구현은 시작하지 않는다.

## 11. 검증 계획과 성공 판단

### 제품 가설과 사용성 검증

고객 인터뷰와 파일럿으로 실제 기록·신청·승인·대조 흐름, 발생하는 예외, 반차·추가 근무·마감의 필요성을 확인한다. 공식 경쟁 자료는 시장 조사 문서에 출처·조회일과 함께 기록했다. 차별점·효율은 인터뷰와 실사용 전 가설로 남긴다.

| 제안 지표 | 측정 의미 | 현재 상태 |
| --- | --- | --- |
| 핵심 시나리오 수행 결과 | 초대·출퇴근·신청·승인·조회 흐름의 완료·실패와 원인 | 지원 MVP의 로컬 합성 시나리오 검증 완료. 실제 파일럿 대상·측정 미실시 |
| 누락·정정·승인 대기와 대조 부담 | 미해결 건, 처리 경과 시간, 반복 확인이 필요한 이유 | 기준선·측정 기간·목표 미정 |
| 집계 대조 결과 | 검증된 사례와 산정 결과의 차이, 근거 추적 가능 여부 | 지원 범위의 계산·상태 전이·원장·불변 출력은 로컬 회귀/종료 정합성 검증. 실제 고객 자료·법 적용 대조 미실시 |
| PC·모바일 핵심 사용성 | 상태 이해, 실패 후 복구, 본인·담당 범위 정보 확인 | 파일럿 대상·브라우저·평가 기준 미정 |

테넌트 간 접근 차단과 필수 계산·정합성 검증은 평균 성공률로 대체하지 않는 수용 조건이다. 검증하지 못한 항목은 통과로 간주하지 않는다.

현재 문서 산출물과 남은 실행 조건은 다음과 같다.

1. MVP·역할·핵심 시나리오, 공식 경쟁 조사·파일럿 검증 계획을 작성했다.
2. 신청·승인·계산 규칙과 입력·기대 결과 사례를 명세했다. 미검증 법령과 실제 데이터 처리 조건을 구분했다.
3. 아키텍처·논리 ERD·HTTP·화면·보안·기술 ADR을 작성했다.
4. 최초 설계 이후 별도 승인으로 Phase 4 개발 환경과 Phase 5 MVP를 구현하고 Phase 6 로컬 품질 검증을 진행했다. 2026-10-26 하루 흐름 홈의 Java467개·Python42개·HTTP62개·브라우저10개 관측은 당시 이력이다. 이후 React 전환·보안/부하 검증을 거쳐 현재 [권한 확장 1단계](quality/identity-access.md)의 Java515개·React113개·HTTP51개·브라우저9회와 V11/기존 DB 보존을 확인했다. 이미지별 부하·보안 검사를 구분하며 현재 기능 이미지의 새33분·전수 스캔은 수행하지 않았다.
5. 남은 조건은 신규 공급자 평가 대기·기존 P1과 Ryuk 관리자 소켓 등 잔여 보안 항목과 법적 예외·개인정보·실제 전달 채널·운영/복구·파일럿 수용이다. 실제 파일럿·상용 운영 완료로 간주하지 않는다.

최초 기획 위임은 문서까지였고 당시 Java·SQL·환경·DB·Docker 작업은 시작하지 않았다. 이후 승인된 구현·로컬 실행 이력은 위 최신 기록과 [AGENTS.md](../AGENTS.md)를 따른다. 로컬 데모·이미지 보안·Ryuk와 [하루 흐름 홈](quality/dayflow-home.md)은 당시 이력이며, 현재 후속 단위는 React [권한·메뉴·내 정보](quality/identity-access.md)다. 현재 단위에서 미실시한 새 부하·보안 전수 검증을 과거 이력으로 대신하지 않는다.

2026-10-24에는 공식 제품·법령·기술 자료를 실제 조회했다. 출처와 확인 범위는 각 상세 문서에 기록했다. 원문 확인·제품 정책 채택 당시에는 의존성 통합·DB·보안·성능 테스트를 수행하지 않았다. 이후 로컬 구현·실행 결과는 위 최신 기록과 [최종 이미지 재검증](quality/runtime-image-soak.md)을 따른다. 실제 고객에 대한 법률 적용·인터뷰·사용자 평가·운영 수용은 별도 미완료다.
