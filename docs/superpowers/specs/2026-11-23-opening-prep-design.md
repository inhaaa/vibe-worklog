## 배경

2026-11-23 판매·오픈 점검에서 고객사 오픈을 막는 문제 8건을 6개 묶음으로 나눴다. 이 문서는 첫 묶음(A 개통 준비)이다.

- **기존 재직자를 넣을 경로가 없다.** 화면의 신규 등록은 입사 예정 관리뿐이다. 그런데 입사일은 서울 기준 오늘 이후만 받는다(`EmployeeOnboardingService.validateDates`). 사원 시트의 행 추가는 `e4a317e`에서 빠졌다. 계정은 사원마다 이메일 초대를 보내야 한다.
- **근무일·휴일 입력이 개발자용이다.** 기간을 정하고 `날짜|종류|이름|근거` 텍스트를 줄마다 입력한다. 공휴일 목록은 없다. 한 번 등록한 기간은 바꿀 수 없다(`calendar_period_not_overlapping`, 수정·삭제 권한 없음). 그래서 나중에 지정된 임시공휴일을 넣을 방법이 없다.

## 목표와 성공 기준

1. 담당자는 기존 재직자를 엑셀에서 붙여넣어 한 번에 등록한다(최대 500명). 직원은 같은 날 사번으로 첫 로그인해 출근할 수 있다.
2. 재직자 등록과 입사 확정 모두 계정을 자동으로 만든다. 담당자는 초대 메일을 보내지 않는다.
3. 담당자는 그 해 공휴일을 한 번에 등록한다. 등록한 뒤에도 마감하지 않은 날짜는 달력에서 바꿀 수 있다. 바꾼 날짜는 재집계 대상이 된다.

## 1. 화면과 흐름

### 1.1 재직자 일괄 등록 — `/admin/employees/import`

- 메뉴는 인사관리 > 사원 > **재직자 일괄 등록**이다(담당자 전용).
- 머리글 없이 7개 열을 붙여넣는다: **사번 · 이름 · 입사일 · 생년월일 · 조직코드 · 직급 · 직책**.
  - 클립보드 텍스트는 탭·줄바꿈 기준으로 나누고, 엑셀의 따옴표 셀도 해석한다.
  - 붙여넣은 행은 공통 시트(`WorklogSheet`)에 들어가며 셀에서 바로 고칠 수 있다.
  - '양식 내려받기'는 머리글 한 줄짜리 UTF-8(BOM) CSV를 준다.
- **검증**: 행마다 '정상' 또는 오류 내용을 표시한다. 오류 셀은 강조한다.
- **저장**: 사유를 받는다. 한 행이라도 오류가 있으면 아무것도 저장하지 않는다.
  - 저장 결과에는 등록 인원과 계정 생성 수를 보여 준다.
  - 다음 단계 링크를 준다: 근무 설정 > 사원 배정, 연차 관리 > 사원별 일괄 입력, 사용자 관리.
- 공개 데모에서는 저장을 막는다(403). 기존 공유 데이터 보호 규칙과 같다.

### 1.2 계정 자동 생성과 최초 접속

- **계정이 생기는 시점**은 세 가지다.
  - 재직자 일괄 등록 저장
  - 입사 예정 확정(`/admin/employees/onboarding/{id}/confirm`)
  - 사용자 관리의 '계정 생성'
- **입사 예정 등록·수정**에 **생년월일(필수)** 칸을 추가한다. 입사를 확정할 때 이 값을 인사정보로 옮긴다. 이 칸이 없으면 신규 입사자가 최초 접속을 할 수 없다. 이미 생년월일 없이 등록된 예정 건은 확정 전에 수정해서 채운다.
- **최초 접속** `/first-login`(로그인 전 공개 화면)
  - 회사코드·사번·생년월일·새 비밀번호·확인을 받는다.
  - 로그인과 같은 재직 조건(입사일 이후, 마지막 재직일 이전)일 때만 성공한다.
  - 성공하면 로그인 화면으로 보내고 "새 비밀번호로 로그인하세요"를 표시한다. 자동으로 로그인하지 않는다.
- **로그인 화면에서 넘어오는 경우**: 로그인에 실패했고 입력한 비밀번호가 입력한 사번과 같으면 최초 접속 화면으로 보낸다.
  - 계정이 실제로 있는지와 관계없이 같은 규칙으로 동작한다.
  - 회사코드와 사번은 플래시 속성으로 넘겨 URL에 남기지 않는다.
  - 로컬·공개 데모 모드는 데모 계정의 로그인과 비밀번호가 같으므로 이 이동을 하지 않는다.
- **사원 상세 '계정·권한'**(`/admin/employees/{id}/access`): 초대 발급 UI를 없애고 계정 상태와 '비밀번호 초기화'를 보여 준다.
- **대기 계정 권한 미리 부여**: 최초 접속 전 계정에도 결재자 등 역할을 부여할 수 있다. 다만 결재선 해석과 자격은 자격 증명이 있는 활성 계정만 쓰므로 최초 접속을 마치기 전에는 결재에 배정되지 않는다.
- **로그인 화면의 메일 비밀번호 찾기**: 이메일이 있는 계정만 쓸 수 있다. 안내 문구에 "이메일이 없으면 담당자에게 초기화를 요청하세요"를 더한다.

### 1.3 사용자 관리 — `/admin/accounts`

- 메뉴는 시스템 설정 > 계정·공통코드 > **사용자 관리**다(담당자 전용).
- 목록 열은 사번·이름·현재 소속·계정 상태다. 사번·이름 검색과 상태 필터를 둔다.
- 선택한 사원에 두 가지 동작을 할 수 있다. 둘 다 사유가 필수이고, 한 번에 최대 100명이다.
  - **계정 생성**: 계정이 없는 재직자만 대상이다.
  - **비밀번호 초기화**: 계정이 있는 사원만 대상이다.

### 1.4 근무일·휴일 — `/admin/calendar`

- **월 달력**(이전/다음 달)을 보여 준다.
  - 날짜마다 종류와 이름을 표시한다.
  - 색은 세 가지다: 공휴일(내장 목록과 같은 날·같은 이름의 휴일), 회사 지정 휴일·비근무일, 미등록.
  - 주말 표시는 화면용이다. 실제 근무 요일은 근무조가 정한다.
- **'YYYY년 공휴일 불러오기'**: 먼저 차이 목록을 미리 보여 준다.
  - 차이 목록 항목: 새로 등록, 근무일 → 휴일, 이미 휴일, 마감 월이라 제외
  - 담당자가 '검토 확인'에 체크하고 사유를 적은 뒤 반영한다.
- **날짜 클릭**: 종류(휴일·근무일·비근무일), 이름, 사유를 받아 그 날짜를 바꾼다.
- **변경 이력**: 날짜, 바꾸기 전 → 후, 담당자, 시각, 사유를 보여 준다.
- 기존 '검토한 기간 등록' 폼(파이프 텍스트 입력)은 없앤다.
- 선택근무 정산에서 '달력 미등록 날짜'를 처리하러 들어온 경우(`settlementReturn`)는 지금처럼 처리 뒤 같은 사원·정산기간으로 돌아간다.

## 2. 데이터와 규칙

### 2.1 계정 — `V40__opening_preparation.sql`

`tna.tenant_account` 변경:

| 변경 | 내용 |
| --- | --- |
| `email` | `DROP NOT NULL`. 기존 `UNIQUE(tenant_id,email)`을 유지하므로 NULL은 여러 개 허용된다. |
| `activation_expires_at timestamptz` | 값이 있으면 최초 접속(또는 초기화) 대기 상태다. |
| `activation_failures smallint NOT NULL DEFAULT 0` | `CHECK (activation_failures BETWEEN 0 AND 5)` |

권한(최소 GRANT):

- `tna_app`: `INSERT(activation_expires_at)`, `UPDATE(activation_expires_at, activation_failures)`. 비밀번호 열은 지금처럼 읽지도 쓰지도 못한다.
- `tna_auth`: `UPDATE(activation_expires_at, activation_failures)`, `SELECT(birth_date) ON tna.employee_personnel`

`tna.employee_onboarding`에는 `birth_date date`를 추가한다. 기존 행 때문에 NULL을 허용하고, 필수 여부는 등록·수정·확정 명령에서 검사한다. `tna_app`에는 해당 열의 `INSERT`와 `UPDATE` 권한을 준다.

상태는 화면과 서비스가 같은 규칙으로 계산한다:

| 상태 | 조건 |
| --- | --- |
| 계정 없음 | 계정 행 없음 |
| 사용 중 | `activation_expires_at IS NULL AND active` |
| 생년월일 필요 | 대기 중이고 `employee_personnel.birth_date IS NULL` |
| 잠김 | 대기 중이고 `activation_failures = 5` |
| 기간 만료 | 대기 중이고 `activation_expires_at <= now()` |
| 최초 접속 대기 | 위에 해당하지 않는 대기 계정(만료 시각 표시) |
| 이전 초대 대기 | `activation_expires_at IS NULL AND NOT active`(기존 이메일 초대를 아직 수락하지 않음). 초기화하면 최초 접속 대기로 바뀐다. |

상태 전이:

| 동작 | DB 역할 | 처리 |
| --- | --- | --- |
| 생성 | `tna_app` | `active=false`, `password_hash=NULL`, `email=NULL`로 만든다. 만료 시각은 `max(현재, 입사일 00:00 서울) + 7일`이다. `role_grant EMPLOYEE`를 준다. 입사 확정·직원 등록·일괄 등록은 별도 계정 생성 감사 없이 그 명령 감사에 함께 기록한다. 계정이 없는 기존 사원은 계정·권한 화면의 '계정 만들기'(재직 중인 사원만, 초기화와 같은 경로)로 만들며 감사 `ACCOUNT_PROVISIONED`(전 `{account:false}` → 후 `{account:true,pending:true}`)를 남긴다. |
| 최초 접속 성공 | `tna_auth` | 재직 중이고, 대기 중이며 만료 전이고, 실패가 5회 미만이며, 생년월일이 일치해야 한다. 비밀번호를 저장하고 `active=true`, 대기 해제, 실패 0, `auth_version+1`로 바꾼다. 감사 `ACCOUNT_ACTIVATED`. |
| 최초 접속 실패 | `tna_auth` | 생년월일이 다르면 실패를 1 올린다. 감사 `ACCOUNT_ACTIVATION_FAILED`. 5회째는 감사 `ACCOUNT_LOCKED`. |
| 초기화 | `tna_app` | 만료 시각을 현재+7일로, 실패를 0으로 바꾸고 `auth_version+1`(기존 세션 무효)을 한다. 감사 `ACCOUNT_ACTIVATION_RESET`(이메일 재설정 `ACCOUNT_RESET_REQUEST/COMPLETE`와 구분). 본인 계정은 초기화할 수 없다(첫 담당자는 생년월일이 없어 영구 잠긴다). 공개 데모는 403. |
| 로그인 | `tna_auth` | 기존 조건에 `activation_expires_at IS NULL`을 더한다. 초기화한 계정은 이전 비밀번호로 로그인할 수 없다. |

- 새 비밀번호는 기존 `PasswordPolicy`를 따른다. 사번이나 생년월일(`YYMMDD`, `YYYYMMDD`)과 같으면 거부한다.
- 담당자용 초대 발급(`POST /admin/employees/{id}/invitations`, `AccountService.invite`)과 그 화면을 없앤다. 이미 발급한 초대 코드는 기존 `/invite` 수락 경로에서 만료 전까지 쓸 수 있다.

### 2.2 재직자 일괄 등록

하나의 명령(`OrgCommands.execute`, action `EMPLOYEE_IMPORT`)으로 다음을 순서대로 처리한다:

1. 고객사 잠금
2. 전체 행 재검증
3. 행마다 `employee` → `employee_personnel`(생년월일·직급·직책) → 소속 배정(적용일: 서울 기준 오늘) → 계정 생성
4. 감사 1건(행 수, 사번 목록)

같은 `commandId`로 다시 요청하면 처음 결과를 돌려준다. 새 테이블은 만들지 않는다.

| 열 | 규칙 |
| --- | --- |
| 사번 | 선택. 비우면 기존 `EmployeeNumbers.next(입사일, …)`로 발급하며, 한 배치 안에서도 이어서 발급한다. 1~40자이고 `@`는 쓸 수 없다. 회사 안이나 배치 안에서 겹치면 안 된다. |
| 이름 | 필수, 120자 이하(기존 규칙) |
| 입사일 | 필수, 서울 기준 오늘 이하. 미래 날짜면 입사 예정 관리로 안내한다. |
| 생년월일 | 필수. 1900-01-01 이후, 입사일 이전 |
| 조직코드 | 필수. 활성 조직의 코드여야 한다. |
| 직급·직책 | 선택, 각 120자 이하 |
| 행 수 | 1~500 |

- 날짜는 `YYYY-MM-DD`, `YYYY.MM.DD`, `YYYY/MM/DD`, `YYYYMMDD`를 받는다. 앞뒤 공백은 무시한다.
- 엑셀 일련번호(숫자만 있는 5자리)는 "날짜 형식으로 표시한 뒤 복사하세요"로 안내한다.

### 2.3 근무일·휴일 — 날짜별 개정

`V40`에서 함께 바꾼다:

- `calendar_version`에 `scope varchar(10) NOT NULL DEFAULT 'PERIOD' CHECK (scope IN ('PERIOD','DAY'))`를 추가한다.
- `calendar_period_not_overlapping`을 지우고 같은 제약을 `WHERE (scope='PERIOD')` 부분 제약으로 다시 만든다. 기간 등록끼리는 지금처럼 겹칠 수 없다.
- **DAY 버전**은 날짜 하나만 담는다(`valid_from=날짜`, `valid_to=날짜+1`, `calendar_day` 1행).
- **적용 규칙**: 한 날짜를 포함하는 버전 가운데 `revision`이 가장 큰 버전을 쓴다.
  - 이 규칙은 `security_invoker` 뷰 `tna.calendar_effective_day(tenant_id, work_date, version_id, kind, name, basis)`로 한곳에 정의한다. 이 뷰는 RLS를 호출자 권한으로 적용한다.
  - 지금 `calendar_day`를 직접 읽는 곳(`ClockMapper`, `MonthEndReviewMapper`, `AttendanceSettingsMapper`)은 이 뷰를 읽도록 바꾼다.
- **날짜 변경 조건**
  - 날짜가 이미 등록된 기간 안에 있어야 한다.
  - 그 달이 마감되지 않았어야 한다(`ClosedAttendanceMonths`).
  - 값이 지금과 달라야 한다.
  - 화면이 본 최신 `revision`(`expectedRevision`)과 같아야 한다. 다르면 409를 돌려준다.
- **'공휴일 불러오기'(연도 Y)**는 한 명령으로 처리한다.
  - 미등록 구간: `PERIOD` 버전을 만든다(기본 WORKDAY, 공휴일은 HOLIDAY).
  - 이미 등록됐지만 휴일이 아닌 공휴일: `DAY` 버전을 만든다.
  - 마감 월의 날짜: 제외하고 목록에 사유를 보여 준다.
- **재집계 표시는 따로 만들지 않는다.**
  - 일 결과와 근무 확인은 달력 버전을 입력 지문에 포함한다(`ClockService.sourceFingerprint`, `correctionConfirmation`).
  - 그래서 새 버전이 생기면 저장된 결과는 `STALE_RESULT`가 되고, 이전 근무 확인은 '확인 필요'가 된다.
  - 연장근무 신청의 `calendar_version_id` FK는 그대로 둔다.

## 3. 보안과 오류 처리

- **최초 접속 화면**
  - 기존 공개 인증 폼과 같은 보호를 적용한다: CSRF, 같은 IP의 과다 요청 차단(429).
  - 실패하면 이유와 관계없이 같은 문구를 보여 준다: "입력한 정보가 맞지 않거나 최초 접속 기간이 지났습니다. 담당자에게 문의하세요." 계정이 있는지, 어떤 상태인지 드러내지 않는다.
- **비밀값 기록 금지**: 비밀번호와 생년월일 원문은 명령 지문, 감사, 로그, 화면 모델에 넣지 않는다. 사용자 관리 목록에도 생년월일은 보여 주지 않는다.
- **새 기능 전체**는 모든 쿼리에 tenant 조건과 FORCE RLS를 적용하고 최소 GRANT만 준다. 공개 데모에서는 일괄 등록, 계정 생성·초기화, 달력 변경을 막는다(403).
- **일괄 등록 저장**은 미리보기 뒤의 경쟁도 다시 검증한다. 예를 들어 다른 담당자가 같은 사번을 먼저 등록했을 수 있다. 실패하면 전체를 취소하고, 422와 함께 행별 오류를 돌려준다.
- **달력 오류**
  - 마감 월: 기존 마감 보호 오류를 그대로 쓴다.
  - 동시 변경: 409와 "최신 내용을 확인한 뒤 다시 저장하세요."
  - 미등록 날짜를 바꾸려 할 때: "먼저 공휴일을 불러와 기간을 등록하세요."

## 5. 테스트와 검증

TDD로 진행한다. 단위마다 실패하는 테스트를 먼저 작성한다.

- **Java 단위**
  - 날짜 형식 해석, 일괄 등록 행 검증
  - 공휴일 목록이 공식 표와 날짜·이름 단위로 일치하는지
  - 최초 접속 규칙: 만료, 5회 잠금, 사번·생년월일과 같은 비밀번호 거부
  - 계정 상태 계산
- **PostgreSQL 통합(Testcontainers 전용 DB)**
  - 일괄 등록이 전부 저장되거나 전부 취소되는지, 같은 `commandId` 재시도
  - 다른 고객사 차단(RLS)
  - `tna_app`이 비밀번호 열을 바꿀 수 없는지
  - 초기화하면 이전 비밀번호 로그인과 기존 세션이 막히는지
  - 입사 확정 시 계정이 생성되는지
  - 같은 날짜에서 최신 개정이 적용되는지(근무 확인·월말 점검)
  - 마감 월 거부, `STALE_RESULT` 전환, `PERIOD` 겹침 거부
- **화면(Vitest)**: 붙여넣기 해석(CRLF·따옴표 셀·빈 열), 행별 오류 표시, 최초 접속 폼, 사용자 관리 선택 동작, 달력 표시와 날짜 수정
- **브라우저(PC·모바일)**
  - 일괄 등록 → 최초 접속 → 출근까지
  - 공휴일 불러오기 → 날짜 변경 → 재집계 표시
  - 초대 메일을 전제로 한 `CustomerOpeningBrowser`를 새 흐름에 맞게 고친다.
- **마지막 확인**: 전체 회귀(`mvnw verify`, `npm --prefix frontend test`, 빌드). 실행하지 못한 검증은 결과 문서에 '미실시'로 적는다.
