# 결재 알림 설계 (E 묶음)

작성일 2026-11-26 · 사용자 승인 설계 · 업무 시간대 `Asia/Seoul` · 기준 브랜치 `claude/opening-prep-20261123`

개통 점검에서 "알림이 없다"가 판매 차단 요인으로 나왔다. 지금은 결재자가 '결재 대기' 메뉴를 직접 열어 보지 않으면 신청이 들어온 줄 모르고, 신청자도 승인·반려 결과를 직접 찾아봐야 한다. [개통 점검 결과](2026-11-23-opening-prep-design.md) · [결재 흐름](../../rules/workflow.md) · [계정 메일 ADR](../../adr/0007-account-mail-delivery.md)

## 1. 사용자 결정

| 질문 | 결정 |
| --- | --- |
| 알림 방식 | 화면 알림과 메일을 함께 쓴다. 누구나 상단 종 아이콘에서 알림을 보고, 계정 이메일이 있으면 메일도 받는다. |
| 알림 상황 | 필수 4가지다. 아래 2절 표를 따른다. 회수는 알리지 않는다(결재 대기에서 사라지기만 한다). 중간 단계 승인은 신청자에게 알리지 않는다. |
| 메일 주소 | 로그인 계정의 이메일만 쓴다. 인사정보의 연락처 이메일은 쓰지 않는다. 계정 이메일이 없으면 화면 알림만 받는다. |
| 구현 방식 | 결재 처리와 같은 트랜잭션에서 알림 행을 저장하고, 1분 주기 작업이 메일을 보낸다. 결재가 롤백되면 알림도 없고, 메일 서버 장애가 결재를 막지 않으며, 재시작 후에도 미발송분을 이어 보낸다. |

## 2. 알림을 만드는 규칙

휴가·출퇴근 정정·휴가 취소·연장근무·연장 취소의 결재 이력은 모두 `LeaveWorkflowService`의 이력 기록 한 곳을 거친다. 이력을 쓸 때 같은 트랜잭션에서 아래 규칙으로 알림을 최대 1건 만든다.

| 결재 이력(`approval_event.event_kind`) | 받는 사람 | 알림 구분 |
| --- | --- | --- |
| `SUBMITTED` (제출) | 새 현재 결재자(`new_approver_id`) | 결재 요청 |
| `STEP_APPROVED` (다음 단계로 넘어감) | 다음 단계 결재자(`new_approver_id`) | 결재 요청 |
| `APPROVED` (최종 승인) | 신청 대상 사원(`target_employee_id`) | 승인 |
| `REJECTED` (반려) | 신청 대상 사원 | 반려 |
| `REASSIGNED` (결재자 변경) | 새 결재자(`new_approver_id`) | 결재 요청 |
| `WITHDRAWN` 등 그 밖 | 없음 | — |

- 받는 사람이 그 이력을 남긴 본인(같은 사원)이면 알림을 만들지 않는다. 예: 담당자가 자기 신청을 대리로 처리한 경우.
- 알림은 이력 1건당 최대 1건이다(`(tenant_id, event_id)` 고유).
- 알림 본문은 저장하지 않는다. 화면과 메일은 이력·신청을 조인해 그때 만든다. 반려 사유는 이력의 사유를 쓴다.

## 3. 저장

V43 마이그레이션에서 `tna.notification`을 만든다.

| 열 | 뜻 |
| --- | --- |
| `tenant_id`, `id` | 기본키 |
| `recipient_employee_id` | 받는 사원 (`employee` FK) |
| `event_id` | 원인 결재 이력 (`approval_event` FK, 회사 안에서 고유) |
| `request_id` | 신청 (`approval_request` FK, 상세 링크·읽음 처리용) |
| `kind` | `APPROVAL_REQUESTED` · `APPROVED` · `REJECTED` |
| `created_at` | 생성 시각 |
| `read_at` | 읽은 시각, 안 읽었으면 NULL |
| `mail_state` | `PENDING` · `SENT` · `SKIPPED` · `FAILED` |
| `mail_attempts` | 발송 시도 횟수 (0~3) |
| `mail_next_at` | 다음 발송 시도 시각 (PENDING일 때만) |

- FORCE RLS로 회사를 격리한다. `tna_app`에는 SELECT, INSERT와 `read_at`·`mail_state`·`mail_attempts`·`mail_next_at`의 UPDATE만 준다. DELETE는 주지 않는다.
- 인덱스: 받는 사람의 안 읽은 알림 건수와 최근 목록, 회사별 발송 대기 조회.

## 4. 화면

- **상단 종 아이콘**: 상단 바의 프로필 옆에 둔다. 안 읽은 건수를 배지로 보여 준다(100건 이상은 `99+`). 건수는 모든 업무 화면의 공통 데이터(`WorkspaceWebConfiguration`)에 싣는다. 누르면 알림 화면으로 간다.
- **알림 화면** `/me/notifications` (메뉴: 내 업무 아래 '알림')
  - 최근 100건을 밀도 있는 목록으로 보여 준다: 구분(결재 요청/승인/반려 태그) · 신청자 · 신청 내용(종류와 기간) · 시각(서울) · 읽음 여부.
  - 행을 누르면 결재 상세 `/requests/{id}`로 간다.
  - '모두 읽음' 버튼은 받는 사람의 안 읽은 알림을 모두 읽음으로 바꾼다(POST, CSRF).
- **자동 읽음**: 받는 사람이 결재 상세를 열면 그 신청에 대한 본인 알림을 읽음으로 바꾼다. 알림 화면에서 들어왔든 메일 링크로 들어왔든 같다.
- 다른 사람의 알림은 보이지도 바꿀 수도 없다. 모든 조회·변경은 로그인한 사원의 `employee_id`로 거른다.

## 5. 메일

- **발송 작업**: 1분마다 실행한다. 서버가 여러 대여도 세션 잠금(`pg_try_advisory_lock`)으로 한 대만 보낸다. 회사 목록은 B 묶음 새벽 작업처럼 인증 연결로 읽고, 회사별로 발송 대기 알림을 최대 100건씩 처리한다.
- **받는 주소**: 받는 사원의 활성 계정 이메일. 계정이 없거나, 비활성이거나, 이메일이 없으면 `SKIPPED`로 바꾼다.
- **재시도**: 실패하면 시도 횟수를 늘리고 1분·5분 뒤에 다시 시도한다. 3번 실패하면 `FAILED`로 남긴다. 화면 알림은 메일 결과와 무관하게 남는다.
- **내용**
  - 제목: `[WorkLog] 결재 요청 · 홍길동 연차 12-01~12-02` / `[WorkLog] 승인 · 연차 12-01~12-02` / `[WorkLog] 반려 · 연차 12-01~12-02`
  - 본문: 회사명, 신청자, 신청 종류, 기간, 반려 사유(반려만), 결재 상세 링크(`tna.mail.public-origin` + `/requests/{id}`). 결재 단계는 메일을 보낼 때 이미 바뀌었을 수 있어 넣지 않는다.
  - 비밀번호·생년월일·주소 같은 인사 개인정보는 넣지 않는다.
- **전달 방식**: 계정 메일과 같은 설정을 따른다.
  - `tna.mail.mode=smtp`: 기존 SMTP 설정(`JavaMailSender`, `tna.mail.from`, `tna.mail.public-origin`)으로 보낸다.
  - `local` 프로필이고 전달 방식이 없으면: 메모리 메일함에 쌓는다(최근 256건). 로컬 확인용이다. 링크 주소는 `tna.mail.public-origin`이 없으면 `http://127.0.0.1:18080`을 쓴다.
  - `public-demo`이거나 전달 방식이 없으면: 메일을 보내지 않고 `SKIPPED`로 바꾼다.
- **로그**: 이벤트 종류와 결과만 남긴다. 메일 주소·본문·사유는 남기지 않는다.
- **설정**: `tna.notification-mail.enabled`(기본 true). 테스트 설정과 브라우저 실행에서는 끄고, 시험은 발송 메서드를 직접 부른다.

## 6. 오류와 경계

- 알림 생성은 결재 트랜잭션 안에서 일어나므로, 알림 저장이 실패하면 결재도 실패한다. 제약 위반이 나지 않도록 규칙에서 받는 사람을 확실히 정한다.
- 같은 이력을 다시 처리해도 알림이 늘지 않는다(고유 제약).
- 발송 작업 중 한 회사가 실패해도 다음 회사를 계속 처리한다.
- 메일 발송은 트랜잭션 밖에서 하고, 결과 반영은 짧은 트랜잭션으로 한다. 발송 직후 서버가 죽으면 같은 메일이 한 번 더 갈 수 있다(최소 1회 전달).
- 퇴사·비활성 계정에는 메일을 보내지 않는다.

## 7. 검증 기준

- 통합 테스트
  - 제출·다음 단계·최종 승인·반려·결재자 변경의 알림 생성과 받는 사람, 회수 시 알림 없음, 본인 처리 시 알림 없음
  - 회사 격리(RLS), 다른 사원의 알림 조회·읽음 처리 차단
  - 결재 상세를 열면 읽음, '모두 읽음', 종 아이콘 건수
  - 메일 발송: 성공, 이메일 없음 건너뜀, 실패 재시도와 3회 후 실패, 동시 실행 시 한 번만 발송, 메일 본문에 개인정보가 없음
  - V43 스키마: RLS·좁은 권한·검사 조건(새 테이블만 추가하므로 별도 업그레이드 시험은 두지 않는다)
- React 테스트: 종 아이콘 배지, 알림 화면 목록·모두 읽음
- 브라우저 확인(로컬 데모): 직원이 신청 → 결재자 종 건수 증가 → 알림 화면에서 상세로 이동해 승인 → 신청자 종 건수와 알림, 발송 작업 뒤 알림의 메일 상태가 `SENT`인지(DB 확인), 모바일 화면. 메일 본문은 통합 테스트가 메모리 메일함으로 확인한다.

## 8. 범위 밖

- 오래 처리되지 않은 결재의 독촉 메일
- 사용자별 알림 끄기 설정
- 카카오톡·문자·푸시 알림
- 실제 메일 서버 발송 확인(현재 단계는 로컬 메일함으로만 확인한다)
- 알림 보관 기간과 삭제
