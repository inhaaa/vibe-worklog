## 범위와 구조

담당자가 인사기본에서 확정된 사원을 조회·편집하고, 입사 예정자를 등록한 뒤 최초 소속과 고정 근무를 정해 입사를 확정할 수 있게 한다. 이미 채용이 결정된 사람부터 처리한다. 지원자·전형 관리, 지원서·첨부, 외부 ATS 연동, 조직코드 자동 발급, 역할 구성원 일괄 편집, 운영 메일, 급여·연차 자동 부여는 후속 범위다.

기존 `/admin/employees` 메뉴를 **인사기본**으로 표시하고 조직·사원 시트의 편집·조회·저장 계약을 재사용한다. 새 입사 흐름은 입사 예정 레코드로 시작한다. 사원 행을 먼저 만드는 안은 현재 재직 판정이 입사일과 활성 상태를 기준으로 하므로, 미확정 예정자가 입사일에 도달했을 때 다른 기능에 노출될 수 있다. 기존 `/admin/employees` 단건 등록과 일괄 `CREATE` 계약은 호환을 위해 유지하고, 새 인사기본 화면의 신규 등록은 입사 예정 흐름으로 연결한다. 기존 사원에게 최초 발령을 추정해 일괄 채우지 않는다. [조직·사원 시트 설계](../../design/org-management.md) · [고정 근무 배정 설계](../../design/fixed-schedule.md)

## 인사기본 시트

담당자는 `인사관리 > 인사기본`에서 시트와 입사 예정 관리를 연다. [역할별 메뉴 배치](2026-11-17-attendance-history-navigation-design.md)

1. **조회**에서 이름·사번, 현재 소속, 활성 상태와 페이지를 선택한다. 목록은 서울 기준 조회일을 표시하고 서버 페이지당 최대 50행을 유지한다. 현재 소속·근무는 조회일 유효 배정으로 계산하며 누락은 `미배정`으로 표시한다. 확정된 미래 입사는 입사 예정 **상태**로 보이며, 최초 소속·근무는 발령 상세에서 확인한다. 아직 확정하지 않은 예정자는 사원 시트에 포함되지 않으며 `입사 예정 관리`에서 조회한다.
2. 시트에 아래 업무 열을 표시한다. 기존 사원의 입사일은 현행 수정 규칙을 유지한다. 이 흐름에서 확정된 사원의 입사일은 최초 소속·근무 적용일과 결속되므로 시트와 기존 단건 수정에서도 변경을 차단한다. 현재 상태와 상세 인사 열은 허용 필드만 관리자 목록에 투영한다. 공통 헤더나 회사 조회에 새 열을 추가하지 않는다.
3. **저장**은 변경한 1~50행과 공통 사유를 보내 시트 배치 한 건으로 처리한다. 저장 전에 변경 건수와 비활성 예정 대상을 확인할 수 있다. 낡은 버전·권한 변경·유효성 오류 시 배치 전체가 실패하고 편집값이 남는다. 편집 대상이 현재 필터에서 사라진 경우도 최신 행을 비교한 뒤 새 명령으로 다시 제출할 수 있다. 응답 유실처럼 결과를 확정할 수 없는 경우 동일 입력은 기존 명령 ID를 유지한다.
4. **비활성화**는 확정된 사원의 이력과 사번을 보존하고, 저장 시 기존 재직·권한 규칙으로 처리한다. 마지막 재직일은 재직 기간의 사실이며 비활성화는 즉시 접근 및 업무 자격을 중지하는 조치다. 마지막 관리자를 없애는 최종 배치는 거부하고, 재직일·활성 변경 시 연결된 세션을 회수한다. 등록 전 임시 입력은 취소로 화면에서 버릴 수 있고, 저장된 입사 예정은 별도 철회 명령으로 이력을 남긴다.

| 시트 열 | 편집 및 연결 |
| --- | --- |
| 사번, 이름, 입사일, 마지막 재직일, 활성 여부 | 사번은 읽기 전용. 나머지는 행 편집을 제공하며 이 흐름에서 확정한 입사일은 고정한다. |
| 재직 표시 상태, 직급·직책·직무 | 기존 인사정보의 현재 표시를 읽기 전용으로 제공한다. 값이 없으면 `미등록`을 표시한다. **인사정보** 링크로 기존 사원별 편집 화면에 연결한다. |
| 현재 소속, 현재 근무, 최초 발령 | 소속·근무는 각각 기존 적용일 배정 화면으로 연결한다. 최초 발령은 이 흐름에서 확정한 사원만 상세로 연결한다. |

시트 저장은 `employee.version`만 변경 대상으로 사용한다. 인사 상태와 직급·직책·직무의 저장은 기존 단건 인사 화면의 별도 버전 계약을 유지한다. [인사정보·버전 설계](../../design/personnel-workspace.md)

### 인사기본 Excel

다운로드 화면에서 `선택한 사원` 또는 `현재 조회 조건의 전체 사원`을 선택한다. 선택은 현재 페이지에서 체크한 행을 사용한다. 전체 다운로드는 명시적 확인을 거쳐 서버 조회 결과를 사용하며 현재 페이지로 잘라내지 않는다. 미확정·철회 예정자는 제외하고 서버에 커밋된 값만 사용한다. 시트에 미저장 변경이 있으면 화면에서 다운로드를 차단하고 먼저 저장 또는 취소하도록 안내한다. 상한은 설계안으로 1,000행이며 초과 시 필터를 좁히도록 안내한다. `.xlsx` 파일에 조회 기준일과 다음 고정 열을 넣는다.

| 내보내기 열 | 값 |
| --- | --- |
| 사번, 이름 | 사번은 앞자리 0을 보존하는 문자열 |
| 현재 소속 코드·이름, 현재 근무 템플릿 이름 | 조회 기준일의 유효 배정. 없는 값은 공란 |
| 입사일, 마지막 재직일, 활성 여부 | 날짜는 `YYYY-MM-DD`, 미지정 종료일은 공란 |
| 직급, 직책, 직무 | 시트에 표시되는 현재 업무용 명칭. 미등록 값은 공란 |

이름·조직명 등 입력 문자열은 문자열 셀로 작성하고 수식·링크로 변환하지 않는다. 생년월일·연락처·주소·사진·가족·장애·보훈 등 상세 인사정보와 계정·권한·감사 사유는 열에 포함하지 않는다. 파일은 요청별로 생성하고 DB 및 공개 경로에 저장하지 않는다. 응답은 XLSX MIME 타입과 `Content-Disposition: attachment`, `Cache-Control: no-store`를 사용한다. 다운로드는 목록 조회와 분리된 관리자 명령이다. 기존 검토용 Excel과 같이 시작부터 독점 변경 잠금을 획득해 조회·파일 생성·권한 재검증·감사를 처리하고, 감사 커밋 이후에 응답 바이트를 반환한다. 공유 읽기 잠금을 쓰기 잠금으로 승격하지 않는다. 성공한 다운로드 감사에는 주체·시각·범위 종류·행 수를 남기고 검색어, 셀 값 및 파일은 기록하지 않는다.

## 입사 예정에서 최초 발령까지

| 상태 | 가능한 행동과 결과 |
| --- | --- |
| `PLANNED` | 담당자가 이름·회사 입사 예정일을 등록한다. 활성 조직과 고정 근무 버전을 미리 선택하거나 확정 직전 지정한다. 이름·날짜·선택값을 수정하거나 사유와 함께 철회할 수 있다. 사원번호·사원·계정 또는 실제 배정은 아직 생성하지 않는다. |
| `CONFIRMED` | 담당자가 사번과 최초 소속·근무를 검토하고 입사를 확정한 상태다. 사원·최초 배정 두 건·확정된 발령 참조·감사가 한 트랜잭션에서 생성된다. 업무 시작일은 회사 입사일이며, 미래일이면 기존 인증·업무 판정이 해당 날짜까지 접근을 막는다. |
| `WITHDRAWN` | 확정 전 예정 기록을 철회한 상태다. 사유·처리자·시각과 남아 있는 예정 이력을 조회할 수 있다. 복구 및 상태 재개가 필요한 경우 새 예정 기록으로 시작한다. |

1. **예정 등록**에는 한글성명 또는 업무상 표시 이름 1~120자와 서울 기준 오늘 이후의 입사일이 필요하다. 마지막 재직일을 이미 확정한 경우 같은 날 이후의 종료일을 선택 입력한다. 같은 이름·입사일의 예정자나 사원이 있으면 중복 가능성을 경고하고 선택한 사람을 확인시킨다. 동명이인 때문에 이름과 날짜 조합에 유일성 제약을 두지 않는다.
2. **확정 검토**에 회사 입사일, 사번 직접 지정 또는 자동 발급 여부, 조직, 템플릿·정확한 버전·사용 시작일을 표시한다. 실행 시 예정 레코드 버전과 화면에서 검토한 조직·템플릿 버전을 다시 검사한다. 삭제되었거나 비활성인 조직·템플릿, 시작일이 입사일보다 늦은 버전, 고객사 외 ID는 거부한다. 충돌 시 새 검토 내용으로 사용자가 다시 확정한다. 사유는 1~500자다.
3. **입사 확정**에서 사번을 비웠으면 기존 `YY + 001~999` 발급기를 고객사 변경 잠금 안에서 사용한다. 퇴사자·비활성 사원을 포함한 기존 발급 번호는 재사용하지 않는다. `99999`는 이 흐름에서 수동·자동 신규 지정 모두 거부한다. 수동 입력은 기존 형식·길이·회사 내 유일성을 따른다. 확정 전에는 정확한 자동 발급 번호를 예약하거나 보장하지 않는다. 사번은 확정 이후 불변이다.
4. **최초 발령**의 효력일은 회사 입사일이다. 새 `employee`는 활성으로 저장하고, 동일한 날부터 `employee_assignment`와 `schedule_assignment`의 최초 구간을 생성한다. 기존 구간 규칙 `[시작, 종료)`와 열린 구간 생성 방식을 재사용한다. 직원의 마지막 재직일은 포함이며 그 이후 현재 재직·근태·초대에서 효력이 없다. 기존 계산 경로가 재직 조건과 배정을 함께 보도록 하고, 발령 자체로 출퇴근·계산·잔여 연차를 만들어 내지 않는다.
5. **확정 이후** 최초 발령 상세에 `입사`, 효력일, 사번, 확정 당시 조직 코드·이름 및 근무 템플릿 이름·버전, 처리자를 보여 준다. 현재 조직·근무는 이후 별도 적용일 배정으로 바꿀 수 있다. 입사 예정일이 지나도록 미확정이면 `예정일 경과`로 표시한다. 담당자가 오늘 이후로 날짜를 정정해야 확정할 수 있으며 소급 발령은 후속 범위다. 확정 후 철회·입사일 정정·재입사도 별도 이력 전이로 다룰 후속 범위다. 확정된 미래 입사가 취소되면 현행 사원 비활성화로 접근과 재직 업무를 중지할 수 있다. 사번·최초 배정과 감사는 보존되며, 기존 미래 소속이 조직 비활성화를 막을 수 있음을 운영 화면에서 안내한다.
6. **계정 초대**는 확정 결과의 별도 작업이다. 미래 입사자는 확정 결과에 `입사일부터 초대 가능`으로 표시하고 입사일 전에는 초대 동작을 제공하지 않는다. 이후 현재 재직 중인 활성 사원만 기존 단건 계정 초대 화면으로 연결한다. 계정·역할·승인자 배정은 최초 발령에서 자동 생성하지 않는다. 실제 메일 발송은 상용 전달 채널의 별도 계약을 따른다. [계정·역할 설계](../../design/account-access.md)
7. **직원 첫날**에는 초대를 수락하고 내 정보에서 본인 사번·최초 소속과 입사 발령을 확인한다. 발령내역의 기존 소속 행에 최초 발령 유형을 표시하되 본인에게 처리자·사유를 새로 노출하지 않는다. 적용 근무는 홈과 근무 일정에서 확인하고, 회사의 기존 허용 네트워크 및 출퇴근 조건을 충족한 뒤 출근한다. 별도 최초 로그인·출근 예외를 추가하지 않는다.

## 데이터와 트랜잭션

신규 `employee_onboarding`은 `tenant_id`와 UUID `id`를 복합 PK로 사용한다. 기존 사원·조직·근무 버전·배정·감사 테이블을 원본으로 사용한다. 아래 필드명은 제안 계약이다. 스키마 번호는 구현 시 메인 마이그레이션 최신 번호를 확인해 다음 번호를 배정한다.

| 데이터 | 필드·제약 |
| --- | --- |
| 예정 | `display_name`, `joined_on`, `left_on?`, `organization_id?`, `schedule_version_id?`, `state`, `version`, 생성·수정 주체와 시각. `left_on`은 `joined_on` 이상. 예정 상태에서는 희망 조직·근무 버전이 비어 있을 수 있다. |
| 확정 및 발령 | `employee_id`, `organization_assignment_id`, `schedule_assignment_id`, `decided_by`, `decided_at`, 확정 당시 조직 코드·이름과 근무 템플릿 이름·개정 번호. `CONFIRMED`에서는 세 업무 참조와 조직·근무 버전·확정 표시값이 필수이다. 동일 고객사의 사원·배정 각각 한 건과 연결하고, 사원의 최초 두 배정 및 효력일 일치는 같은 트랜잭션에서 검증한다. 사원별 한 건만 연결하도록 부분 유일 제약을 둔다. 신규 발령은 이 연결을 읽고, 기존 사원은 현재의 소속 이력만 읽는다. |
| 철회 | `decided_by`, `decided_at` 필수, 확정 업무 참조와 확정 표시값은 공란. 사유는 공통 감사 이벤트로 조회한다. `PLANNED`는 결정 주체·시각과 확정 필드를 비워 둔다. `CONFIRMED`와 `WITHDRAWN`은 종료 상태이며 필드를 후속 명령으로 덮어쓰지 않는다. |

조직·일정·사원·처리자 관계에 테넌트 복합 FK를 사용하고 모든 SQL에 `tenant_id`를 명시한다. `FORCE RLS`와 제한된 애플리케이션 열 권한을 적용한다. 인증 전용·일반 운영자 DB 역할에는 신규 예정 레코드의 읽기·쓰기 권한을 부여하지 않는다. 예정·철회 이름은 일반 감사 페이로드에 복제하지 않으며, 버전·상태 및 업무 참조를 남긴다.

변경 명령은 고객사 독점 잠금 → 현재 관리자의 재직·세션·권한 확인 → 동일 명령 재실행 판정 → 대상·입력 버전·업무 규칙 검증 → 업무와 감사 기록 → 커밋 순서다. 확정은 `OrgCommands` 한 번과 하나의 업무 감사 이벤트를 사용한다. 기존 사번 및 조직·근무 배정 검증을 재사용하고 독립 단건 명령을 중첩 호출하지 않는다. 최초 근무 또는 감사가 실패하면 사번을 포함해 모든 변경을 롤백한다. 같은 주체·명령 ID·정규화 입력의 재시도는 이전에 확정된 사원·배정 참조를 반환한다. 같은 ID의 다른 입력 또는 다른 명령 ID로 확정된 예정자를 재확정하면 `409`로 응답한다.

## HTTP·권한·오류 계약

조회·저장·다운로드는 현재 재직 중인 같은 회사 `ATTENDANCE_ADMIN`에게만 허용한다. 조회는 공유 읽기 흐름에서 진입과 반환 전 권한을 확인한다. `tenant_id`·`employee_id`는 본인·담당자 경계를 서버가 확인하고, 전송된 회사 값으로 테넌트를 변경할 수 없다. 공개 `public-demo`에서는 신규 예정 변경과 인사 Excel을 숨기고 직접 요청도 거부한다. 기존 사원 단건·일괄 변경의 공유 5인 보호와 상세 인사 가드를 유지한다. 지원되는 로컬 일반·격리 환경에서 신규 명령을 검증한다.

| 경로 | 요청과 결과 |
| --- | --- |
| `GET /admin/employees` | `q`, `organizationId`, `status`, `page`로 사원 시트를 제공한다. 기존 `employeeId`는 상세 선택과 등록·편집 후 돌아갈 조회 문맥으로 유지한다. 입사 예정 관리 링크에서 예정일이 지난 미확정 건도 볼 수 있다. |
| `POST /admin/employees/bulk` | 기존 `commandId`, `reason`, `rows` 계약을 유지한다. 시트 편집은 기존 `UPDATE/DEACTIVATE`를 사용한다. `CREATE`는 기존 호출과 호환한다. |
| `POST /admin/employees/exports` | CSRF와 `scope=SELECTED/FILTERED`를 받는다. `SELECTED`는 확인한 사원 ID 목록, `FILTERED`는 `q`, `organizationId`, `status`를 받으며 서로 배타적이다. `employeeId` 선택 문맥과 `page`는 필터 범위에 영향을 주지 않는다. 선택 ID에 타사·사라진 사원이 섞이면 전체 요청을 `404`로 거부한다. 상한 초과는 `422`다. 성공 시 `200`과 XLSX를 반환하고, 파일 생성마다 별도 접근 감사를 남긴다. |
| `GET /admin/employees/onboarding` 및 `GET /admin/employees/onboarding/{id}` | 예정·확정·철회 목록과 상세를 제공한다. 상태·이름·입사일 범위로 검색하고 최대 50행씩 조회한다. 상세에 최초 발령과 실제 사원 관리 링크를 포함한다. 이 정적 경로를 기존 UUID 사원 상세보다 먼저 매칭한다. |
| `POST /admin/employees/onboarding` | 예정값으로 등록한다. `displayName`, `joinedOn`, `leftOn?`, `organizationId?`, `scheduleVersionId?`, `commandId`, `reason`을 받는다. |
| `POST /admin/employees/onboarding/{id}/changes` | 예정값 전체와 `expectedVersion`, `commandId`, `reason`을 받아 `PLANNED`를 수정한다. |
| `POST /admin/employees/onboarding/{id}/confirm` | `expectedVersion`, `organizationId`, `expectedOrganizationVersion`, `scheduleVersionId`, `expectedTemplateVersion`, `employeeNo?`, `commandId`, `reason`으로 확정한다. 이름과 날짜는 버전 검증한 예정값을 사용한다. |
| `POST /admin/employees/onboarding/{id}/withdraw` | `expectedVersion`, `commandId`, `reason`으로 `PLANNED`를 철회한다. |

POST에 CSRF를 적용하고 낯선 필드·잘못된 형식은 `400`, 자격 부족은 `403`, 다른 회사나 없는 대상으로부터의 조회·수정은 `404`, 낡은 버전·사번 중복·상태 경쟁은 `409`, 날짜·필수값·업무 규칙 실패는 `422`로 처리한다. 정상 변경은 `303`으로 해당 상세 또는 조회 문맥으로 이동한다. `409/422`에서 제출값과 서버 최신값을 구분해 보여 준다. 결과가 불명확한 `503`에서 같은 입력은 같은 명령 키를 사용한다. 사용자가 내용을 수정하거나 최신 내용을 확인해 재제출하면 새 키를 부여한다.

## 수용 검증

| 시나리오 | 기대 결과 |
| --- | --- |
| 2명 편집과 1명 비활성화, 마지막 행에서 충돌 | 같은 배치의 이름·재직·세션·감사 변경 전체가 롤백된다. 입력, 오류 행, 최신값이 남는다. 편집 중 취소는 서버를 바꾸지 않는다. |
| 동시 확정과 응답 유실 | 같은 명령 재실행은 최초 결과를 반환한다. 다른 명령은 한 건만 성공한다. 사원·자동 사번·최초 소속·최초 근무·감사는 한 건씩만 남는다. 별개의 예정 두 건 동시 확정은 고객사 안에서 다른 사번을 받는다. |
| 입사일 어제·오늘·미래, 마지막 재직일 경계 | 어제 날짜는 정정 안내, 오늘과 미래는 확정 가능하다. 미래 효력은 서울 기준 입사일을 경계로 보이고 종료일까지 유효하다. 미래 입사 전에 계정 초대와 인증을 열지 않는다. |
| 버전이 다른 템플릿·비활성 조직·타사 UUID·이미 철회된 예정 | 확정은 실패하고 사원·최초 발령의 부분 기록이 없다. 근무 구간 생성 또는 감사 실패를 강제해 같은 원자성을 확인한다. |
| 보존·기존 기능 | 기존 사원 번호·배정·프로필·근태 결과가 바뀌지 않는다. 확정 후 새 배정은 기존 구간을 닫고 최초 참조를 보존한다. 정식 입사 확정 경로에서 확정된 입사일은 기존 단건·일괄 쓰기로 변경할 수 없다. |
| 입사 첫날 직원 흐름 | 초대를 수락하면 내 정보의 본인 사번·최초 소속·입사 발령과 근무 일정·홈의 적용 근무가 일치한다. 내 정보에 처리자·사유는 새로 노출되지 않는다. 기존 허용망과 출퇴근 조건을 충족하면 현재 방식으로 출근할 수 있다. |
| Excel 필터·선택·권한 회수 | 여러 페이지의 정확한 필터 결과 또는 선택 사원만 담긴다. 사용자 문자열은 수식으로 실행되지 않고 사번 0은 보존된다. 시트가 미저장이면 화면은 다운로드 요청을 보내지 않으며 직접 API는 서버 확정 데이터만 읽는다. 상한 초과·권한 회수·감사 실패에는 파일 바이트를 반환하지 않는다. |
| 공개 데모 및 권한 경계 | 공유 5인 단건·일괄 보호, 신규 예정 쓰기·내보내기 차단, 대표·승인자·일반 직원·다른 고객사 거부, PostgreSQL 연결 재사용 후 테넌트 격리를 검증한다. |

구현은 인사기본 시트·Excel, 예정 등록·철회, 입사 확정·최초 발령·초대 연결 순서로 검증할 수 있다. 각 단위는 API·DB 계약의 실패 사례부터 작성한다. 단위·실제 PostgreSQL 통합·React 회귀와 일반/공개 프로필의 접근 경계를 합성 자료로 확인한다. 실제 고객 자료 사용 승인과 운영 환경에서의 V17 상세 인사정보 수집·이용·보존 기준 합의는 별도 출시 조건이다.
