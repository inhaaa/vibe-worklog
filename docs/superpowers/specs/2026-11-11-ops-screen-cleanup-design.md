# 운영 화면 정리·초 단위 시각·근무 확인 자동 계산 설계 (①)

기준일: 2026-11-11, Asia/Seoul. 사용자가 같은 날 화면별 정리안 그림을 보고 "이대로 확정"으로 승인했다. 작업 브랜치는 `claude/ops-screen-cleanup-20261111`(worktree `target/ops-screen-cleanup-20261111`, 기준 `main` 1bf37d3)이다.

## 1. 배경과 결정

사용자는 실제 운영 화면에 필요 없는 문구·열을 지우고, 상태·최신성 같은 검토용 정보와 밀리초 표시를 없애 `17:09:58`처럼 보이기를 요청했다. 같은 요청의 상단 탭, 담당자 사원 전환·대리 신청, 근태 현황 통계는 별도 작업이다. 진행 순서는 ① 화면 정리 → ② 상단 탭(최대 10개) → ③ 담당자 사원 전환·대리 신청 → ④ 근태 현황 통계이며, 이 문서는 ①만 정한다.

| 결정 | 내용 |
| --- | --- |
| D1 범위 | 직원 화면 전체: 내 정보, 출퇴근 기록, 근무 일정, 근로시간, 내 근태현황·신청, 신청 상세·정정 신청. 근로시간 화면은 담당자 '근태 집계'(`/admin/attendance`)와 같은 컴포넌트라 함께 바뀐다. 시각 표시 변경은 모든 화면에 적용한다. |
| D2 계산 | 직원이 근무 확인(기존 '퇴근 후 본인 확인')을 저장하면 그날 실근로를 바로 계산한다. 정정·휴가 승인 등 다른 사실 변경은 지금처럼 담당자 수동 재집계를 쓰며 ④에서 다시 정한다. |
| D3 방식 | 화면에서 직접 삭제하고 공통 시각 함수를 고친다. 상세 보기 토글이나 도움말 이동은 하지 않는다. |

## 2. 공통 표시 규칙

| 항목 | 현재 | 변경 |
| --- | --- | --- |
| 기록 시각(Instant) | `2026-11-11 17:09:58.315` | `2026-11-11 17:09:58` |
| 일정 시각(LocalTime) | `09:00:00.000` | `09:00` (초가 0이 아니면 `09:00:30`) |
| 시간량 | `7:53:00.000` | `7:53:00` |
| 계산 전·없는 값 | `미확정` | `-` |
| 일수 단위 | `DAY` | `일` |

- 프런트 `ui.tsx`의 `fmtDateTime`, `fmtTime`, `duration`과 서버 `SeoulTimeDisplay`(instant·time), `WorktimeController.duration`을 위 형식으로 바꾼다. 표시할 때만 초 미만을 버린다. 저장·계산·합산은 계속 밀리초 정본을 쓴다([계산 규칙](../../rules/calculation.md) 5절 유지). 합계는 밀리초로 더한 뒤 마지막에 한 번만 표시 형식으로 바꾼다.
- 화면 라벨의 `(서울)`, `Asia/Seoul` 표기를 지운다. 사이드바 하단의 `Asia/Seoul 기준` 한 곳만 남긴다.
- 직원 화면에는 영문 상태·사유 코드(`REVIEW_REQUIRED`, `PARTIAL_TOTAL`, `NOT_CALCULATED` 등), 규칙 버전(`CALC-1`), 사실·검토·결과 버전, 결과 ID를 표시하지 않는다. 계산 근거 상세(`/worktime/results/{id}`)와 감사 화면은 근거 확인용이므로 내용을 유지하고, 시각 형식만 공통 함수에 따라 바뀐다.
- 시각 입력(`datetime-local`)은 `step="0.001"`을 `step="1"`로 바꾸고, 입력칸에 채우는 기존 값도 초까지만 넣는다. 서버는 지금처럼 초 단위 ISO 값을 받는다.
- 바꾸지 않는 것: 검토용 Excel 형식(밀리초·`+09:00`, [ADR-0002](../../adr/0002-review-xlsx.md)), 저장값·hidden 값·감사·스냅샷.
- 회사 근무현황(`/company/attendance`) 열 머리글의 `(시:분:초.밀리초)`는 값 형식과 맞도록 지운다. 이 화면의 다른 정리(상태·최신성 열 등)는 담당자 화면을 다루는 ③·④에서 한다.

- 삭제: 인사 탭 제목 아래 설명문(기본사항의 "개인 정보와 입사 정보를 한눈에 확인하세요." 등 7개 탭 공통)과 "주민등록번호 미수집 · 원문 입력·저장하지 않습니다." 안내. 주민등록번호를 수집하지 않는 정책은 그대로다.

### 3.2 출퇴근 기록 `/me/attendance`

- 삭제: '출근 기록·실제 근로 확인' 제목과 그 아래 4줄(날짜·Asia/Seoul·사실/검토 버전, 예정 근무, `캘린더: WORKDAY`, 체류시간 안내).
- 변경: 예정 근무를 한 줄로 보인다. 근무일은 `예정 09:00~18:00 · 휴게 12:00~13:00`, 소정 비근로일은 `비근무일`, 일정이 없으면 기존처럼 경고 `근무 일정 미배정`을 보인다. 조회일이 오늘이면 '오늘의 근무' 카드의 "서울 현재 시각으로 기록됩니다." 자리에, 다른 날이면 출퇴근 기록 표 위에 보인다.
- 변경: '원천 출퇴근 기록' → '출퇴근 기록', 열 '원천 사건 | 서버 저장 시각 (서울)' → '구분 | 시각'.
- 변경: '승인 정정 반영값 · 원천은 별도 보존' → '정정 반영 기록'. 항목의 `IN`/`OUT`은 `출근`/`퇴근`으로 보인다.
- 변경: '퇴근 후 본인 확인' → '근무 확인'. 안내문("원천 한 쌍·같은 날짜…")과 예정 휴게 목록을 지운다. 체크 문구는 "휴게를 뺀 실제 근로가 맞습니다", "휴게가 예정과 같습니다", 버튼은 `근무 확인`이다.
- 표시 조건: 일정이 있고, 현재 반영 출근·퇴근이 각각 1건이며, 현재 사실에 대한 확인이 아직 없을 때만 확인 폼을 보인다. 서버 검증은 그대로 둔다.
- 확인 후: 확인이 있으면 `근무 확인 완료 · 실근로 8:11:26`을 보인다. 계산 결과가 없으면 `근무 확인 완료 · 실근로는 담당자 재집계 후 표시됩니다.`를 보인다. 이를 위해 출퇴근 기록 화면 모델에 그날 현재 계산 결과의 실근로(밀리초, 없으면 null)를 더한다.

### 3.3 근로시간 `/me/worktime` · 근태 집계 `/admin/attendance`

- 제목 '일·주·월 근로시간 검토' → '근로시간'. 조회 라벨 '기준 월 (서울)' → '기준 월'.
- 월 요약 4줄(부분합 문장, 최신성, 영문 코드, 법정 안내문) → 지표 3개.
  - 실근로 합계: 이 달에서 현재 계산 결과가 있는 날의 실근로 합.
  - 확인 전: 4절 규칙의 일수. 계산 규칙의 "부분합은 미확정 건수와 함께 보인다"를 지키려고 합계 옆에 둔다.
  - 휴가: 이 달 각 날짜의 현재 승인 휴가 일수 합.
- 일 결과 표의 열은 `근무일 | 실근로 | 휴게 | 8시간 초과 | 휴가`이다. 상태·최신성, 실근로 ms, 휴게 ms, 일8시간 초과 ms, 근거·예외·버전 열은 지운다.
  - 값은 현재 계산 결과일 때만 보이고, 결과가 없거나 오래됐으면 `-`이다. 휴가는 1이면 `1`, 0이면 `-`이다.
  - 근무일 셀은 결과 ID가 있으면 계산 근거 상세로 이동하는 링크다.
  - 숫자 열 정렬은 지금처럼 밀리초 값으로 한다.
- 주간 참고량 문장 목록 → 표 `주간 | 실근로 | 확인 전 | 40시간 초과`. 승인한 그림에는 `확인 전` 열이 없었지만, 주간 실근로도 부분합이라 같은 규칙으로 추가한다.
  - 주간은 `2026-11-02 ~ 2026-11-08`(월~일)로 표시한다. 실근로는 그 주에서 현재 계산 결과가 있는 날의 합이며, 월 밖의 날도 포함한다.
  - 40시간 초과는 기존 주 계산 값이고, 값이 없으면 `-`이다.
- 담당자 영역(수동 재집계·검토용 Excel): 기능·입력·링크는 유지한다. "결과 ID·입력/규칙 버전·필터를 고정한…" 문단과 "자유 사유·이메일·IP는…" 안내만 지운다.

### 3.6 신청 상세·정정 신청

대상 경로는 `/requests/{id}`, `/me/requests/correction`, `/admin/requests/exceptions/new`, 신청 모달의 정정 입력이다.

- 신청 상세 삭제: 제출 당시 결재선의 '결재선 버전'(코드·이름·버전)과 '해석 시각 (서울)' 행, "제출 당시 해석은 보존됩니다…" 안내, '제출 당시 근태정책' 섹션 전체와 그 안내, '신청 버전 v…' 표시, '요청한 정정' 아래 "원천 기록은 보존하며…" 안내. 적용 범위·결재 방식·제출 당시 소속·최초 결재 담당·처리 이력은 유지한다. 신청 일수의 `DAY`는 `일`로 바꾼다.
- 신청 모달의 정정 입력도 같은 원칙을 따른다. 출퇴근 근거 목록의 `(서울)`과 "원천 기록을 보존하고…" 문장을 지우고, 빈 목록 문구는 `출퇴근 기록이 없습니다.`로 통일한다.
- 정정 화면 삭제: 안내문 6개("원천은 수정·삭제하지 않으며…", "유지·시각 수정·누락 정정 중…", "시각 수정일 때만 제안 시각을…", "실제 확인한 근거를 기준으로…", "민감정보를 적지 마세요. 확인되지 않은 실제 근로는…", "작성자·대상자와 다른 승인자가…")와 '현재 원천 기록' 아래 날짜 안내.
- 정정 화면 변경: '현재 원천 기록' → '현재 출퇴근 기록', 빈 목록 문구는 `출퇴근 기록이 없습니다.`이다. '제안 출근 시각 (서울)' → '출근 시각', '제안 퇴근 시각 (서울)' → '퇴근 시각'.
- 정정 화면 변경: '기존 승인 정정을 다시 변경하는 경우'의 '변경할 현재 승인 정정 ID' 입력칸을 지운다. 대신 서버가 그 날짜의 현재 승인 정정 ID를 채워 hidden으로 보낸다. 신청 모달이 이미 쓰는 방식이며 `LeaveWorkflowMapper.currentCorrection`을 사용한다.
- 시각 입력은 1초 단위이고, 휴게 편집기(`RequestBreakEditor`)를 포함해 입력 라벨의 `(서울)` 표기를 지운다.

## 4. '확인 전' 일수 규칙

다음을 모두 만족하는 날을 확인 전으로 센다. 서버가 날짜별로 판단해 월·주 요약에 일수로 넣으며, 프런트는 직접 세지 않는다.

1. 오늘(서울) 이전인 날. 오늘은 현재 반영 퇴근 기록이 있을 때만 포함한다.
2. 실근로가 표시되지 않는 날. 즉 현재 계산 결과가 없거나, 오래됐거나, 실근로 값이 null이다.
3. 다음 중 하나에 해당하는 날.
   - 현재 반영 출퇴근 기록이 있다.
   - 일정상 근무일이고 캘린더가 휴일로 확정되지 않았으며 승인된 종일 휴가가 없다.
   - 일정이 미배정이거나 캘린더가 미확인이다. 근무 여부를 알 수 없으므로 확인 전으로 센다.
   - 대기 중인 정정이 있다.

따라서 기록이 없는 확정 비근무일, 기록이 없는 승인 휴가일, 미래 날짜는 세지 않는다. 기록 없는 날의 제외 여부는 `WorktimeCalculator.day`와 같은 규칙으로 판단한다. 즉 계산기가 기록 없이 0시간으로 확정하는 날만 제외하며, 이 판단은 `WorktimeCalculator.pending`으로 둔다. 날짜별 판단에는 `WorktimeService.readDays`가 이미 읽는 날짜별 입력(일정·캘린더·반영 기록·휴가·대기 정정)을 재사용하고 추가 조회를 만들지 않는다. 날짜별 결과는 `DayView.pending`, 기간 일수는 `PeriodView.pendingDays`로 내려준다. 휴가 열과 휴가 합계를 위해 `DayView.approvedLeaveDays`(현재 승인 휴가 일수)도 함께 내려준다.

## 5. 근무 확인 시 자동 계산

1. POST `/me/work-confirmations`는 기존 `ClockService.confirm`으로 검증·저장·감사를 마친다(트랜잭션 1).
2. 성공하면 같은 요청에서 `WorktimeService`의 새 본인 근무 확인 계산(확인한 날이 속한 주)을 실행한다(트랜잭션 2).
   - 대상은 로그인한 본인뿐이고 입력은 확인한 날짜 하나다. 다른 사원이나 기간을 입력으로 받지 않는다.
   - `BusinessCommands.execute(..., "EMPLOYEE", ...)`로 현재 직원 권한, tenant 잠금, 감사, 멱등성을 재사용한다. 감사 행위는 `WORKTIME_AUTO_CALCULATE`, 사유는 "근무 확인 후 자동 계산"이다.
   - 명령 ID는 확인 명령 ID에서 결정적으로 만든다. 그래서 같은 확인을 다시 보내도 계산은 한 번만 실행된다.
   - 기존 수동 재집계와 같은 계산기·저장 방식을 쓴다. `calculation_run`의 from·to는 그날이고 expanded는 그날이 속한 주(월~일)다. 일 결과는 새 revision으로 저장하며 입력 개정을 '계산됨'으로 표시한다. 공통 저장 부분은 수동 재집계와 한 메서드로 묶어 중복을 만들지 않는다.
   - 주 40시간 초과는 그 주 7일이 모두 현재 결과일 때만 나온다([계산 규칙](../../rules/calculation.md) `over_40h_millis`). 기록 없는 휴무일은 근무 확인을 할 수 없으므로, 확인할 때 그 주 7일을 함께 계산한다. 그만큼 확인 1건이 일 결과 7행을 쓰고, tenant 잠금을 하루 계산보다 약 5배 오래 잡는다(MVP 규모에서 허용).
   - 그 주의 남은 날도 미리 계산된다. 기록 없는 휴무일·승인 휴가일은 0시간 현재 결과가 되어 근로시간 화면에 `0:00:00`으로 보이고, 남은 근무일은 실근로가 없어 `-`다. 그날 기록·휴가·정정이 생기면 입력이 바뀌어 결과가 오래되고 다시 계산 전으로 돌아간다.
3. 계산이 실패해도(검증 거부·저장소 오류, 같은 주 다른 날의 손상·모순 입력) 확인 저장은 유지하고 화면은 정상 이동한다. 실패는 개인 식별 정보 없이 로그로 남긴다. 그날 값은 `-`와 확인 전으로 남고, 담당자 재집계로 복구한다.
4. 조회 GET은 계속 재집계하지 않는다.

## 6. 바꾸지 않는 것

- 계산 규칙(확인된 구간만 실근로, 밀리초 정본), DB 스키마(Flyway 변경 없음), 권한·tenant·RLS 경계, 검토용 Excel, 계산 근거·감사 상세 내용.
- 담당자 설정 화면의 문구 정리는 ③·④에서 한다.
- 서버 응답 중 화면에서 더 쓰지 않게 되는 값(내 정보의 배정 정보 등)은 이번에 지우지 않는다.

## 7. 오류·경계

- 출퇴근 기록이 없거나 중복이거나 자정을 넘는 날은 확인 폼이 보이지 않는다. 정정 신청 동선은 기존처럼 유지한다.
- 오래된 결과는 값 대신 `-`로 보이고 확인 전으로 센다. 예전 값을 현재 값처럼 보이지 않는다.
- 일정 시각이 초를 가지면 초까지 보인다. 일정 시각은 초가 0일 때만 `HH:mm`로 줄인다.

## 8. 검증

TDD로 진행한다. 실패하는 테스트를 먼저 보고 구현한다.

- 프런트 단위: `fmtDateTime`·`fmtTime`·`duration` 형식과 null 표시, 화면별 삭제 문구 미표시, 근로시간 열 목록, 근무 확인 폼 표시 조건, 대리 작성 섹션 표시 조건, 시각 입력 step.
- 서버 단위·통합: `SeoulTimeDisplay` 초 단위, 근무 확인 후 일 결과 생성과 실근로 값, 같은 확인 재전송 시 계산 1회, 계산 실패 시 확인 유지, 다른 사원 대상 계산 불가, 확인 전 경계(오늘·주말·휴가·미배정·기록 있는 휴일·오래된 결과), 정정 화면의 승인 정정 ID 자동 입력.
- 밀리초 문자열을 기대하는 기존 테스트는 새 형식으로 고친다.
- 실행: `frontend`의 `npm test`, `npm run build`, 백엔드 관련 테스트(DB가 필요한 IT는 기존 로컬 전용 DB 규칙을 따른다).
- 브라우저: 로컬 앱에서 6개 화면을 확인하고, 근무 확인 후 실근로가 보이는지 본다. 로컬 DB에 쓰는 실행 검증은 시작 전에 사용자에게 확인받는다.
