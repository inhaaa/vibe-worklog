# 신청서코드 관리와 팀장·실장 순차결재 명세

작성일 2026-11-18 · 검토안 · 개발 기준 `ab8c87a` (휴가 운영 변경 포함)

## 1. 직원과 담당자가 보게 될 결과

담당자가 **휴가 신청은 실장까지, 출퇴근 정정은 팀장까지**로 설정할 수 있다. 같은 직원이 연차를 신청하면 제출 전에 팀장과 실장을 순서대로 확인한다. 팀장이 승인하면 실장의 결재함에 들어가고, 직원에게는 `대기 · 2/2 실장 결재 중`으로 보인다. 실장이 최종 승인한 때 연차가 차감된다. 같은 직원의 출퇴근 정정은 팀장 승인으로 끝난다. 아래 사례는 설정 예시이며, 도입 당일 각 회사에는 기존 결재선이 적용된다.

| 기본 신청서코드(제안) | 직원에게 보이는 이름 | 기존 신청 종류 | 업무 처리와 결재의 관계 |
| --- | --- | --- | --- |
| `L01` | 휴가 신청서 | `LEAVE_DAY` | 현재 지원하는 종일 연차를 신청한다. 근태코드와 잔여를 검증하고 최종 승인 때 차감한다. |
| `L02` | 휴가 취소 신청서 | `CANCEL_LEAVE` | 원신청의 휴가 종류와 근태코드 버전을 이어받는다. 결재선은 취소 신청을 제출하는 날의 L02 설정으로 새로 만든다. |
| `A01` | 출퇴근 정정 신청서 | `ATTENDANCE_CORRECTION` | 해당 근무일의 출퇴근·실제 휴게 정정을 신청한다. 최종 승인 때 정정 효력을 반영하고 원천 기록을 보관한다. |

신청서코드는 **어떤 신청을 어떤 경로로 결재할지**, 근태코드는 **어떤 기준으로 일수·근무 기록을 처리할지** 정한다. 따라서 같은 연차에도 신청과 취소에 서로 다른 결재선을 연결할 수 있다. 기존 근태코드 식별자와 휴가 종류 필터는 그대로 사용한다. 연장근무 신청서는 해당 업무와 근무 기준이 마련될 때 이 방식으로 추가한다.

## 2. 담당자 설정 흐름

1. **조직관리 > 조직 관리**에서 조직의 `결재 단위`를 지정한다. 선택값은 `팀`, `실`, `경유 조직`이다. 경유 조직은 상위 조직을 찾을 때 지나가며 그 조직장에게 결재를 배정하지 않는다. 기존 조직의 초기값은 `미지정`이다. 담당자는 조직도에서 팀과 실의 조직장, 시작일과 마지막 담당일을 확인한다. 조직명·직책에 ‘팀’이나 ‘실’이 들어가는지는 판정에 쓰지 않는다.
2. **시스템 설정 > 결재 설정 > 결재선 관리**에서 기존 `지정 사원`, `소속 조직장`과 신규 `조직장 순차결재` 중 하나를 선택한다. 순차결재는 `팀장까지` 또는 `실장까지`를 지정해 결재선 버전으로 저장한다. 새 방식은 신청서에 연결할 때 선택한다. 기존 사원·조직별 1단계 배정 화면은 기존 두 방식을 계속 사용한다.
3. **시스템 설정 > 결재 설정 > 신청서코드 관리**에서 목록을 열고 한 행을 선택한다. 목록에는 코드·신청서명·업무 종류·사용 상태·현재 결재선·다음 적용일을, 상세에는 적용 기간·결재선 버전·변경 사유·변경자를 표시한다. PC는 목록 옆, 모바일은 선택한 행의 상세에서 편집한다. 목록으로 돌아오면 선택과 검색 조건을 복원한다.
4. 상세에서 `기존 배정 사용` 또는 `신청서 전용 결재선`을 고른다. 전용 결재선은 이름·버전·종료 단위를 확인해 연결한다. 같은 코드의 결재선에 새 버전이 생겨도 기존 연결은 지정한 버전을 사용한다. 담당자가 새 버전과 적용 시작일을 저장해야 전환된다.
5. 담당자는 사번·이름으로 예시 사원을 선택해 **이 사원이 오늘 직접 신청하면 누구에게 가는지** 미리 본다. 편집 중인 설정을 시험하면 `저장 전 설정`을 표시한다. 실제 대리 신청 화면에서는 로그인한 담당자를 작성자로 검증한다. 오류에는 단계·조직·원인과 수정할 화면을 보여 준다. 저장하면 적용일·설정 버전·사유를 이력에 남기고 재조회할 수 있다.

**코드 관리 규칙.** 최초 세 코드는 기존·신규 고객사 모두에 제공한다. 담당자는 코드·이름으로 검색하고, 현재 지원하는 세 업무 중 하나를 골라 코드를 등록하거나 이름·사용 상태·결재선 연결을 변경할 수 있다. 코드는 영문 대문자와 숫자로 이루어진 2~8자리 문자열이며 숫자만으로도 등록할 수 있다. 앞자리 0을 보존하고, 한 고객사 안에서 사용 종료된 코드까지 중복을 금지한다. 저장한 코드와 업무 종류는 고정한다. 이름·사용 상태·결재선은 서울 오늘 또는 미래 적용일부터 새 버전으로 남긴다.

같은 업무·같은 날짜에는 신규 접수용 코드가 최대 하나다. 기존 코드를 새 코드로 교체하면 한 번의 저장으로 기존 효력 종료와 신코드 적용을 처리한다. 예를 들어 12월 1일을 지정하면 11월 30일까지 기존 코드, 12월 1일부터 새 코드다. 이후 예약과 겹치면 충돌 날짜를 표시하고 저장 전체를 되돌린다. 사용 중지만 하면 해당 기간에는 그 종류의 신규 접수를 막고 기존 신청의 조회·결정은 유지한다. 휴가 신청서만 중지한 경우 사용 중인 취소 신청서로 기승인 연차의 취소를 요청할 수 있다.

## 3. 제출일의 결재선 생성 규칙

- 서버는 신청 동작으로 업무 종류를 정하고, **제출 시점의 서울 날짜**로 신청서 버전을 한 건 선택한다. 소속은 작성자 대신 **신청 대상자의 주 소속**을 쓴다. 휴가 대상일이나 과거 정정일은 기존 근태 정책을 고르는 데 쓴다.
- `기존 배정 사용`은 현행 순서인 명시 사원 결재선 → 기존 사원별 지정 승인자 → 주 소속 조직 결재선을 따른다. `신청서 전용 결재선`은 해당 버전만 해석한다. 지정된 결재선의 비활성·공석·자격 오류를 기존 배정으로 우회하지 않는다.
- 순차결재는 제출 시점의 주 소속부터 위로 올라가며 종료 조직까지만 검사한다. **팀장까지**는 처음 만나는 팀장을 넣고 끝낸다. 팀보다 실을 먼저 만나면 ‘이 사원의 결재 경로에 팀이 없습니다’로 접수를 차단한다. **실장까지**는 팀을 만나면 팀장을 넣고 처음 만나는 실에서 실장을 넣고 끝낸다. 실 직속 사원은 실장 한 단계다. 경유 조직만 건너뛴다. 종료 단위 미도달, 검사 구간 내 미지정·비활성 조직, 순환, 실에 도달하기 전 팀 단위 중복은 미리보기와 제출 모두에서 차단 사유를 표시한다.
- 각 단계는 그 조직에서 제출일에 유효한 조직장 한 명을 찾는다. 조직장 화면의 시작일과 마지막 담당일은 양쪽 모두 포함한다. 다른 회사 사원, 공석, 미수락·비활성 계정, 재직·결재 권한 미충족은 접수 오류다. 전체 단계가 유효해야 접수하며 첫 단계만 먼저 만들어 두지 않는다.
- **팀장 본인의 신청**에서 신청 대상자가 첫 팀장이고 종료 단위가 실장이면, 자기 결재 제외 사유를 기록하고 독립된 실장을 `1/1 실장 결재 중`으로 표시한다. 해당 팀장이 다른 직원의 신청을 대리 작성한 경우에는 제출을 막고 다른 적격 담당자가 작성하도록 안내한다. 대리 작성자를 바꾸는 것만으로 승인 단계가 줄어들지 않는다. 종료 단계가 대상자·작성자 자신이거나 한 사람이 팀장과 실장을 겸임하면 제출을 막고 원인과 조직을 표시한다.
- 직원의 연차·정정 양식, 캘린더에서 시작한 신청, 원신청 상세의 취소, 담당자의 예외 신청 모두 같은 해석기를 사용한다. 제출 버튼 위에 신청서명·코드, 기준일, 결재 순서와 사원을 보여 준다. 제출 시 다시 해석해 사용자가 확인한 결과와 달라졌으면 입력을 유지하고 새 결재선을 보여 준 뒤 재확인받는다. 내 정보의 기존 결재자 표시는 `기존 배정 기준`으로 표시해 개별 신청 미리보기와 구별한다.

## 4. 결재 진행과 업무 반영

| 동작 | 신청 상태와 결재함 | 업무 결과 |
| --- | --- | --- |
| 직원 제출 | 전체는 대기. 첫 결재자의 대기함에만 나타난다. 다음 단계는 상세에 ‘예정’으로 보인다. | 신청 이력 및 기존 대기 표시를 기록한다. |
| 팀장 중간 승인 | 전체는 대기. 팀장에게는 ‘내가 처리한 결재 · 1단계 승인’, 실장에게는 새 대기 건이 보인다. | 잔여·휴가 효력·출퇴근 정정 결과를 확정하지 않는다. |
| 마지막 단계 승인 | 전체는 승인. 최종 처리자·시각과 각 단계의 처리자·시각·사유를 구분해 표시한다. | 휴가 차감, 취소 복원 또는 정정 반영을 기존 업무 규칙에 따라 정확히 한 번 실행한다. |
| 어느 단계에서든 반려 | 전체는 즉시 반려. 남은 단계는 ‘진행 종료’로 보이고 대기함에서 빠진다. | 이미 남긴 중간 결재 이력을 보존한다. 취소 반려라면 원래 휴가는 유효하다. |
| 작성자 철회 | 최종 결정 전이면 중간 승인 후에도 철회 가능하다. 진행·예정 단계가 닫힌다. | 처리된 단계와 철회 사유를 보존하고 원장 변동은 없다. |

직원은 **내 신청**에서 현재 단계와 결재자를 확인한다. 담당자는 **휴가 신청 현황**이나 **출퇴근 정정 현황**에서 중간 승인 건을 ‘대기’ 한 건으로 조회한다. ‘승인’ 건수와 최종 처리자는 최종 결정에서만 가져온다. 취소 신청의 실장 승인이 끝나면 원신청은 `승인 · 취소됨`, 취소 신청은 `승인`이다. 상세에서 원신청과 취소 신청 각각의 결재 과정을 확인한다.

**결재자 변경.** 접수 후 조직 이동·조직장 교체·신청서 설정 변경은 이미 생성한 단계나 최초 배정자를 바꾸지 않는다. 실제 결정 시점에 현재 차례·권한·재직·독립성을 다시 검증한다. 예정자가 퇴사하거나 권한을 잃으면 그 단계가 도래했을 때 `대기 · 재할당 필요`로 표시한다. 담당자는 현재 단계에 한해 적격 사원에게 사유를 남기고 재할당한다. 작성자·대상자·이미 처리한 사원·다른 예정 단계 결재자는 재할당할 수 없다. 담당 권한만으로 승인할 수 없다. 과거 단계의 실제 처리자는 현재 결재 조회 자격을 유지하는 동안 본인이 처리한 신청 상세를 읽을 수 있다. 미래 단계에 이름이 있다는 사실만으로 결재함·상세 권한을 부여하지 않는다.

## 5. 데이터와 인터페이스 계약

| 단위 | 저장·조회 계약 |
| --- | --- |
| 신청서와 적용 버전 | 고객사·코드·업무 종류는 고정한다. 버전에는 표시명·사용 상태·적용일·결재선 선택 방식·연결한 불변 결재선 버전·사유·변경자·시각을 둔다. 당일 수정은 더 높은 개정으로 남기고 이미 접수한 버전은 보존한다. |
| 조직과 결재선 정의 | 조직에 결재 단위와 변경 이력을 둔다. 조직장 순차결재 버전에 종료 단위(팀·실)를 저장한다. 현재 조직의 부모 관계는 제출 당시 읽어 고정한다. 과거 날짜의 트리를 현재 조직도로 역산하지 않는다. |
| 신청 당시 결재선 | 새 신청에는 신청서 버전·제출 기준일·선택 출처를 고정한다. 전용 경로는 해당 신청에 귀속되는 불변 스냅샷에 결재선 버전, 경유·제외를 포함한 조직 경로와 단위, 소속·조직장 배정 ID와 버전, 단계 번호·역할·최초 결재자를 기록한다. 전용 지정 사원 경로는 해당하는 필드만 기록한다. 실제 사원·조직 배정이 없는 전용 경로에 기존 배정 ID를 만들어 넣지 않는다. |
| 진행과 결정 | 신청·단계 번호는 고객사 내 해당 신청에서 유일하다. 최초 배정과 현재 담당·처리 결과를 구분한다. 대기 신청의 현재 단계는 정확히 하나이며 처리 이력에 단계·실제 처리자·사유·시각을 기록한다. 신청의 현재 담당과 결재함이 같은 단계를 가리켜야 한다. 중간 승인 이벤트와 최종 승인 이벤트를 구별한다. |
| 기존 자료 전환 | 기존 3종은 저장된 `kind`로 기본 코드와 연결해 ‘기존 신청’으로 조회한다. 과거 신청의 새 설정 버전·누락된 결재 단계는 추정하지 않는다. 기존 직접 지정 참조 또는 V13 스냅샷, 현재 담당, 승인·반려·철회·효력·원장 기록을 보존한다. 전환 전 대기 건은 종전 1단계로 끝낸다. |

- 관리자 조회·저장 진입점은 `GET /admin/request-forms`, `POST /admin/request-forms/commands`를 제안한다. 저장은 명령 ID·기대 버전·변경 사유와 허용 입력만 받는다. 관리자 미리보기는 신청서 버전 또는 편집안과 대상 사원을 받는 읽기 연산이다. 직원의 미리보기와 제출에서는 서버가 인증된 계정·대상 권한·신청 동작을 확인한다.
- 신청 상세와 결재함 조회에 신청서 코드·당시 이름, 단계별 최초/현재 결재자·상태·실제 결정, 전체 상태·현재 순번·전체 단계 수를 제공한다. 단계 결정·철회·재할당은 기존 요청 경로를 활용하고, 현재 신청 버전과 예상 단계를 검증한다. 버전 충돌은 재조회, 업무 입력·설정 오류는 해당 항목의 수정으로 복구한다.
- 신청·단계 생성·이벤트는 한 트랜잭션이다. 중간 승인과 다음 담당자 전환도 함께 저장한다. 최종 승인은 기존 근태 버전·잔여·취소 가능 시각·중복 여부 등 해당 업무 요건을 재검증한다. 실패 시 최종 단계가 대기로 남고 중간 이력이 보존된다. 동시에 처리하거나 같은 명령을 재시도해도 결정·효력·원장 반영은 한 번이다.
- 새 테이블·참조는 인증된 고객사 ID와 복합 키·명시적 SQL 조건·RLS를 적용한다. 기존 설정 관리와 동일하게 서버에서 관리자 권한·CSRF·동시 편집·멱등성을 검증한다. 기존 이력 참조와 새 전용 경로는 신청당 하나의 최초 출처만 갖도록 후속 Flyway에서 제약을 확장한다. 전환 전후 기존 신청 수·상태·실제 담당·효력·원장 잔여를 대조한다.

## 6. 구현 시 수용 검증

| 시나리오 | 합격 기준 |
| --- | --- |
| 처음 도입한 고객사 | 세 코드가 보이고 명시 사원 결재선 → 기존 지정 승인자 → 소속 조직 결재선의 종전 우선순위와 1단계 결과를 유지한다. 기존 부적격 경로는 사유와 함께 차단된다. |
| 같은 직원, 다른 신청서 | 휴가에 실장까지, 정정에 팀장까지를 연결한다. 같은 직원의 휴가는 팀장→실장, 정정은 팀장만 표시되고 각각의 결재함에 순서대로 도착한다. |
| 실제 승인·차감 | 잔여 3일인 사원이 1일을 신청한다. 팀장 승인 후 대기·잔여 3일, 실장 최종 승인 후 승인·잔여 2일이다. 팀장은 처리 내역에서, 직원과 담당자는 상세에서 두 단계를 확인한다. |
| 취소·반려·철회·정정 | 취소 1단계 승인까지 원휴가는 유효하고, 최종 승인 후 ‘취소됨’과 잔여 3일을 확인한다. 중간 승인 후 실장 반려·작성자 철회 각각에서 잔여가 유지된다. 정정은 설정한 최종 단계에서만 누락 해소와 반영 결과를 확인한다. |
| 조직 예외 | 실 직속, 팀장 본인, 경유 조직, 공석·겸임·미지정·상위 실 없음, 대리 작성자와 결재자 일치 사례를 각각 검사한다. 다음 단계 사원의 선결재, 과거 처리자의 재결정, 다른 고객사의 설정·신청 접근도 차단한다. |
| 날짜·변경·구버전 | 서울 자정, 조직장 마지막 담당일과 후임 첫날, 신청서 교체일 양쪽, 적용 중지, 미리보기 직후 설정 변경을 검사한다. 제출 후 조직을 옮겨도 기존 결재선은 같고 다음 신규 제출에는 새 경로가 보인다. |
| 경합과 복구 | 팀장 승인 두 번, 승인과 철회, 재할당과 이전 결재자의 승인, 최종 승인 중 잔여 부족과 쓰기 실패를 각각 검증한다. 현재 단계·이력·원장·효력은 한 가지 결과와 일치한다. 다음 결재자가 자격을 잃은 건은 명시 재할당 후 남은 단계만 처리한다. |
| PC·모바일 | 두 화면 폭에서 담당자 설정·미리보기·저장·재조회 → 직원 신청 → 팀장 승인 → 실장 승인 → 담당자 상태·효력 확인을 같은 가상 사례로 수행한다. 모바일에서 결재 순서·현재 차례·반려 사유를 확인하고 상세 복귀 후 기존 필터와 페이지가 유지된다. |

구현 순서는 **① 신청서코드와 기존 신청 매핑 → ② 조직 결재 단위와 신청서별 경로 미리보기 → ③ 단계별 처리·이력·최종 효력 → ④ 결재함·운영 화면과 PC·모바일 통합 검증**이다. 각 단계의 데이터·인터페이스와 실패 사례를 테스트로 먼저 고정한다.
