# 업무 중심 메뉴·공통 사원 헤더·신청 화면 개편 설계안

- 기준일: 2026-11-01, Asia/Seoul.
- 상태: 2026-11-02 사용자가 인사정보 등록을 포함한 구현·테스트를 승인했다. 실제 구현 계약은 [인사정보·업무 화면](../../design/personnel-workspace.md), 실행 결과는 [검증 보고서](../../quality/personnel-workspace.md)를 따른다. 공개 배포 여부는 별도로 기록한다.
- 요청: 대표메뉴 → 서브메뉴 → 게시판 형태의 하위메뉴, 홈 제거, 재사용 가능한 사원 인사정보 헤더와 그 아래 관련 메뉴, 신청 화면 현대화.
- 기존 기준: [PRD](../../prd.md), [화면 계약](../../design/screens.md), [조직·사원](../../design/org-management.md), [계정·권한](../../design/account-access.md), [연도별 신청](../../design/annual-requests.md).

## 1. 화면 방향과 접근 비교

권장안은 **왼쪽 업무 트리 + 본문 사원 헤더 + 헤더 아래 업무 탭 + 목록/상세**다. 대표메뉴는 업무 영역, 서브메뉴는 업무 묶음, 하위메뉴는 실제 화면 링크다. 목록은 검색·필터·상태·행 선택·상세·주요 행동이 분명한 업무 게시판 형태로 구성한다. 게시글·댓글 기능을 새로 추가한다는 의미는 아니다.

| 접근 | 장점 | 부담 | 선택 |
| --- | --- | --- | --- |
| 왼쪽 3단계 업무 트리와 사원별 업무 탭 | 전체 업무 위치와 현재 사원 문맥이 함께 보이며 기존 URL을 유지하기 쉽다 | 트리 접힘·활성 경로와 작은 화면 동작을 정해야 한다 | 권장 |
| 상단 대표메뉴와 큰 펼침 메뉴 | 넓은 본문을 확보한다 | 3단계를 펼칠 때 업무 문맥이 가려지고 작은 화면은 별도 구조가 필요하다 | 대안 |

흰색 본문·옅은 회색 바탕·절제한 파란색 주요 행동을 유지하되, 현재의 작은 글씨와 빽빽한 폼을 정리한다. 본문 기본 글씨는 14~15px, 입력은 42~44px 높이를 기준으로 하고 제목·설명·상태·행동의 위계를 통일한다. 새로운 디자인/그리드 라이브러리를 이 개편에 추가하지 않는다. 기존 공통 그리드 검토안은 별도 작업이다.

## 2. 대표메뉴 → 서브메뉴 → 하위메뉴

아래 트리는 기능 목록이며 실제 표시는 기존 역할별 접근 권한으로 걸러낸다. 하나 이상의 허용 하위메뉴가 있을 때만 부모를 표시한다.

```text
내 업무
  인사정보
    내 정보                         /me/profile
  근태관리
    출퇴근 기록                     /me/attendance
    근무 일정                       /me/schedule
    근로시간                        /me/worktime
  휴가·신청
    내 근태현황·신청                 /me/requests
결재
  결재함
    결재 대기                       /approvals
    내가 처리한 결재                 /approvals/completed
인사·조직
  조직·사원
    사원 관리                       /admin/employees
    조직 관리                       /admin/organizations
    조직장 배정                     /admin/organization-heads
    조직도                          /company/organizations
  계정·권한
    권한 관리                       /admin/access
근태 운영
  회사 현황
    회사 근무현황                   /company/attendance
    회사 신청 현황                  /company/requests
    근태 집계·Excel                 /admin/attendance
  휴가 운영
    전체 신청                       /admin/requests
    연차 관리                       /admin/leave-balances
  근무 운영
    근무 설정                       /admin/schedules
    근무일·휴일                     /admin/calendar
시스템 설정
  결재 설정
    결재선 관리                     /admin/approval-routes
    결재선 배정                     /admin/approval-route-assignments
  업무 기준
    근태코드 관리                   /admin/attendance-types
    공통코드 관리                   /admin/common-codes
    계산 정책                       /admin/work-policies

    허용 네트워크                   /admin/networks
```

대표메뉴·서브메뉴는 접기/펼치기 버튼이고 하위메뉴는 실제 링크다. 현재 화면의 조상은 최초 진입과 화면 이동 때 열린다. 사용자는 다른 묶음도 열 수 있다. 브레드크럼은 `대표메뉴 / 서브메뉴 / 하위메뉴`와 상세 제목을 표시한다. 모바일은 같은 트리를 메뉴 패널에 표시하고 선택·Escape로 닫는다. native button/link와 aria-expanded/aria-current를 사용하며 복잡한 ARIA tree 역할을 임의로 붙이지 않는다.

메뉴 계약은 `id, label, children`을 갖는 부모와 `id, label, href, roles, 관련 page ID`를 갖는 하위메뉴로 구분한다. 권한 판정은 하위메뉴에서 적용하며 서버 인가는 그대로 유지한다. pathname 완전 일치만 사용하지 않고 상세 page ID와 문맥을 함께 매핑한다. 신청 상세는 본인 신청·결재·관리 진입 문맥을 허용된 경로 안에서 유지하고, 새로고침 때는 현재 사용자의 열람 관계에 따라 결정한다.

기존 `/me/requests`는 허용된 query만 받으므로 공통 `tab=` 파라미터를 모든 링크에 추가하지 않는다. 기존 year/typeId/status/page/authoredPage 및 상세·원장·배정 링크를 보존한다.

## 3. 홈 제거와 출퇴근 기능 보존

- 홈 메뉴와 홈 중심의 대시보드 구성을 제거한다. 로그인 후 기본 진입과 WorkLog 로고는 `/me/profile`의 인사정보 화면으로 연결한다.
- 출근·퇴근·실제 근로/휴게 확인은 `내 업무 / 근태관리 / 출퇴근 기록`으로 모은다. 현재 `/me/attendance` 화면에는 기록·확인 폼이 있지만 출근/퇴근 동작은 홈에 있으므로 버튼과 서버 명령 정보를 함께 옮긴다.
- 출근/퇴근 버튼은 서울 오늘을 조회할 때만 제공하며 서버 현재 시각으로 기록한다. 과거 날짜에는 과거 시각 출퇴근 버튼을 만들지 않는다. 실제 근로/휴게 확인은 선택 근무일과 해당 근거 개정에 연결한다.
- 출퇴근 POST의 성공 복귀도 출퇴근 화면으로 변경한다. 기존 `/me/today` GET은 같은 출퇴근 화면으로 안내해 기존 북마크·호출자의 이동을 보존한다. 사용 중인 상태 fragment 경로를 확인 없이 제거하지 않는다.
- 허용 IP·원천 기록·입력 개정·멱등성·서울 근무일 판단은 변경하지 않는다. 파일 삭제는 이 설계 범위에 포함하지 않는다.

## 4. 공통 EmployeeHeader와 헤더 아래 메뉴

```text
사진/이니셜   김직원  [재직]       인사정보
              개발팀 · 사번 0001
생년월일      직급       직책       직무       입사일
1990.01.01    선임       팀원       개발       2024.03.04
────────────────────────────────────────────────────
인사정보 | 출퇴근 기록 | 근무 일정 | 휴가·신청 | 근로시간
────────────────────────────────────────────────────
선택한 업무의 검색·요약·목록·상세
```

위의 이름·날짜는 화면 배치 설명용 가상 예시다. 실제 자료가 없는 항목을 예시 값으로 채우지 않는다.

`EmployeeHeader`는 전달된 인사정보를 표시하는 공통 컴포넌트이며 자체 조회·권한 판단·저장을 하지 않는다. 본인 화면에서 먼저 사용하고, 사원 상세에서는 관리자에게 허용된 대상 사원의 자료로 재사용한다. 회사 전체 목록처럼 대상 사원이 없는 화면에서는 회사/업무 제목을 쓰고 특정 사원 헤더를 강제로 표시하지 않는다. 결재 상세에는 허용된 신청 대상 요약만 전달하며 사원 상세 권한을 새로 부여하지 않는다.

| 헤더 입력 | 계약 |
| --- | --- |
| employeeId, employeeNo, employeeName | 서버에서 확인한 업무 대상. 상단 로그인 사용자와 구분 |
| companyName, organizationName | 현재 표시 대상의 회사·현재 유효 소속 |
| photoUrl | nullable. 서버가 허용한 이미지 경로만 전달. 없거나 이미지 로드 실패 시 이니셜 |
| birthDate | nullable/생략 가능. 본인·인사 관리자 projection에만 제공 |
| gradeName, positionName, jobName | 직급·직책·직무. 각각 독립 항목이며 조직장을 직책으로 자동 대입하지 않음 |
| joinedOn | 입사일. 날짜는 서울 기준 업무 날짜 형식으로 표시 |
| employmentStatus | WORKING / ON_LEAVE / SUSPENDED / PRE_JOINING / LEFT / UNKNOWN. 입사 전·퇴사 경계를 구분하고 확인되지 않은 값을 재직으로 추정하지 않음 |
| asOf, variant | 서버 조회 기준 시각과 full/compact 표시. 작은 화면에서도 필요한 인사정보에 접근 가능 |
| children | 허용된 실제 링크로 구성한 업무 탭. 일반 사원에게 관리자 탭을 만들지 않음 |

본인 탭은 인사정보·출퇴근 기록·근무 일정·휴가/신청·근로시간으로 연결한다. 관리자 사원 상세의 탭은 실제 대상 경로가 있는 사원정보·소속 이력·근무 배정·계정/권한을 우선 사용하고, 본인 경로에 다른 사원 ID를 붙여 재사용하지 않는다. 탭과 왼쪽 메뉴의 활성 표시는 같은 문맥 매핑을 사용한다.

## 5. 현재 데이터와 확장 경계

현재 employee에는 이름·사번·입사일·마지막 재직일·active/version이 있고, 소속·근무·승인 배정은 별도 조회한다. 사진·생년월일·직급·직책·직무·휴직/정직은 저장 모델이 없다. `workspaceEmployee`는 로그인 본인의 이름·회사만 제공한다. 따라서 JSX/CSS 변경만으로 요청한 모든 실제 정보를 제공할 수 없다.

권장 구현은 화면 개편과 함께 아래 인사정보 저장 계약을 확장하는 것이다.

- 생년월일과 직급·직책·직무는 선택 입력으로 추가하고 본인 조회·인사 관리자 조회/변경에 연결한다. 생년월일은 미래 날짜를 거부한다. 직급·직책·직무는 현재 공통코드에 이미 적합한 그룹이 있는지 먼저 확인하고, 없으면 해당 그룹의 확정 뒤 연결한다. 이번 화면 개편에서 호봉·급여·평가 기능은 추가하지 않는다.
- 재직/휴직/정직은 현재 계정의 active와 분리한 인사 표시 상태와 적용일·변경 이력으로 관리한다. 입퇴사일에 따른 입사 전/퇴사 경계를 함께 표시한다. 이 변경만으로 로그인·결재 자격·근태 계산을 자동 변경하지 않으며 기존 인증·근무 판정 계약을 유지한다.
- 기존 자료는 새 필드를 미등록으로 두고 현재 active로 휴직/정직 여부를 역추정하지 않는다. 인사 상태를 명시 등록하기 전에는 `상태 미등록`을 표시할 수 있다. 비활성 계정과 인사 상태는 별도 문구로 구분한다.
- 사진은 미등록 시 이니셜을 즉시 제공한다. 실제 사진 등록은 같은 회사 사원의 인사 관리 범위에서 허용하고, 파일 크기·허용 이미지 형식·실제 디코딩·재인코딩·보호된 조회를 정의한 뒤 구현한다. SVG/외부 URL을 임의로 받아 모든 화면에 노출하지 않는다. 저장 위치는 기존 첨부파일 기반의 존재 여부를 먼저 확인하며 전역 환경 변경으로 확대하지 않는다.
- 현재 multipart는 보안 검증 후 비활성화돼 있고 공통 Form 전송은 파일을 거부한다. 사진 등록은 별도 전송 인터페이스·제한된 요청 크기·인증/CSRF·현재 관리자 권한·테넌트 경계부터 정의하며, 화면 편의를 위해 전역 multipart나 기존 파일 거부 정책을 일괄 완화하지 않는다. 공통 헤더의 이미지 표시와 실제 사진 등록의 검증 결과를 구분한다.
- 새 저장 구조는 실행 시점의 마지막 Flyway 다음 번호를 사용한다. 현재 미커밋 V15와 충돌하지 않게 순서를 확인하며 적용된 이력을 수정하지 않는다. 본인/관리자와 대표/승인자의 조회 projection을 분리하고 필요한 SQL tenant 조건·RLS·현재 권한 재확인을 유지한다.
- 인사정보 수정은 기존 commandId·버전 충돌·감사·수정 사유·422 입력 보존을 재사용한다. 생년월일과 사진 원문을 일반 감사 목록·오류·접근 권한 없는 응답에 추가하지 않는다.

대안은 우선 메뉴·헤더·신청 화면만 개편하고 미등록 필드와 이니셜을 표시하는 것이다. 이 경우 화면 뼈대 구현과 실제 인사정보 기능의 완료를 구분하며 후속 등록 기능이 필요하다.

## 6. 신청 화면

신청 화면은 `사원 헤더 → 업무 탭 → 연도/상태 요약 → 검색·필터와 신청 버튼 → 신청 게시판` 순서다. 목록은 신청 유형·기간/일수·결재 진행·상태·신청일·상세 동작을 명확히 분리한다. 색상만으로 상태를 표현하지 않고 레이블을 함께 쓴다. 작은 화면에서는 신청 한 건을 하나의 카드로 배치하고 각 값의 항목명을 함께 표시한다.

작성 화면은 큰 단일 폼 대신 `신청 유형 → 내용 작성 → 제출 전 확인`의 단계가 보이는 모달을 사용한다. 첫 화면은 연차·출퇴근 정정 선택 카드, 작성 영역은 관련 필드만, 확인 영역은 예상 일수·잔여·결재 경로를 요약한다. 달력/기간, 사유, 결재 요약, 주요 제출 버튼의 시각적 위치를 통일한다. 미지원 반차·시간차·병가는 실제 신청 가능한 카드로 표시하지 않는다.

기존 AnnualRequestPage의 미리보기·최종 제출·서버 재검증과 GET 일반 작성 페이지를 재사용한다. 새 업무 API나 저장되지 않는 임시저장 기능을 디자인만으로 약속하지 않는다. 사용자에게 보이는 KEEP/SET/CLEAR는 유지·시각 수정·누락으로 정정으로 표시하고 전송 값은 유지한다. commandId·fingerprint·revision은 숨김 입력으로 보존한다. 실제 휴게 입력은 시작/종료 행과 추가/제거 버튼으로 제공하되 현재 서버 형식으로 직렬화하고 유효성 검증을 유지한다.

기간·일수·현재 잔여·선택 연도의 귀속 잔액을 혼동하지 않게 기존 수치 계약을 유지한다. 409/422/503의 입력 보존·중복 제출 방지·미리보기 후 변경 시 재확인·Escape·초점 복귀·미저장 이동 확인도 유지한다.

## 7. 구현 순서와 수용 기준

설계 확정 뒤 인터페이스/입력 스키마와 기대 결과부터 작성하고, 각 단위에서 실패하는 테스트 → 구현 → 정리 순서로 진행한다.

1. 메뉴 모델·역할별 필터·현재 화면 매핑 테스트를 먼저 추가한다. 3단계 트리·브레드크럼·모바일 메뉴를 구현하고 기존 링크와 접근 권한을 검증한다.
2. 홈 진입 변경과 출퇴근 화면의 버튼/명령 제공을 테스트한다. 로그인·로고·기존 오늘 경로·출퇴근 성공 복귀·허용 IP·근로/휴게 확인을 회귀한다.
3. EmployeeHeader 입력 계약·미등록·이미지 실패·상태·본인/선택 사원 구분 테스트를 먼저 추가하고, 인사 데이터 저장 확장과 조회 경계를 구현한다. DB 단위는 스키마 업그레이드·기존 자료 보존·RLS·버전 충돌을 검증한다.
4. 신청 모달의 단계·유형 전환·입력 보존·확인/제출과 접근성을 먼저 테스트한 뒤 화면을 개편한다. 기존 연도별 집계·미분류 귀속·취소/정정·결재 경로 규칙을 회귀한다.
5. React 관련/전체 테스트·타입/production build·관련 Java/격리 테스트를 실제 실행한다. PC와 390px에서 계층·헤더·목록·모달·키보드·초점을 관측한다.
6. 변경 파일·문서·git diff를 확인한다. 기존 미커밋 작업과 이번 작업을 분리해 필요한 파일만 포함한다. 공개 반영은 [전용 후속 절차](../../development/worklog-public-updates.md)에 따라 보안 통합·DB 보존·기존 서비스 전후 확인을 실제 수행한 경우에만 완료로 기록한다.

2026-11-01 최초 설계 문서 작성 당시에는 기존 소스·설정·DB·공개 서버를 변경하지 않고 문서 링크·경로·범위 일관성만 검증했다. 이후 승인된 구현과 실제 검증은 위 후속 계약·보고서에 구분해 기록한다.
