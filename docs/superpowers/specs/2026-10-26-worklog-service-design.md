# WorkLog 사용자·관리 업무 확장 설계

> 기술 선택 후속 결정: 2026-10-26 사용자가 전체 React 전환을 승인해 아래 Thymeleaf 유지 전제는 [ADR-0003](../../adr/0003-react-frontend.md)으로 대체했다. 이 문서의 신규 업무 기능·권한·데이터 계약은 후속 구현 범위로 유지하며, 프론트 기술 전환만으로 구현 완료가 되지 않는다.

> 2026-10-27 실행: 1단계 대표 역할·메뉴·내 정보·권한 목록/단건 변경·회사 읽기를 React 기준으로 구현·로컬 검증했다. [실행 계획](../plans/2026-10-27-react-identity-access.md)과 [실제 결과](../../quality/identity-access.md)를 따른다. 2절은 최초 설계 당시 기준이며 당시 본인 정보는 현재 지정 승인자까지 제공하고 조직장 배정·나머지 단위·운영 수용은 후속으로 남겼다.

> 2026-10-27 착수·2026-10-28 기준 2단계 구현 계약: 조직·사원 원자적 시트, V12 조직장 이력, 관리자/대표 조직도와 본인 조직장 표시는 [실행 계획](../plans/2026-10-27-react-org-sheet.md)·[상세 계약](../../design/org-management.md#react-조직사원-시트조직장조직도-2단계-계약)을 따른다. 전체 회귀·기본 DB 반영·실제 화면 확인의 완료 여부와 수치는 [별도 검증 보고서](../../quality/org-sheet-heads.md)에 기록한다. 위 1단계 결과는 당시 이력이며 새 결재선·권한/코드 시트·본인 연도별 모달·월간 개선·운영 수용은 계속 후속이다.

## 1. 상태·승인·적용 범위

- 작성일: **2026-10-26, Asia/Seoul**. 조사 기준: `caf1074`의 소스·V1~V10 마이그레이션과 기존 설계·검증 기록.
- 사용자는 내 정보, 시트형 관리, 권한·조직장·결재선, 공통코드와 근태코드 분리, 연도별 조회 후 모달 신청, 월간근무현황의 설계 방향을 승인했다. 대표의 범위는 **회사 전체 현황 조회·지정 결재**, 설정 변경은 관리자로 정했다.
- 최초 산출물은 **후속 개발을 위한 설계 문서**였다. 당시 문서 작성·검증·커밋·일반 Push만 수행하고 코드·DDL·설정·DB·실제 화면은 변경하지 않았다. 이후 별도 승인한 1·2단계의 구현 계약과 실행 사실은 상단 기록·단위별 보고서로 구분한다. 설계 작성은 기능 구현·테스트 통과·서비스 출시 완료를 뜻하지 않는다.
- 아래 세부 정책은 승인된 방향을 구체화한 설계 기준이다. 다단계 결재·새 휴가 계산·법정 한도·자동 연차 발생을 이번 승인에 포함된 구현으로 확대하지 않는다.
- 기존 [PRD](../../prd.md), [조직·사원](../../design/org-management.md), [계정·권한](../../design/account-access.md), [신청·승인](../../design/leave-workflow.md), [계산](../../design/worktime-engine.md), [결과 조회](../../design/worktime-results.md), [보안](../../design/security.md)을 기반으로 한다. 현재 실행 사실은 해당 문서와 [개발 안내](../../development/local.md)의 변경 단위별 결과를 따른다.

## 3. 설계 선택과 메뉴

기존 Thymeleaf·htmx·일반 폼·CSS/JavaScript와 모듈형 모놀리스를 확장한다. 새 SPA·그리드·차트 라이브러리를 도입하지 않는다. 메뉴만 변경하는 안은 권한·연도 집계·결재선 요구를 충족하지 못하고, 전면 재작성은 검증된 원장·격리·승인 흐름을 다시 만들어야 하므로 채택하지 않는다.

| 메뉴 묶음 | 화면 | 접근 범위 |
| --- | --- | --- |
| 내 업무 | 홈, 내 정보, 내 근무 일정, 내 근태현황·신청, 월간근무현황 | 공통: 본인 |
| 결재 업무 | 결재 대기함, 내가 처리한 결재 | 현재 결재 담당 자격과 실제 배정 범위 |
| 회사 현황 | 조직별/사원별 근무현황, 회사 신청 현황, 조회용 조직도 | 관리자·대표: 자기 회사 |
| 인사 관리 | 조직 관리, 사원 관리, 조직장 배정 | 관리자 |
| 권한·결재 설정 | 권한 관리, 결재선 관리·배정 | 관리자 |
| 근태 설정 | 근태코드 관리, 근무 일정, 근무일·휴일, 허용 네트워크 | 관리자 |
| 운영 관리 | 공통코드 관리, 연차 기초·원장, 재집계·검토 Excel, 감사 | 관리자 |
| 서비스 운영 | 기존 별도 운영자 콘솔 | 기존 운영자 인증. 고객사 권한과 독립 |

관리자·대표도 공통 개인 업무를 사용한다. 같은 계정에 관리자와 대표를 함께 부여할 수 있으며 권한은 명시적으로 부여한 역할의 합집합이다. 대표만 있는 계정에는 설정 메뉴를 제공하지 않는다. 직함·조직장·화면 선택값으로 역할을 추정하지 않는다.

## 4. 권한 계약

### 4.1 역할·기능 권한·데이터 범위

| 표시 역할/기능 | 저장·호환 방향 | 허용 | 제한 |
| --- | --- | --- | --- |
| 공통 | 기존 `EMPLOYEE` 유지 | 본인 정보·출퇴근·신청·결과 | 타인 업무·자기 역할 변경 금지 |
| 관리자 | 기존 `ATTENDANCE_ADMIN` 유지 | 자기 회사 설정·관리·검토 | 관리 역할만으로 결재 허용하지 않음 |
| 대표 | 신규 `COMPANY_REPRESENTATIVE` | 회사 현황 조회·지정 결재 | 관리자 역할이 없으면 설정·원장 조정·재집계 금지 |
| 결재 담당 가능 | 기존 `APPROVER`를 기능 권한으로 유지 | 실제 배정된 신청의 처리 | 공통·관리자·대표와 별개. 미배정 건·자기/작성 신청 결재 금지 |

권한 관리 시트는 계정·사원·조직·공통(필수)·관리자·대표·결재 담당 가능·현재 상태를 표시한다. 3종 화면 역할을 저장할 때 기존 `APPROVER`를 누락시켜 회수하지 않는다. 행 입력의 `approverEnabled`는 미지정=유지, true=부여, false=명시 회수로 구분한다. 조직장·대표 지정 자체로 관리 또는 결재 기능 권한을 자동 부여하지 않으며, 결재선에 넣을 때 적격성을 검증한다. 고객사가 역할 종류나 서버 기능 권한을 임의 생성하는 기능은 제공하지 않는다.

- 관리자는 현재 재직·활성·초대 수락 완료 계정의 권한을 변경한다. 마지막 유효 관리자 보호, `auth_version` 증가·기존 세션 회수와 감사는 유지한다.
- 대표 전용 회사 조회는 본인 조회와 관리자 변경 경계에 새 **회사 읽기 범위**를 추가한다. 시작 시점과 반환 직전 현재 계정·재직·역할·세션 버전을 재확인한다. 조회 공급자는 저장·재집계·쓰기 잠금 승격을 하지 않는다.
- 대표의 현황 목록에는 필요한 사번·이름·조직·근무량·신청 유형/상태만 제공한다. 자유 사유·민감 증빙·IP·비밀값·감사 상세·관리자용 Excel 생성은 대표의 기본 조회 범위에 포함하지 않는다. 지정 결재자는 결정에 필요한 해당 신청 상세를 기존 최소 노출 규칙에 따라 본다.
- tenant는 principal에서 결정한다. 메뉴 표시와 별도로 Controller·서비스·SQL·RLS에서 범위를 검증한다. 운영자에게 고객사 역할을 부여하거나 운영자 DS로 회사 현황을 조회하지 않는다.

### 4.2 내 정보

`GET /me/profile`에서 이름·사번·회사·현재 소속·현재 조직장·입사/마지막 재직일·본인 계정 이메일·현재 역할·적용 근무·현재 결재 담당 정보를 조회한다. 미배정·부재·비활성은 상태로 표시하고 추정값을 채우지 않는다. 상단 이름도 이 화면에 연결한다.

첫 단위는 읽기 전용이다. 이메일·인사 정보·권한·비밀번호 변경은 이 화면의 임의 수정 대상으로 추가하지 않으며, 기존 계정 복구 경로는 유지한다. `employeeId`·`tenantId` 입력으로 조회 대상을 선택할 수 없다.

## 5. 시트형 관리와 조직

2단계 구현 계약은 이 절 중 **조직·사원 시트와 조직장/조직도**에 한정한다. 권한·공통코드·근태코드·결재선 시트는 후속이다. 기존 단건·소속·계정·지정 결재 경계와 1단계 회사 읽기를 유지하며 실제 검증 범위는 [2단계 보고서](../../quality/org-sheet-heads.md)로 구분한다.

### 5.1 공통 편집 동작

조직·사원·권한·공통코드·근태코드·결재선 관리 화면에 검색/필터와 `조회 / 입력 / 삭제 / 저장 / 취소` 도구 모음을 둔다. 허용하지 않는 작업은 비활성 상태와 이유를 표시한다. 권한 시트의 입력은 기존 계정 선택이며 역할 종류 생성이 아니다.

| 동작 | 계약 |
| --- | --- |
| 조회 | 기본 50행 페이지와 기존 검색 조건 사용. 미저장 변경이 있으면 이동/재조회 전 손실 확인 |
| 입력 | 신규 행을 화면에 추가. 저장 전 서버 값 불변 |
| 셀 수정 | 변경 행·필드를 표시. 고정 코드·사번은 저장 이후 수정 불가 |
| 삭제 | 미저장 행은 화면 제거. 저장된 마스터는 비활성 예정 표시, 저장 시 효력 종료/비활성화 |
| 저장 | 현재 화면의 변경분 1~50행을 한 트랜잭션으로 처리. 성공 후 결과 재조회 |
| 취소 | 서버 요청 없이 조회 당시 값으로 복원. 삭제 예정도 복구 |

저장된 행의 삭제 버튼에는 이력 보존 비활성 처리임을 명시한다. 권한 행 삭제는 선택 기능 권한 회수이며 계정·필수 공통 역할 삭제가 아니다. 조직·사원·소속·원장·출퇴근·신청·결재·감사 원문은 이 화면에서 물리 삭제하지 않는다. 비활성 코드/결재선의 기존 사용 이력과 대기 신청은 보존한다.

배치는 `commandId`, `reason`, `rows[]`를 받고 행마다 `clientRowId`, 기존 `id?`, `expectedVersion?`, `operation=CREATE|UPDATE|DEACTIVATE`, 허용된 업무 필드를 가진다. 기존 행은 버전 필수, ID·clientRowId 중복/범위 초과/알 수 없는 필드를 거부한다. 별도 화면의 서로 다른 업무를 한 배치에 섞지 않는다.

고객사 독점 잠금 → 현재 관리자 재확인 → 명령 재전송 검사 → 모든 대상·버전·최종 상태의 업무 규칙 검증 → 변경·세션 회수·감사 → 커밋 순서다. 한 행이라도 실패하면 모든 행과 감사·세션 회수 변경을 롤백한다. 조직 계층은 배치의 최종 그래프로 순환을 검증하고, 마지막 관리자도 최종 권한 집합으로 판단한다. 독립 트랜잭션의 단건 API를 반복 호출하는 일괄 저장은 금지한다.

배치 전체에 기존 `OrgCommands`와 같은 명령 해시·재시도 계약을 적용한다. 루트 명령의 감사에는 배치 ID·행별 clientRowId/결과 ID/결과 버전의 안전한 매핑을 남기고, 기존 단일 target_id 반환을 배치 결과 복원까지 확장한다. 입력 해시는 정규화한 행 순서·clientRowId·기존 ID·기대 버전·업무 입력·사유를 포함하며 서버 생성 결과 ID·결과 버전은 제외한다. 행별 감사는 서로 다른 명령 ID로 추가하고 기존 `request_trace_id`에 같은 배치 ID를 넣어 연결한다. 업무 값은 각 행의 안전한 전후 요약으로 남긴다. 감사 화면의 배치 요약은 허용된 ID·버전·건수만 해석한다. 같은 명령의 입력이 달라지면409다.

409/422 응답은 신규·수정·삭제 예정 행과 commandId·clientRowId를 유지한다. 행/필드별 오류를 표시하고 첫 오류에 초점을 둔다. 충돌은 최신값과 편집값을 비교할 수 있게 하며, 사용자가 수정·재확인한 새 저장에는 새 commandId를 발급한다.503 등 성공 여부가 불분명한 동일 내용 재전송은 원래 commandId를 사용한다. 자기 권한 변경으로 세션이 회수됐다면 다시 인증한 현재 적격 관리자만 성공 결과를 재조회/재전송할 수 있다. 관리자 권한까지 회수된 작성자는403이며 이미 커밋한 변경은 유지한다.

### 5.2 조직·사원·조직장

- 조직 시트: 조직코드·이름·상위 조직·조직장·활성 상태. 코드 불변, 동일 회사 부모, 자기 부모·순환 금지, 활성 자식/현재·미래 소속이 남은 조직 비활성화 차단을 유지한다. 조직장은 별도 배정 화면으로 편집한다.
- 사원 시트: 사번·이름·입사/마지막 재직일·활성 상태를 편집한다. 현재 소속·조직장·근무는 조회 및 배정 화면 연결로 제공한다. 소속 셀을 덮어써 이력을 바꾸지 않는다. 기존 소속 이동·재직·세션 회수·마지막 관리자 보호를 유지한다.
- 조직도: 계층을 접고 펼치는 트리와 선택 조직의 조직장·직원 목록을 제공한다. 기본은 서울 기준 오늘의 유효 소속이며 검색 결과의 범위를 표시한다. 일반 직원의 전사 직원 검색은 이번 기본 권한에 추가하지 않는다.
- 조직장: 조직별 한 명, 동일 회사의 활성·현재 재직 사원으로 지정한다. 첫 구현은 오늘 이후 적용일, `[valid_from, valid_to)`와 당일 교체 이력을 사용한다. 과거 배정은 덮어쓰지 않고, 중첩은 차단한다. 조직장이 그 조직의 소속원이어야 한다는 제약은 두지 않아 겸직을 허용한다.
- 조직장 퇴사·권한 회수로 기존 기록을 삭제하지 않는다. 부재/재지정 필요를 표시하고 신규 결재 해석은 실패시킨다. 조직장이라는 이유로 설정·회사 전체 열람 권한을 주지 않는다.

### 5.3 2단계의 구체 입력·이력 계약

조직·사원 배치는 각각 기존 CSRF 폼의 `commandId`, `reason`, `rows` JSON 배열을 받는다. `clientRowId`는 UUID 문자열이고 신규 조직 부모는 저장된 같은 회사 조직 ID만 선택한다. 업무별 필드 allowlist와 JSON 중복 키 검사로 역할·소속 등 범위 밖 입력을 차단한다. 목록의 `organizationSheet`/`employeeSheet`는 전체 표시 `rows`, 최신 DB 원본 `latestRows`, 행/필드 `errors`를 분리한다.409/422에는 현재 검색·상태·페이지에서 사라진 편집 대상의 최신 원본도 포함해 비교하고, 편집·비활성 예정·명령/행 ID·사유를 유지한다. 루트 감사의 안전한 결과 매핑으로 같은 명령의 결과를 복원하며 성공 재전송도 현재 관리자 권한을 요구한다.

조직장 변경은 조직의 `expectedVersion`을 집계 버전으로 검증한다. 적용일은 서울 오늘 이후이며 현재 및 적용일 모두 재직 중인 활성 사원이어야 한다. 같은 조직 소속·계정·APPROVER는 필수 조건이 아니며 자동 부여하지 않는다. 적용일에 걸친 구간만 닫고, 같은 시작일 교체·종료는 기존 행을 superseded 처리한다. 새 구간은 이전 종료일 또는 다음 예약 시작일까지여서 이후 예약·미배정 공백을 보존한다. 과거 배정과 기존 신청의 지정 결재자는 바꾸지 않는다.

관리자 시트의 `organizationHeadsById`·`employeeContext`와 본인 프로필에 현재 조직장·재직 적격성·결재 자격을 추가한다. 조직도는 관리자/대표의 회사 공유 읽기로 전체 조직 트리와 선택 조직의 오늘 재직 사원50명·검색 범위를 제공하며 이메일·자유 사유·계정/세션을 제외한다. 본인 프로필은 principal 대상에 고정한다. 조직장 기반 결재선 해석은 3단계 계약으로 남긴다.

## 6. 결재선과 결재

### 6.1 첫 구현 범위

**결재자는 한 명인 순차 없는 1단계**로 유지한다. 결재선 정의·적용 배정·실제 신청 당시 해석 결과를 분리한다. `지정 사원` 또는 `신청 대상자의 현재 소속 조직장`을 선택할 수 있다. 두 명 이상의 순차 결재·합의·병렬·자동 대결·상위 조직 자동 탐색은 후속 범위다.

신규 신청의 결재선 선택 우선순위는 **명시 사원별 결재선 → 기존 사원별 지정 승인자 → 현재 소속 조직의 결재선**이다. 상위 우선순위가 존재하지만 공석·비활성·자기결재이면 하위로 우회하지 않고422와 재지정 안내를 반환한다. 조직장 선택에서도 다른 사람을 임의 추정하지 않는다. 이 순서는 기존 직접 지정의 동작을 보존한다.

제출 시 현재 유효한 조직·배정·결재선 버전·조직장 배정과 실제 결재 사원을 고정한다. 대상 사원·작성자 계정과 결재자의 독립성, 결재자의 활성·재직·수락 완료·`APPROVER`를 확인한다. 대표의 본인 신청도 독립된 다른 결재자가 필요하다. 미배정이면 제출을 차단한다.

### 6.2 대기·변경·결정

- 결재선·조직장·소속 변경은 이후 제출에 적용한다. 기존 대기 건은 자동 이동하지 않고 저장 당시 실제 결재자를 유지한다.
- 결정 시 현재 지정자, 현재 결재 기능 권한·재직·세션과 신청 버전을 재확인한다. 이전 스냅샷만으로 퇴사자나 권한 회수자의 결재를 허용하지 않는다.
- 결재자 부재는 관리자의 명시 재할당으로 처리한다. 사유·변경 전후 결재자·신청 버전·원래 스냅샷을 남기며 새 결재자에게도 독립성을 적용한다. 기존 승인 결과는 바꾸지 않는다.
- 승인·반려·철회·별도 취소 신청과 취소 심사 중 원승인 효력, 승인 시 잔여 재검증·동시성·원장 단일 반영은 기존 계약을 유지한다. 결재자 변경으로 기승인 휴가를 취소하지 않는다.
- 기존 `/approvals`, `/requests/{id}`, 승인/반려/철회/취소/재할당 POST를 재사용하고 완료 결재 조회를 추가한다.

## 7. 공통코드와 근태코드

### 7.1 공통코드

공통코드는 고객사별 표시·분류용 코드그룹과 상세코드다. 그룹/코드 식별자·표시명·정렬·사용 여부·설명을 관리한다. 그룹 내 코드 유일, 저장 후 코드 불변, 비활성 코드의 과거 참조 보존을 적용한다. 시스템 소유 그룹은 구조·시스템 코드를 관리자도 삭제/변경할 수 없다.

권한 역할, 신청 상태, 승인 결과, 서버 처리 핸들러, 법적 계산 규칙은 공통코드의 사용자 편집 대상으로 제공하지 않는다. 아직 소비하는 업무가 없는 분류를 추가해도 사원 필드나 계산이 자동 변경되지 않는다.

### 7.2 근태코드

근태코드 관리는 관리자 전용 별도 메뉴다. 안정적인 코드와 **불변 정책 버전**을 분리하고 사용자는 코드·이름·유형·단위·유급 구분·차감 규칙·근무 인정 규칙·유효기간·사용 상태·신청 가능 여부를 확인한다. 상세 정책에는 근거·등록자·변경 사유가 필요하다.

| 구분 | 첫 구현의 허용 |
| --- | --- |
| 시스템 연차 코드 | 기존 종일 연차에 연결. DAY·정수·승인 시 원장 차감 유지 |
| 출퇴근/휴게 정정 | 기존 별도 정정 프로세스. 휴가 잔여가 있는 코드로 취급하지 않음 |
| 신규 병가·경조·외근·반차·시간차 등 | 초안 등록 가능. 지원 계산·차감·결재 계약과 테스트가 없으면 신청 활성화 불가 |
| 처리 방식 | 서버의 고정 capability가 시스템 유형별 지원을 결정. 사용자 스크립트·자유 산식 없음 |

`approval_request.kind`의 `LEAVE_DAY`·`ATTENDANCE_CORRECTION`·`CANCEL_LEAVE`는 프로세스 상수로 유지한다. 업무 근태유형/버전은 별도 참조다. 신규 코드를 기존 연차 핸들러에 임의 매핑해 사용할 수 없다. 유급 여부·근무 인정 방식도 코드명만으로 추정하지 않는다.

신청 당시 근태유형 버전을 고정하고 승인 시 해당 버전의 지원 여부와 일정·휴일·중복·잔여·재직을 재검증한다. 정책 수정은 후속 버전으로 만들고 신규 신청에만 적용한다. 비활성은 신규 신청을 막되 기존 대기·완료 건의 처리와 취소를 막지 않는다. 미지원 핸들러 오류는 정상 승인으로 대체하지 않는다.

버전은 `effective_from`과 `revision`으로 선택한다. 대상 일자 이하 가장 늦은 적용일에서 최고 revision을 사용하며 다음 적용일 전까지 유효하다. 비활성화도 `enabled=false`인 후속 버전으로 표현한다. 동일 적용일 정정은 새 revision이고 이전 행은 보존한다. 첫 구현에서 한 신청 기간은 한 정책 버전으로 해석돼야 하며, 기간 중 버전이 달라지면 분리 신청을 안내한다. 이미 제출한 대기는 당시 버전을 유지하며 이후 비활성/새 버전을 소급 적용하지 않는다.

## 8. 연도별 조회와 신청 모달

### 8.1 조회 기준

`GET /me/requests?year=YYYY`를 기본 진입으로 한다. 기본 연도는 서울 기준 현재 연도이며 대상 기간은 `[1월1일, 다음 해1월1일)`이다. 제출일이 아닌 **대상 근무일/휴가일**로 조회한다. 연도 경계를 걸친 신청은 각 연도에서 해당 날짜의 수량만 집계하고 상세는 원신청 전체를 보여준다.

화면 순서는 연도·근태유형·상태 조회 → 유형별 현황 → 신청 이력 → `신청` 버튼이다. 상태/유형 필터는 목록에 적용하며 연도 전체 현황 수치는 필터로 축소하지 않는다. 목록은50행 페이지, 수치는 해당 연도 전체 대상이다. 대리 작성한 타인 신청은 본인 수치에 넣지 않고 별도 작성 이력으로 구분한다.

| 표시값 | 정확한 의미 |
| --- | --- |
| 등록 기초·조정 | 근거로 확인된 귀속연도의 OPENING/ADJUSTMENT 합. 법정 자동 발생량이나 연초 잔여라고 표시하지 않음 |
| 사용 | 선택 연도 날짜 중 오늘까지 현재 승인 효력이 유효한 휴가 DAY |
| 사용 예정 | 선택 연도 날짜 중 오늘 이후 현재 승인 효력이 유효한 DAY. 승인 시 이미 차감됐음을 표시 |
| 결재 대기 | 선택 연도에 속하는 대기 DAY. 예약·차감하지 않음 |
| 현재 사용 가능 | **조회 시점 오늘** 유효한 묶음의 현재 원장 잔여. 선택 연도의 역사적 잔여와 구분 |
| 귀속연도 원장잔액 | 확인된 귀속연도 묶음별 잔액과 사용기간. 만료/미개시분과 현재 사용 가능분을 구분 |

현재 `leave_bucket`에는 귀속연도가 없고 유효기간이 연도를 넘을 수 있다. 기존 `base_date`의 연도로 자동 귀속시키지 않는다. 관리자 근거 확인 후 별도 귀속 이력을 등록하고, 확인 전의 등록 기초·귀속연도 잔액은 **귀속 미확인**으로 표시한다. 신청별 실제 사용·대기·예정 조회는 기존 일자와 효력으로 제공할 수 있다.

기초 잔여는 등록 이전의 사용을 반영한 자료일 수 있으므로 과거 사용을 다시 빼지 않는다. 서로 다른 귀속연도분이 섞인 묶음은 전체를 한 연도에 배정하거나 자동 분할하지 않고 미분류로 둔다. 최초 분류는 묶음 전체가 단일 귀속연도라는 근거가 있는 경우만 허용한다. 확정 후 근거 오류가 발견되면 사유를 가진 미분류 revision을 추가해 분류를 해제한다. 자료 범위는 `REGISTERED_DATA_ONLY` 또는 `NO_REGISTERED_DATA`로 표시하고, 확인 가능한 연도 수치도 등록 자료 기준임을 명시한다. 빈 조회 결과만으로 연간 사용0일·발생0일을 확정하지 않는다.

과거 연도를 선택해도 모든 상태는 조회 시점 현재 상태다. 과거 시점의 잔여·당시 대기 상태를 재현하는 기능은 이번 범위가 아니다. 현재 잔여를 과거 연말 잔여로 표시하지 않는다. 자동 발생·소멸·이월은 추가하지 않고 기존 원장·유효기간을 보존한다. `현재 잔여=연도 기초-연도 사용`이라는 잘못된 등식도 사용하지 않는다.

### 8.2 모달 작성과 제출

`신청` 버튼 → 유형 선택 → 기간·기초 묶음 또는 정정 대상·사유 입력 → 예상 차감·현재 잔여·실제 결재자 미리보기 → 제출 순서다. 미리보기는 참고이며 제출·승인 시 서버가 다시 검증한다. 계산 미지원 코드는 선택할 수 없다. 연차와 정정의 서로 다른 입력·검증 DTO를 유지한다.

- native `<dialog>`와 외부 JS를 사용한다. 제목·설명·레이블, 최초 초점·키보드 이동·Escape 닫기·닫은 뒤 신청 버튼 초점 복귀를 제공한다. 입력 중 닫기에는 손실 확인을 둔다.
- JS가 없어도 동일 작성 GET의 일반 폼과 기존 POST로 완료할 수 있게 한다. 모달 표시 자체로 신청 데이터를 생성하지 않는다.
- 422는 입력·선택 연도·신청 유형·commandId를 유지하고 모달을 다시 열어 오류 요약/필드로 초점을 이동한다. htmx422 부분 교체를 사용하면 이 폼 범위에만 허용한다.
- 409는 최신 잔여/일정/버전 확인을 안내하고 자동 덮어쓰기·자동 재제출을 하지 않는다.503은 같은 명령의 성공 여부를 확인할 수 있게 유지한다. 인증 만료 시 입력값·사유를 URL에 옮기지 않는다.
- 제출 중 버튼을 잠그고 실패 시 복구한다. 서버의 commandId 멱등성을 최종 보장으로 유지한다. 성공은303으로 선택 연도 현황에 복귀해 생성 건과 상세 링크를 표시한다. 입력 기간이 조회 연도 밖이면 대상 연도로 이동할 수 있는 안내를 제공한다.

## 9. 월간근무현황

기존 `/me/worktime?month=YYYY-MM`과 관리자 `/admin/attendance`의 자료를 재사용하고 대표용 회사 읽기 경로를 추가한다. 흰색·파란 업무 테마와 공통 shell을 유지한다.

배치는 **월 선택·기준 시각 → 요약 카드 → 주간 실근로 그래프 → 일별 표 → 계산 근거 상세**다. 관리자 재집계·Excel 동작은 별도 관리 영역에 둔다. 직원용 카드에 원시 ms·내부 enum·추적 ID를 나열하지 않는다.

| 지표 | 산정·표시 계약 |
| --- | --- |
| 월 소정근무 | 유효 일정과 회사 캘린더로 확인한 해당 월 근무 예정량. 연차일의 원래 소정 일정과 실출근 예정은 구분 |
| 월 실근로 | 확인된 실제 근로의 합. 휴게·휴가 인정시간 제외. 미확정/오래됨이 있으면 부분합 표시 |
| 주 소정·실근로 | 선택 월과 교차하는 모든 주를 표시하고 각 주 전체 범위와 월 내부 분량을 명시. 경계 주를 잘라 주간 합계로 오인시키지 않음 |
| 휴가 | 승인 효력이 있는 DAY·사용/예정. DAY를 임의 시간으로 변환하지 않음 |
| 근무 인정시간 | 실근로와 별도 항목. 검증된 유형별 인정 규칙이 없으면 산정 미지원 |
| 최대/잔여 기준 | 검토된 적용 대상·기간·정책 버전의 상한이 있는 경우만 표시. 회사 참고기준과 법정 판정을 구분 |
| 확인할 항목 | 기록 누락·근로/휴게 미확인·결재 대기·재집계 필요를 분리 |

월 소정근무는 기존 일 결과 `scheduledMillis`의 단순합으로 확정하지 않는다. 휴일·미배정·버전 충돌을 검증하고 해당 기간의 캘린더·일정 근거를 연결한다. 기존 CALC-1 산정값 자체는 이번 화면 설계로 변경하지 않는다.

주 상한에 임의 주 수를 곱해 월 법정 최대시간을 만들지 않는다. 월 최대가 필요하면 해당 사원·월의 근거가 확인된 **회사 관리용 월 참고상한**을 별도로 등록·표시한다. 법정 적합성 판정으로 안내하지 않는다. 주간 기준도 적용 검토·온전한 주·현재 결과가 확인돼야 비교한다. 미확정이 남으면 잔여를 확정하지 않고 확인된 부분합과 기준만 표시한다.

미래 날짜는 `예정`, 당일 미완료는 `진행 중`, 지난 날짜의 미확정은 `확인 필요`로 표현한다. 기존 전체 기간의 미확정 수치와 구분하는 조회 DTO를 두되 null을0으로 바꾸거나 결과를 저장하지 않는다. 최신성이 깨진 결과는 이전 계산값임을 표시하고 현재 확인 합계와 섞지 않는다.

주간 그래프는 CSS 막대와 동등한 텍스트/표를 제공한다. 확정·부분합·미산정·정책 미확인을 색과 문구로 함께 표시한다. 시간은 시·분 중심이며 원본 밀리초는 상세에서 보존한다. 일별 표는 날짜·출퇴근·실근로·휴게·휴가·상태·상세 링크 순서로 구성하고 모바일에서는 요약 행을 먼저 보여준다.

## 10. 스키마·인터페이스 선행 계약

### 10.1 논리 스키마 변경안

아래는 **전체 확장의 논리 모델**이며 적용 완료 목록이 아니다. 대표 역할은 1단계 V11, 조직장 이력은 2단계 V12의 구현 계약으로 구체화했으며 실제 DB 적용 여부는 각 단위 보고서를 따른다. 나머지 신규 논리 대상은 후속이다. 모든 고객사 행은 tenant를 포함한 PK/FK·명시 SQL 조건·FORCE RLS·최소 앱 권한을 적용한다. 생성/변경 주체·시각·사유, 변경 가능한 상태의 version을 포함한다. 새 적용기간은 종료일 제외이며 기존 `leave_bucket.usable_to`의 종료일 포함 의미는 바꾸지 않는다.

| 대상 | 필수 필드·제약 |
| --- | --- |
| 기존 `role_grant` | COMPANY_REPRESENTATIVE 허용 확장. 기존3종 값·active·APPROVER 보존 |
| `organization_head_assignment` | organization_id·employee_id·valid_from/to·superseded_at·version. 조직별 유효 한 명, 중첩 금지, 당일 교체 원본 보존 |
| `approval_route` / `approval_route_version` | code·name·active, route_id·revision·approver_kind=DIRECT_EMPLOYEE/ORGANIZATION_HEAD·employee_id?. 직접 지정일 때만 employee_id 필수. 버전 내용 불변 |

신규 경로는 신청 ID·스냅샷 ID를 미리 생성하고, 스냅샷 참조가 채워진 신청 → 해당 신청의 스냅샷 순으로 같은 트랜잭션에 저장한다. 신청의 `(tenant_id,route_snapshot_id,id)`가 스냅샷의 `(tenant_id,id,request_id)`를 참조하는 FK만 `DEFERRABLE INITIALLY DEFERRED`로 둔다. 반대 방향 request_id FK는 일반 FK다. 같은 회사의 다른 신청 스냅샷도 재사용할 수 없다. 기존 배정 ID/버전은 둘 다 존재하거나 둘 다 NULL이고, 신규 스냅샷과 기존 배정 중 정확히 하나를 허용한다. 기존 NOT NULL 배정 필드를 무조건 비워 신규 경로를 흉내 내지 않는다.

근태유형 버전은7.2의 적용일·revision 선택 규칙으로 한 일자의 유효 버전을 하나로 정하고 기존 버전 내용을 수정하지 않는다. 비활성화·교체 뒤에도 과거 신청의 정책 본문은 보존한다. 귀속연도 분류 정정도 새 revision이며 연차 일수를 추가·차감하는 원장 조정과 분리한다.

기존 적용 migration을 편집하지 않는다. 단위별 후속 Flyway migration 번호를 현재 저장소에서 다시 확인하고, 구조·호환 자료 연결·권한/제약·회귀를 함께 검증한다. 최초 설계 작성에서는 migration 파일을 생성하거나 DB 명령을 실행하지 않았으며 이후 V11·V12 계약과 실제 실행은 각 단위 기록으로 구분한다.

| GET `/me/worktime?month`, GET `/admin/attendance?month&employeeId` | 기존 본인/담당자 월 조회 유지 |
| POST `/admin/work-policies/reference-limits` | 관리자만 사원·기간별 참고상한의 검토 근거와 새 revision 등록 |

회사 현황 목록은 각 사원의 상세 월 계산을 전체 사원 수만큼 직렬 호출하지 않는다. 페이지 대상과 같은 기간을 묶어 읽고, 전체 회사 합계와 현재 페이지 합계의 범위를 구분한다. 조직 필터는 오늘 유효 소속 기준이며 근무일 당시 조직별 집계는 이번 첫 단위에 포함하지 않는다.

관리 POST에는 CSRF·commandId·변경 사유·expectedVersion, 신청 POST에는 기존 종류별 revision/fingerprint를 적용한다. 형식400, 권한403, 타 회사/범위 밖/미존재404, 버전/명령 충돌409, 업무조건422, 과다요청429, 저장소 오류503을 구분한다. 새 경로 추가 시 기존 GET/POST와 정적 경로 우선순위도 검증한다.

### 10.3 조회 DTO의 책임

- `MyProfileView`: 본인 정보와 현재 배정·역할의 안전한 표시값.
- `AnnualAttendanceView`: year·asOf·coverageStatus·유형별 사용/예정/대기·현재 사용 가능·귀속 상태·페이지 목록. 연도 귀속량과 현재 재고를 서로 다른 필드로 둔다.
- `RequestComposeView`: 종류별 폼·선택 유형 버전·잔여 묶음·예상량·현재 해석 결재자·오류. 미리보기 결과를 권한 증거로 신뢰하지 않는다.
- `MonthlyAttendanceView`: month·asOf·본인/회사 범위·소정·최신 확인 실근로·이전 결과·미래/진행/미확정 구분·주간 범위·휴가·검토된 참고상한.
- `BulkChangeForm/Result`: 제한된 행별 입력과 결과 ID·버전 매핑. arbitrary entity/필드 이름으로 DB 열을 수정하는 범용 편집 API는 만들지 않는다.

## 11. 구현 순서와 수용 기준

각 단위는 스키마/DTO/HTTP 계약 확정 → 실패 테스트 작성·실패 확인 → 최소 구현 → 회귀·브라우저/DB 검증 → 문서·커밋 순서로 진행한다. 이 절은 개발 순서·수용 기준이며 실행 가능한 작업별 구현 계획은 개발 착수 시 별도로 작성한다. 최초 설계 작성 당시 아래 테스트를 실행한 것은 아니며 실제 수행 결과는 각 단위 보고서를 따른다.

1단계 실제 결과는 [당시 보고서](../../quality/identity-access.md), 2단계 실행 순서·검증 대상은 [조직 시트 계획](../plans/2026-10-27-react-org-sheet.md)을 따른다. 2단계의 통과·실패·미실시 범위와 로컬 V12 반영 여부는 [별도 보고서](../../quality/org-sheet-heads.md)에 실제 결과로 기록하며 위 수용 목록만으로 완료를 선언하지 않는다.

| 단위 | 먼저 검증할 수용 사례 |
| --- | --- |
| 1. 권한·메뉴·내 정보 | 대표 설정 POST403·공통 타인조회404·위조 tenant 차단·조회 중 역할 회수·풀 컨텍스트 재사용·본인 정보만 제공 |

## 12. 서비스 오픈 판단과 이번 문서 검증

이 설계의 구현 완료와 공개 서비스 오픈은 별도 판단이다. 현재 [Phase 6 보고서](../../quality/phase6-report.md), [보안 후속](../../quality/security-runtime-recheck.md), [최신 변경 검증](../../development/local.md)의 실제 수행 범위를 유지한다. 이전 이미지의 전체 회귀·취약점·지속 부하를 현재 또는 미래 이미지의 동일 검증으로 기록하지 않는다.

| 공개 전 조건 | 완료 증거 |
| --- | --- |
| 제품·계산 | 지원 근무/근태 유형 명시, 위 단위별 회귀·격리·동시성·실제 PC/모바일 업무 수용 |
| 고객사 정책·법 적용 | 실제 대상·시행일·근무제·휴가/기초 잔여·상한 근거를 공식 자료로 검증. 이 문서에는 신규 법정 수치를 확정하지 않음 |
| 계정 전달 | 실제 초대·복구 메일의 배송·만료·재발급·실패·abuse 대응 검증 |
| 운영·보안 | 운영 HTTPS/프록시·방화벽·비밀 회전·관측/알림·권한 검토, 배포 대상 이미지의 잔여 보안 항목 판단·검사 |
| 복구·개인정보 | 서버 유실을 포함한 별도 환경 복구·백업 보존/접근, 개인정보 고지·처리 근거·리전·보존/파기 정책 검토 |
| 파일럿·배포 | 운영 사양 부하/장애·사용자 파일럿의 미해결 항목과 수용 결과, 별도 외부 접속/배포 승인 |

실제 메일·고객 자료·외부 서버 접속·배포는 이번 작업에 포함하지 않는다. 새 법령·공급자 취약점 상태·라이브러리 지원 버전을 외부에서 재조회한 결과도 아니다. 새 의존성·전역 도구·환경 설정은 추가하지 않는다.

최초 설계 문서 작성 단위는 기존 코드/명세와의 대조, 상대 링크 대상 존재, Markdown 구조, 정책·용어 일관성, `git diff --check`와 변경 범위를 검증했고 Java/Python 테스트·실제 브라우저·DB·컨테이너 검증은 실행하지 않았다. 이후 구현·검증·커밋·Push 결과는 상단의 단위별 보고서에서 확인하며 과거 문서 검증을 현재 코드 검증으로 확대하지 않는다.
