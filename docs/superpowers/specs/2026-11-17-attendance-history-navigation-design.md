## 2. 직원 출퇴근 기간 조회

### 화면과 동선

- `내 업무 > 근태관리 > 출퇴근 기록`은 오늘의 기록과 근무 확인을 여는 기존 `/me/attendance`로 연결한다. 홈 위젯과 모바일의 출근·퇴근 버튼은 기존 명령·중복 차단·저장 후 복귀 동작을 사용한다. 지난 날짜 상세와 기간 목록에는 출근·퇴근 버튼을 두지 않는다.
- 출퇴근 화면의 `기간 조회` 링크로 기간 화면을 연다. 첫 진입에는 서울 기준 오늘까지의 최근 3개월을 채우고 조회한다. 시작일·종료일을 편집해 과거의 임의 구간을 조회할 수 있다. `이번 달`은 이달 1일~오늘, `지난달`은 지난달 1일~말일을 바로 조회한다. `출퇴근 누락만`은 해당 기간의 누락 건을 찾아 주며 `오늘 기록` 링크는 오늘 상세를 연다.
- 기간 목록은 종료일부터 역순으로 날짜별 한 행을 보여 준다. 근무일과 예정 근무 또는 휴일·비근무일·일정 미배정, 출근·퇴근, 기록 상태, 실근로를 한눈에 확인한다. 날짜 링크로 기존 하루 상세를 연다. 브라우저에서 뒤로 가면 기간과 결과가 복원되도록 검색 조건은 URL에 남긴다.
- 하루 상세는 원천 출퇴근과 승인 정정 반영 기록을 구분하고, 서버가 허용한 날에 기존 근무 확인을 제공한다. 정정 안내가 있는 날에는 `/me/requests/correction?date=YYYY-MM-DD`로 바로 이동한다. 근무 일정 등에서 사용 중인 `/me/requests/new?year=YYYY&kind=ATTENDANCE_CORRECTION&date=YYYY-MM-DD`도 날짜가 채워진 진입으로 유지한다.
- 목록은 작은 화면에서 날짜·출근·퇴근·상태 순으로 읽을 수 있도록 쌓고 각 값의 제목을 표시한다. 날짜 입력, `조회`, 날짜 상세 및 정정 링크는 키보드로 접근할 수 있게 한다. 오류 메시지는 해당 입력과 연결하고 초점을 오류 입력으로 옮긴다.

### 날짜와 HTTP 계약

| 요청 | 동작 |
| --- | --- |
| `GET /me/attendance` | 서울 기준 오늘의 기존 상세. |
| `GET /me/attendance?date=YYYY-MM-DD` | 기존 단일 일자 상세. 기간 기본값과 관계없이 기존 달력·확인 완료·이력 딥링크를 받아들인다. |
| `GET /me/attendance?view=period` | 서버가 현재 서울 날짜를 한 번 계산한다. `to = today`, `from = to.plusDays(1).minusMonths(3)`로 채운 기간 목록을 반환한다. |
| `GET /me/attendance?view=period&from=YYYY-MM-DD&to=YYYY-MM-DD` | 날짜 형식과 기간을 검증한 뒤 본인의 목록을 반환한다. 기존 HTML 진입과 `Accept: application/vnd.worklog.page+json` 응답을 모두 지원한다. |
| `GET /me/attendance?view=period&from=YYYY-MM-DD&to=YYYY-MM-DD&missingOnly=true` | 유효 기록에 대해 서버가 `MISSING`으로 판단한 행만 반환한다. 필터를 해제하면 `missingOnly`를 생략한다. |

- 시작일·종료일 양끝을 포함한다. `from <= to <= today`이며 `from >= to.plusDays(1).minusMonths(3)`이어야 한다. 마지막 날짜 바로 다음날을 기준으로 역산한 달력 3개월이며, 대상 월에 같은 날짜가 없으면 `LocalDate.minusMonths` 규칙에 따라 말일을 사용한다. 기간 유효성은 조회 대상 기간의 폭으로 정하며 과거 조회 시점에 하한을 두지 않는다.
- `today=2026-11-17`이면 기본 기간은 `2026-08-18`~`2026-11-17`이다. `2024-02-29`~`2024-05-30`은 유효하고, 동일 종료일에 시작일 `2024-02-28`은 범위 초과다. 시작일과 종료일이 같은 하루도 유효하다.
- 빠른 선택은 서버가 제공한 `today`로 계산한 날짜 쌍을 `from`·`to`에 적용해 조회하고, 선택한 누락 필터 값을 URL에 유지한다. `2026-11-17`의 이번 달은 `2026-11-01`~`2026-11-17`, 지난달은 `2026-10-01`~`2026-10-31`이다.
- 날짜 형식 오류, 알 수 없는 `view`, `true` 이외의 `missingOnly`, 기간 모드에서 한쪽 날짜만 존재하거나 `date`를 섞은 요청, 기간 모드 없이 기간 전용 인자를 보낸 요청은 400이다. 날짜 형식이 맞고 역순·미래 종료일·최대 범위 초과인 경우 422로 입력값과 사유를 표시한다. 오류 시 기간을 자동 보정하거나 부분 결과를 보여 주지 않는다. 로그인 요구와 현재 계정 재검증은 기존 HTML·페이지 JSON 응답 계약을 따른다.
- 신규 기간 페이지 모델에는 `today`, `from`, `to`, `missingOnly`, `rows`를 포함한다. 행은 `workDate`, 일정 구분·표시용 근무 시각, 유효 출근·퇴근 표시 시각, 기록·정정·계산 상태, 현재 `actualWorkMillis` 또는 `null`로 구성한다. 중복 또는 순서 오류로 한 쌍을 확정할 수 없으면 시각을 임의 선택하지 않는다. 시각은 화면에 초 단위로 표시하고 원천과 계산의 밀리초 정본은 기존 상세·계산 흐름에서 사용한다.
- 기간 GET은 `TnaPrincipal`의 회사·사원만 읽는다. 기간 계약에 사번·사원 ID·테넌트 ID를 두지 않는다. 기존 계정·현재 권한 확인, 테넌트 조건과 RLS를 적용하며 쓰기 명령·자동 집계·감사 명령·예정 휴게 확인을 실행하지 않는다. 날짜별 유효 기록·확인 전·결과 최신성 판단을 재사용하는 전용 읽기에 3개월 범위 검증을 둔다. 기존 `WorktimeService.range`의 31일 조회·재집계·Excel 제한을 각 경로에서 계속 적용한다. 행마다 페이지나 계산 GET을 다시 호출하지 않는다. 기존 스키마를 사용한다.

### 날짜별 상태 기준

| 입력·현재 상태 | 목록과 하루 상세의 의미 |
| --- | --- |
| 정상 원천 쌍 또는 승인된 유효 쌍 | 목록은 현재 반영 시각을 보여 주고 정정 반영 여부를 표시한다. 하루 상세에서 원천과 승인 반영 기록을 비교할 수 있다. |
| 입사 전·퇴사 후 | `재직 기간 외`로 표시하고 기간 목록의 근무·정정·누락 판단에서 제외한다. 기존 하루 상세에서 보이는 원천은 보존한다. |
| 일정 미배정 또는 캘린더 미확인 | 각각의 상태를 보여 준다. 근무일·휴일·실근로 값을 추정하지 않는다. |
| 확정 휴일·비근무일·승인 휴가일에 기록 없음 | 해당 날짜 구분을 보여 준다. 출퇴근 누락 경고 또는 정정 유도를 붙이지 않는다. 현재 계산 결과가 있는 경우에만 그 결과를 표시한다. |
| 오늘 근무 중이거나 근무일에 출퇴근 누락·중복·순서 오류 | 오늘 유효 출근 1건과 퇴근 0건의 정상 진행 상태는 `근무 중`으로 표시한다. 오늘 기록이 아직 없으면 `기록 없음`으로 표시한다. 퇴근만 한 건인 경우, 중복, 순서 오류는 오늘이어도 `확인 필요`로 보인다. 지난 근무일 누락과 비정상 기록도 `확인 필요`로 표시한다. 정정 제안은 기존 `correctionSuggested` 서버 판정을 재사용한다. |
| 대기 정정 | `정정 대기`로 표시한다. 대기 제출값은 유효 시각에 반영하지 않는다. 승인 휴가일·재직 외·정정 대기·일정 미배정·캘린더 미확인에는 기존 판정에 따라 정정 유도를 숨긴다. |
| 근무 확인 또는 계산 결과 없음·오래됨 | 현재 실근로가 없으면 `-`를 표시한다. 서버가 판정한 날짜에만 `확인 전`을 표시한다. 오래된 값이나 미확정 값을 0시간으로 표시하지 않는다. 담당자 재집계나 기존 근무 확인 후 계산으로 새 결과가 생기면 새로 조회할 때 표시한다. |

`MISSING`은 재직 중이고 일정·캘린더가 확인된 근무일에서 과거에 출퇴근 양쪽 또는 한쪽이 없거나, 오늘 퇴근 기록 한 건만 있어 출근이 누락된 경우다. 승인 휴가일·휴일·비근무일·정정 대기, 오늘 정상 진행 중, 중복·순서 오류, 일정·캘린더 불명은 `출퇴근 누락만`에서 제외한다. 계산 미확정만으로는 누락으로 판단하지 않는다.

## 3. 업무별 메뉴와 신청 목록

| 역할과 업무 | 메뉴·현재 경로 |
| --- | --- |
| 직원 · 인사정보 | `내 업무 > 인사정보 > 내 정보`는 `/me/profile`. 담당자의 별도 인사기본 경로는 인사기본 명세에 따라 연결한다. |
| 직원 · 근태관리 | `출퇴근 기록` `/me/attendance`, `근무 일정` `/me/schedule`, `근로시간` `/me/worktime`, `출퇴근 정정 신청` `/me/requests/correction`. |
| 직원 · 휴가·신청 이력 | `휴가 신청`은 기존 작성 경로 `/me/requests/new?kind=LEAVE_DAY`로 연결한다. `/me/requests`는 `내 신청 이력`으로 표시하고 연차·정정·취소가 함께 있는 본인 연도별 조회와 기존 재신청·대리 작성 이력은 이 경로로 찾는다. |
| 담당자 · 인사·조직 | `인사관리 > 인사기본` `/admin/employees`를 둔다. `조직관리`의 조직 `/admin/organizations`, 조직장 배정 `/admin/organization-heads`, 조직도 `/company/organizations`를 사용한다. [인사기본 및 입사 화면 계약](2026-11-17-personnel-onboarding-design.md) |
| 담당자 · 근태관리 | `회사 근무현황` `/company/attendance`는 사원별 월간 읽기, `출퇴근 정정 현황` `/admin/requests?scope=CORRECTION`은 처리용, `근태 집계·Excel` `/admin/attendance`는 검토·재집계용으로 배치한다. `근무 설정`, `근무일·휴일`, `근태코드 관리`, `계산 정책`은 근태관리의 기준 설정에 둔다. |
| 담당자 · 휴가관리 | `휴가 신청 현황` `/admin/requests?scope=LEAVE`와 `연차 관리` `/admin/leave-balances`를 둔다. |
| 담당자 · 시스템 설정 | `권한 관리` `/admin/access`, `공통코드 관리` `/admin/common-codes`, 결재선 정의·배정, 허용 네트워크와 변경 이력을 기존 경로에 연결한다. |
| 대표 · 회사 읽기 | `조직관리 > 조직도` `/company/organizations`, `근태관리 > 회사 근무현황` `/company/attendance`와 `회사 정정 현황` `/company/requests?scope=CORRECTION`, `휴가관리 > 회사 휴가 신청 현황` `/company/requests?scope=LEAVE`로 연결한다. 같은 회사 읽기를 제공하며 담당자 처리 링크·설정 동작은 표시하지 않는다. |
| 승인자 · 결재 | 기존 `결재 대기` `/approvals`, `내가 처리한 결재` `/approvals/completed`를 사용한다. 지정 업무 범위에서만 결정 권한을 가진다. |

- 관리 목록과 회사 읽기 목록의 기존 SQL에 `scope` 서버 조건을 적용한다. `CORRECTION`은 `ATTENDANCE_CORRECTION`, `LEAVE`는 `LEAVE_DAY`와 `CANCEL_LEAVE`다. 회사 조회는 유형 조건을 정렬·페이지 제한 전에 적용하며 기존 연도·조직·상태 필터와 현재 소속 기준을 유지한다. 미지원 `scope`는 400이다. `scope` 없는 `/admin/requests`, `/company/requests`는 기존 혼합 읽기 링크의 호환 경로다. `휴가관리 > 전체 신청` 메뉴 노출을 정리한다.
- 담당자는 유형별 목록에서 원래 신청 상세, 예외 정정 및 재배정 동선을 사용한다. 관리자만 접근하는 관리 목록 및 쓰기 경로의 권한, 대리 정정의 독립 승인 규칙, 대표의 GET 제한을 기존대로 적용한다. 기존 예외 정정·재배정과 무범위 링크를 새 메뉴 URL로 일괄 리다이렉트하지 않는다.
- 직원 `/me/requests`의 `QUERY` 허용 목록은 `year`, `typeId`, `status`, `page`, `authoredPage`, `createdId`다. 작성 `CONTEXT`는 `year`, `typeId`, `status`, `page`, `authoredPage`, `mode`, `kind`, `_csrf`와 기존 단계별 입력 허용 목록을 계속 사용한다. `kind=LEAVE_DAY`는 공통 작성기의 유형을 미리 고른다. 작성 딥링크의 `date`, `predecessorRequestId`, 미리보기, 작성 후 `303 /me/requests?year=…&createdId=…`, 접수 상세와 돌아가기를 유지한다. 전용 정정 폼의 기존 저장 후 상세 이동도 유지한다. `scope`는 관리자·회사 목록에서만 받는다.
- 등록된 직원·담당자·대표·승인자 간 역할 전환을 유지한다. 메뉴는 해당 역할이 열 수 있는 하위 항목만 노출하고 빈 그룹은 숨긴다. 링크의 서버 권한이 최종 결정이다. 모바일 메뉴, 현재 메뉴 강조와 탐색 경로는 `scope`가 있는 링크를 각각 식별하고, 상세의 승인자·관리자·본인 진입 문맥을 실제 허용된 경로 안에서 보존한다.

## 4. 수용 시나리오

| 시나리오 | 합격 기준 |
| --- | --- |
| 서울 자정과 날짜 유효성 | `view=period` 기본값을 서울 자정 이후 새 날짜로 다시 계산한다. 월말·윤년·연말, 하루, 정확히 3개월, 하루 초과, 역순, 미래, 날짜 형식·누락 오류를 서버와 UI에서 검증한다. 오늘 이후 일정 상세의 기존 `date` 딥링크도 열린다. |
| 지난 기간 접근과 상세 | 3개월보다 오래된 기간도 구간 폭이 허용되면 조회된다. 기간 목록에서 날짜를 선택하면 현재 유효 시각과 원천을 하루 상세에서 확인하고 브라우저 뒤로 기간이 복원된다. |
| 빠른 선택과 누락 필터 | 이번 달·지난달은 위 기간의 날짜를 표시하고 URL로 재현된다. 누락 필터는 해당 기간의 `MISSING`만 반환한다. 오늘 정상 진행·휴가·비근무·대기 정정·중복·순서 오류가 제외되고 누락 행의 상세 링크가 작동한다. |
| 오늘 업무 회귀 | 직원이 홈과 오늘 화면에서 기존 명령으로 출퇴근하고 정상 퇴근 뒤 근무 확인과 결과 표시를 확인한다. 오늘 퇴근 전에는 누락으로 판단하지 않는다. 과거 상세의 근무 확인·정정 조건과 날짜 인계를 유지한다. |
| 불확정과 승인 상태 | 미배정·캘린더 미확인·기록 누락·중복·승인 휴가·대기 정정·승인 반영·오래된 결과를 표본으로 검증한다. 기간 GET 전후 원천·확인·재집계·감사 명령 자료가 동일하다. |
| 유형·역할·격리 | 각 `scope`에는 해당 유형만 나타나고, 무범위 기존 링크와 상세·예외·재배정이 열린다. 대표는 같은 회사의 허용 GET만 열고, 담당자 쓰기와 다른 회사·사원 조회는 기존 서버 권한에서 차단된다. 조작된 대상 ID로 본인 기간 자료의 범위를 바꿀 수 없다. |
| 메뉴와 모바일 | 네 역할 및 겸임 계정에서 본인 메뉴, 전환 후 메뉴, 빈 그룹 숨김과 상세 탐색 경로를 확인한다. 390px에서 날짜 입력·조회·날짜 링크·키보드 초점을 확인하고 PC에서 같은 시나리오를 수행한다. |
