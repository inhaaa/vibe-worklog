# 고객사 개통과 직원 첫 출근 검증

2026-11-21 서울 기준. 운영자가 새 회사를 개설하고, 담당자와 직원이 초대 메일로 들어와 첫 출근을 마치는 경로를 로컬 합성 자료로 확인했다. [인수 기준](../superpowers/plans/2026-11-21-customer-onboarding.md) · [재현 명령](../development/local.md#새-회사에서-첫-출근을-검증하는-방법)

## 검증 환경

- 전용 PostgreSQL에 새 스키마와 운영자 한 명을 준비했다. PC와 모바일에는 다른 회사와 이메일 주소를 사용했다. 회사, 근무 기준, 근무일, 허용망, 소속·근무 배정, 직원·결재자, 사용자 계정과 결재선은 업무 화면에서 등록했다.
- 로컬 Mailpit의 SMTP 서버에서 메일을 받았다. 수신 주소·건수를 대조하고 웹 메일함에서 회사 코드, 입력 화면 주소, 일회용 코드와 만료 시각을 확인했다. 운영자·담당자·결재자·직원은 독립 브라우저 세션을 사용했다.

## 새 회사 두 곳의 첫 출근

Chrome 157.0.8103.52에서 PC와 모바일 화면에 서로 다른 가상 회사를 개설했다. 모바일은 390×844 터치 에뮬레이션으로 조작했고 양식 제출에는 키보드도 사용했다. 각 회사의 담당자·결재자·직원은 해당 회사의 테스트 메일함에서 받은 코드로 초대를 수락했다.

| 실제 사용 흐름 | PC 1440×900 | 모바일 390×844 |
| --- | --- | --- |
| 첫 담당자 활성화 | 초대 수락 전 로그인 거부, 수락 후 회사 초기 설정 진입 | 동일 |
| 근무 기준 설정과 배정 | 09:30~18:30 근무, 12:30~13:30 휴게. 근무일과 출퇴근 허용망을 저장하고 직원 홈에서 배정 시간 확인 | 09:00~18:00 근무, 12:00~13:00 휴게. 같은 순서로 확인 |
| 결재선 설정 | 결재자 입사·초대·권한 부여 후 `A01` 출퇴근 정정 신청서에 `R01` 연결. 직원 사번으로 미리 보자 지정한 결재자 표시 | 동일 |
| 직원 초대 재발급과 첫 출근 | 기존 초대 코드 거부, 새 코드로 활성화. 회사코드·이메일로 로그인하고 출근 버튼을 한 번 클릭해 한 건 저장 | 새 코드로 활성화한 뒤 출근 버튼을 한 번 터치해 한 건 저장 |
| 비밀번호 복구 | 복구 후 이전 세션은 로그인 화면으로 이동하고 이전 비밀번호는 거부됨. 사번·새 비밀번호로 로그인해 초 단위까지 같은 출근 시각 확인 | 동일 |
| 수신 메일 | 최초 담당자 1통, 결재자 1통, 직원 초대·재발급·복구 3통 | 같은 구성으로 5통 |

두 환경 모두 담당자 홈, 직원별 결재선 미리보기, 출근 직후, 복구 후 재로그인 화면에서 가로 넘침을 검사했다. 브라우저 실행 중 페이지 오류는 0건이었다. 메일에 표시된 만료 시각은 서울 기준으로 초대 발급 후 24시간, 복구 요청 후 30분이었다. [브라우저 시나리오](../../scripts/verify-customer-opening-browser.cjs) · [독립 검증 환경](../../src/test/java/kr/tna/CustomerOpeningBrowser.java)

별도의 모바일 회사에서도 첫 출근 버튼을 한 번 터치했다. 브라우저가 `touchstart`, `touchend`, `click`을 한 번씩 전달했고 출근 요청은 한 건이었다. 서버는 HTTP 303으로 응답했다. 비밀번호를 복구하고 다시 조회한 시각은 첫 출근 때와 같은 `18:35:01`이었다.

## 개통 환경과 회귀

- 개통용 Compose는 일반 회사코드 로그인과 전용 메일함을 함께 연다. 세 Compose 파일을 결합한 설정에서 DB 볼륨과 포트가 기존 로컬 데모와 분리되는지 검증했다. 전용 로컬 이미지에 개발 JAR를 적용한 구성에서도 운영자 로그인·신규 회사·메일 수신·초대 수락·회사코드와 사번 로그인을 확인했다.
- 하나의 결재선을 저장한 직후 미저장으로 표시되는 문제를 재현했다. 종료 단위가 비어 있는 지정 사원 결재선을 다시 읽을 때 변경 건수는 0이고 저장 버튼은 비활성이다. 실제로 이름을 다시 수정하면 1건으로 바뀐다.
- 초대 메일 전달이 실패한 경우 등록된 최초 담당자·직원 계정이 보존되고 같은 주소로 재발급할 수 있는지 검증했다. 브라우저에서는 테스트 메일함에 도착한 메일을 열었다. 비밀번호 복구는 계정 존재 여부와 관계없이 같은 안내를 반환했다.
