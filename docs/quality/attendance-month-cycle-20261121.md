# 일상 근태와 월 마감 검증

2026-11-21에 로컬 가상 회사의 2026년 9월 근태를 마감했다. 업무 시계는 서울 기준 9월 30일 신청과 10월 1일 마감을 차례로 재현했다. 마감 이력에는 실제 DB 처리 시각이 기록됐다. [인수 기준](../superpowers/plans/2026-11-21-attendance-month-cycle.md) · [재현 방법](../development/local.md#정정과-휴가-승인부터-월-마감까지-검증하는-방법)

## 담당자·직원·결재자 흐름

1. 담당자가 9월 29일 연구개발팀 C101의 원천 출근 09:00과 퇴근 누락을 확인하고 보완을 요청했다. 직원은 보완함에서 유효 퇴근 17:30과 실제 휴게 12:00~13:00을 제출했다. 같은 직원이 9월 30일 종일 유급 경조휴가도 신청했다.
2. 신청 상세에서 원천 퇴근 ‘미기록’과 제안 퇴근 ‘17:30’을 구분해 확인했다. 두 신청이 남은 채 다음 달로 이동하자 마감이 차단됐다. 담당자 역할을 겸한 독립 결재자가 결재함에서 정정을 승인하고, 이어서 회사 휴가를 승인했다.
3. 담당자가 남은 사원·근무일 두 건을 선택해 재집계했다. 보완 요청이 해소되고 회사 전체 재점검 값이 0이 되자 9월을 처음으로 마감했다. 신청자의 마감 전후 일별·월별 근무 결과가 같았다.

| 마감 점검 | 두 신청 대기 | 정정 승인 | 휴가 승인 | 재집계 후 |
| --- | ---: | ---: | ---: | ---: |
| 확인할 사원·근무일 | 3 | 3 | 2 | 0 |
| 정정 결재 대기 | 1 | 0 | 0 | 0 |
| 결재 대기 신청 | 2 | 1 | 0 | 0 |

## 직원 화면과 마감 파일

C101은 29일 실근로 450분, 30일 실근로 0분과 유급휴가 인정 480분을 확인했다. 고객지원팀 C202의 30일 실근로는 실제 휴게 30분을 반영해 240분, 같은 부서 C900의 휴무일은 0분이었다. 세 계정으로 본인 월 요약과 재직일 4행을 읽어 파일의 사원 명세와 대조했다.

Chrome 157.0.8103.52의 PC 1440×900, 모바일 터치 에뮬레이션 390×844에서 동일한 합성 회사·사원·근무일을 독립 DB에 준비하고 각각 8단계를 끝까지 실행했다. 두 실행 각각에서 회사 전체와 두 부서의 파일을 받고, 반대 화면 크기로 같은 DB·마감 v1에 다시 로그인해 세 파일을 받았다. 실제 파일 12개의 숫자 셀, 직원별 행, 부서·회사 합계와 마감 범위가 일치했다. 같은 마감본끼리 비교한 6쌍은 SHA-256도 일치했다. 기기별로 캡처한 7개 화면에서 페이지 오류와 문서 가로 넘침은 없었다. 모바일 일별 표는 내부 가로 스크롤을 사용한다. ## 보존과 회귀

V36은 마감한 달의 유급휴가 인정시간을 기존 근로시간 계산기에서 받아 근무일 당시 소속으로 고정한다. 도입 전 마감은 기존 파일의 열 순서와 값을 유지한다. 재개 후 재마감하면 그 버전의 새 열에 숫자를 제공한다.

- 전용 PostgreSQL에서 V35의 자료와 기존 열 권한을 대조하고 V36을 적용했다. 예전 마감에 유급시간을 소급해서 채운 행은 0개였고 두 번째 실행에서 적용한 마이그레이션도 0개였다.
- 별도 일 결과가 없는 고정 근무 종일휴가는 부서 이동 전 0시간, 이동 당일의 새 부서에 7.5시간으로 집계됐다. 마감 후 합성 근무 기준을 바꿔도 파일 바이트가 같았다. 선택근무는 표준 421분을 그대로 인정했다.
- 검산기 회귀 10개에서 반일·무급휴가, 부서 이동자의 중복 인원, 숫자 대신 들어간 문자열, 누락·중복 명세, 실제 근로와 유급시간 혼입, 다른 마감본이 섞인 다운로드를 검사했다. [파일 검산 테스트](../../scripts/test_verify_month_cycle_workbooks.py)
- 최종 Maven 검증에서 단위 테스트 254개와 전용 PostgreSQL을 포함한 통합 테스트 843개가 통과했다. 실패·오류·건너뜀은 0개였다. 프런트엔드 테스트 62개 파일의 717개 사례와 TypeScript 검사·Vite 빌드, Python 검증 도구 테스트 107개도 통과했다.
