# 월말 퇴근 누락 보완 요청 검증

[업무 명세](../superpowers/specs/2026-11-18-month-end-correction-followups.md) · [구현 계획](../superpowers/plans/2026-11-18-month-end-correction-followups.md)

## 담당자·직원·결재자 흐름

전용 로컬 PostgreSQL의 서로 다른 가상 사원으로 PC Chrome(1440×900)과 모바일 터치 에뮬레이션(390×844)을 조작했다. 각 사원에게 09시 출근 원천 한 건이 있고 퇴근 기록은 없었다.

| 조작 | 두 화면에서 확인한 결과 |
| --- | --- |
| 담당자가 회사 근무현황의 월말 확인 대상에서 사유를 입력하고 보완 요청 | 같은 월·조회 조건·페이지에 돌아와 직원 확인 대기를 확인했다. 같은 근무일에 추가 요청을 보낼 수 없었다. |
| 직원이 홈과 내 근태 보완 요청에서 사유를 확인하고 해당일 정정 신청 | 본인 날짜로 정정 화면이 열렸다. 직원이 18시 퇴근과 실제 휴게 1시간을 제출했다. |
| 팀장 승인 후 직원과 담당자가 다시 조회 | 정정 결재 대기가 유지됐다. |
| 실장 최종 승인 후 재조회 | 승인된 정정 상세와 재집계 대기가 표시됐다. |
| 담당자가 해당일 재집계 후 같은 월말 목록으로 복귀 | 실근로 8시간·휴게 1시간을 확인했다. 대상일이 월말 목록에서 사라졌고 직원 홈과 미해소 목록에서도 해소됐다. |

각 사원의 저장 결과를 조회해 보완 1건, 정정 1건, 승인 단계 2건을 확인했다. 보완 요청의 해소 결과 ID는 해당 사원의 일 결과와 일치했다. 원천 기록은 각 사원의 최초 출근 1건으로 검증 전후 체크섬도 같았다.

## 0시간과 미확정 시간의 구분

가상 사원이 잘못 찍은 출근 1건에 대해 정정을 신청해 그 기록의 효력을 해제했다. 정정 최종 승인 후 종일휴가 또는 확정 휴무 근거가 있을 때만 재집계 대기로 바뀌고, 재집계한 실근로 0시간 결과로 해소됐다. 근무일에 반차만 사용했거나 근거가 없을 때는 재집계 후에도 미해소 상태를 유지했다. 각 경우 원천 출근 1건은 그대로 남았다.

## 화면과 접근 권한

홈은 미해소 요청 3건까지 표시하고 전체 목록은 20건씩 조회한다. HTTP 테스트에서 조회 파라미터로 다른 사원을 지정해도 로그인한 직원의 요청만 반환했다. PostgreSQL에서 같은 명령의 재전송과 동시 요청, 다른 테넌트 접근 차단, 활성 요청 유일성과 V28에서 V29로 전환할 때의 기존 자료 보존을 검증했다.

## 정정을 다시 신청한 경우

18시 퇴근 정정 A가 승인된 뒤 같은 날짜에 19시 대체 정정 B를 제출했다. PostgreSQL 통합 테스트에서 B가 대기 중일 때는 두 화면에서 B를 열었다. B를 반려·철회하고 나면 직원과 담당자의 상세는 실제 근무에 쓰이는 A를 열었다. 근무 확인이 필요한 경우와 재집계 대기인 경우를 각각 검증했다. 실근로 8시간으로 해소된 요청에는 A와 일 결과가 연결됐고, B의 반려·철회 이력도 보존됐다.

직원의 실제 휴게가 예정과 다른 경우를 위해 홈과 전체 목록의 ‘근무 확인 필요’ 행에서 같은 날짜의 근무 확인과 정정 신청을 모두 열 수 있는지 화면 테스트로 확인했다.

## 월말 조회 성능

전용 로컬 DB에 사원 300명, 31일간 9,300 사원일과 원천 출퇴근 18,600건을 준비했다. 전체 사유 첫 페이지의 50행은 238ms, 101번째 페이지는 두 차례 각각 2,044ms와 891ms였다. 사유별 첫 페이지는 24~96ms였다. 조직과 사번 필터를 비운 이 측정에서 월말 목록용 MyBatis 조회는 결과가 있는 페이지에서 조직·날짜 후보·보완 요청을 각 1회씩 호출했고, 빈 페이지에서는 조직과 날짜 후보만 조회했다.

## 최종 브라우저 검증

2026-11-18~19 로컬 Chrome에서 검증했다. 정상 보완 흐름을 확인한 뒤 새 가상 사원 두 명에게 18시 승인 후 19시 대체 정정까지 진행했다. PC에서는 팀장이 19시 신청을 반려했고 모바일에서는 직원이 철회했다. 두 기기에서 직원 홈·전체 목록·담당자 월말의 정정 상세가 모두 승인된 18시를 열었다. 재집계 후에도 09시 출근 원천은 그대로였고, 사원마다 실근로 8시간·휴게 1시간의 일 결과와 18시 승인 건이 해소 기록에 연결됐다.

최종 실행에서 PC와 모바일 각각 8개 업무 단계와 17개 화면을 확인했다. 최종 화면 오류와 가로 넘침은 모두 0건이었다. PC에서 반려 직후 테스트 도구가 화면 이동을 기다리다 시간이 초과되어, 저장된 반려 건을 직원·담당자별 새 Chrome 세션에서 다시 열어 후속 단계를 검증했다. 모바일 검증에는 390×844 터치 에뮬레이션을 사용했다.

브라우저 검증 JAR의 SHA-256은 `2f92d4340bc0c18b8835a5412595225a470fe1999b5a7251b6ea871f6d66659d`이다. V29 마이그레이션과 프런트 빌드 파일 101개를 대조했다. 독립 빌드와 작업 폴더에서 다시 패키징한 JAR에 든 파일 854개의 내용도 모두 일치했다. 공개 데모 배포는 보류했다.

## 자동 테스트 결과

최종 소스에서 Maven 전체 검증을 실행해 Java 단위 199건과 PostgreSQL을 포함한 통합 774건이 통과했다. 실패·오류·건너뜀은 0건이었다. React는 57개 파일의 테스트 642건이 전부 통과했고 TypeScript 검사와 Vite 빌드도 성공했다. 브라우저 검증용 전용 앱과 DB는 종료했다.
