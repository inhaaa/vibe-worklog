# 회사 근태 월 마감·재개 검증

## 담당자 점검과 기록 보존

| 상황 | 전용 PostgreSQL에서 확인한 결과 |
| --- | --- |
| 조회 조건이나 페이지에서 확인 대상이 보이지 않음 | 회사 전체의 사원·근무일 62건을 점검했다. 월 경계에 걸친 대기 연차와 미해소 보완도 마감 직전에 다시 검사했다. |
| 두 담당자가 동시에 같은 월을 마감 | 새 버전은 한 건만 저장됐다. 기존 명령의 재전송은 당시의 이름·사유·처리 시각을 반환했다. 같은 명령으로 다른 사유를 제출하면 409를 반환했다. |
| 마감한 과거 날짜와 열린 다음 달이 같은 주 | 윤년 2월을 마감하고 3월을 재집계해도 2월 일 결과 ID가 유지됐다. 열린 3월의 본인 근무 확인·개인 재집계·일괄 재집계와 서울 당일 출근을 확인했다. |
| 마감 후 미래 퇴직일과 이름 변경 | 기존 8시간 일 결과와 근거 상세를 조회할 수 있었다. 일 결과가 없는 정상 휴무일은 조회와 검토용 Excel에서 근거 있는 0시간으로 표시됐다. 마감월의 재직일을 바꾸는 변경은 일괄관리에서도 전체 롤백됐다. |
| 신청 후 퇴사 | 지정 결재자의 대기함·상세에서 일반 승인은 422로 거절됐다. 독립 결재자가 사유를 남겨 반려하자 대기 신청이 1건에서 0건으로 줄고 마감이 가능해졌다. 근태 원천·승인 효력·연차 원장은 추가되지 않았다. |
| 재직기간과 미해소 보완이 충돌 | 단건·일괄 수정에서 요청일이 재직기간 밖으로 빠지면 날짜를 안내하고 해당 저장을 되돌렸다. 이미 기간 밖에 있던 이관 건은 점검에 사번과 날짜를 표시했다. 두 사원의 재직기간을 바로잡은 뒤에도 원래 보완 세 건을 모두 유지했다. |
| 역할 변경·회사 격리·이력 보존 | 상태 조회·점검·저장·명령 재전송에서 현재 권한을 재확인했다. 두 POST에 CSRF를 적용했다. V29 자료·권한을 보존한 V30 이관, 이관 재실행, RLS와 앱 역할의 추가 전용 이력을 확인했다. |

## PC와 모바일 담당자 흐름

PC Chrome 1440×900은 2024년 3월, 같은 Chrome의 모바일 터치 에뮬레이션 390×844는 2024년 6월을 사용했다. 두 가상 시나리오에서 담당자가 생성한 업무 기록을 전용 PostgreSQL과 대조했다.

1. 필터로 화면에 표시된 확인 대상이 없어도 회사 전체 점검은 재집계 대상 한 건을 찾아 마감을 차단했다. 담당자가 해당 건을 재집계한 뒤 사유를 입력해 마감했다.
2. 마감한 달의 상세를 조회할 수 있었고 같은 날에 새 재집계를 제출하면 409로 차단됐다. 다른 탭의 사원 상세에서 마감월 이후의 마지막 재직일을 변경해 저장했다.
3. 원래 탭에서 사유를 입력해 재개하자 같은 조회 조건에서 재집계할 날짜가 다시 나타났다. 두 번째 재집계 후 재마감했다. 각 월에는 마감 → 재개 → 재마감 세 건이 순서대로 남았고 정상 휴무일의 실근로는 세 버전 모두 0시간이었다.

두 기기에서 업무 POST를 각각 12회 확인했다. PC 9개 화면과 모바일 8개 화면의 본문 너비가 뷰포트 안에 들어왔다. 페이지 JavaScript 오류는 0건이었다. Chrome의 기본 아이콘 요청 `/favicon.ico`는 403을 반환했다.

브라우저에서 사용한 JAR의 SHA-256은 `41a9c2e9bc2d93c0b749a6089609dab43de12fb325c9bed5ac97e277323f3088`이다. 빌드한 프런트 파일 101개가 JAR의 내용과 일치하고 V30 마이그레이션을 포함했다.
