# 월말 확인 대상 일괄 재집계 검증

[업무 명세](../superpowers/specs/2026-11-19-month-end-batch-recalculation.md) · [구현 계획](../superpowers/plans/2026-11-19-month-end-batch-recalculation.md)

## 승인된 정정과 남은 퇴근 누락

전용 로컬 PostgreSQL에서 사원 두 명에게 09시 출근 기록을 만들었다. 첫 사원에게 보완을 요청하고 18시 퇴근과 1시간 휴게가 포함된 정정을 승인했다. 두 번째 사원은 퇴근 기록이 없는 상태로 두었다.

- 담당자가 두 사원의 같은 날짜를 선택해 미리봤을 때 계산 실행 건수와 감사 건수는 그대로였다.
- 한 번의 실행으로 사원별 주간 집계가 두 건 생겼다. 첫 사원의 실근로는 8시간으로 확정됐고 보완 요청은 직원의 미해소 목록에서 빠졌다. 두 번째 사원은 실근로 미확정으로 남았고 ‘근무 확인 필요’로 다시 조회됐다. 원천 출근 기록은 두 건 그대로였다.
- 같은 날짜에 새 출근 기록이 생겼을 때 화면의 확인 사유가 같아도 미리보기의 계산 근거가 달라졌다. 일반 월말 조회 응답에는 내부 검증값이 노출되지 않았다.

## 원자성·재시도·권한

| 조건 | 전용 PostgreSQL 검증 결과 |
| --- | --- |
| 같은 페이지의 사원·근무일 50건 선택 | 두 사원에 걸친 주간 집계 8건과 일 결과 56건을 만들고 선택한 50건의 결과를 반환했다. 같은 사원의 떨어진 두 주만 선택했을 때 사이 주에는 결과가 생기지 않았다. |
| 같은 미리보기와 같은 명령을 동시에 실행 | 한 번만 계산하고 두 요청에 같은 결과를 반환했다. 이후 새 집계가 생겨도 이전 명령은 최초 결과를 반환했다. |
| 같은 미리보기로 다른 명령을 동시에 실행 | 먼저 실행한 명령만 저장됐다. 나중 명령은 변경된 근거를 감지해 409로 응답했다. |
| 두 번째 사원 처리 실패 | 첫 번째 사원에 대해 이미 계산하던 일 결과, 주간 실행과 감사가 모두 롤백됐다. |
| 권한·회사·페이지 경계 | CSRF 검증, 담당자 역할, 현재 기본 사원 자격을 검사했다. 기존 영수증 재전송에도 권한 회수가 적용됐고 다른 회사나 페이지의 행을 포함한 요청은 계산하지 않았다. |

## PC와 모바일의 담당자 흐름

최종 JAR로 로컬 Chrome PC(1440×900)와 모바일 터치 에뮬레이션(390×844)에서 다른 가상 사원 두 명씩을 사용했다. 2026년 10월의 마지막 주에서 4행을 선택했을 때 두 기기 모두 10월 26일~11월 1일의 계산 범위와 ‘사원별 주간 집계 2건’을 표시했다. 미리보기 전후 업무 DB 값이 같았고, 실행 뒤 각 기기에 주간 집계 2건과 일 결과 14건이 추가됐다.

| 선택한 날짜와 근거 | 두 기기에서 확인한 결과 |
| --- | --- |
| 10월 26일, 근무·휴게 확인 완료 | 실근로 8시간, 해소 |
| 10월 27일, 퇴근 기록 누락 | 실근로 미확정, 근무 확인 필요 |
| 10월 28일, 정정 결재 대기 | 실근로 미확정, 근무 확인 필요·정정 결재 대기 |
| 10월 31일, 근거가 있는 휴무 | 실근로 0시간, 해소 |

네 날짜의 상세 링크가 각각 저장된 일 결과를 열었다. 상세에서 돌아오면 조회 월·당시 소속·검색어·사유·페이지가 유지됐다. 실행 전후 원천 출퇴근 기록과 결재 이력을 대조했다.

PC에서는 저장 직후 목록 조회 한 번에 503을 반환하도록 로컬 브라우저에서 재현했다. 목록 갱신 대기와 실패 동안 이전 행과 링크는 숨겨지고 방금 저장된 결과 4건은 열람할 수 있었다. 목록 재조회 성공 뒤 추가 재집계 POST와 추가 DB 변경은 0건이었다. PC 11개 화면과 모바일 9개 화면에서 가로 넘침과 페이지 JavaScript 오류는 없었다. 브라우저가 자동 요청한 공통 `/favicon.ico`는 403을 반환했다.

## 자동 검증과 산출물

Maven 전체 검증에서 Java 단위 202개와 PostgreSQL을 포함한 통합 테스트 783개가 통과했다. 최종 화면 보완 뒤에는 두 응답 형식을 함께 요청하는 실제 브라우저 헤더로 HTTP 테스트를 강화했다. 최종 조합에서 관련 단위 25개와 통합 50개를 다시 실행해 실패·오류·건너뜀 0건을 확인했다.

최종 프런트엔드의 React 테스트는 58개 파일, 653개가 모두 통과했다. 월말 일괄 화면의 11개 테스트를 포함한다. 사유 입력 오류 후 수정, 세션을 다시 인증해야 할 때의 자료 숨김, 응답 유실 시 같은 명령 재전송, 목록 조회 실패 뒤 재조회까지 확인했다. TypeScript 검사와 Vite 프로덕션 빌드도 통과했다.

전체 Maven 검증본과 브라우저 최종 JAR을 대조한 결과 864개 파일 중 변경된 것은 프런트엔드 `app.js`와 `app.css` 두 개였다. 최종 JAR의 SHA-256은 `f355a377adaf8765d81bbd398d630f85540b4af5618e0601dd00f6df137df84a`이며, 프런트엔드 자원 101개가 빌드 출력과 일치했다. Flyway V29를 사용했다. 로컬 검증 앱과 전용 DB는 모두 종료했고 공개 데모 배포는 보류했다.
