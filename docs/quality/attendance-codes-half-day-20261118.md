# 근태코드·오전/오후 반차 로컬 검증

[업무 명세](../superpowers/specs/2026-11-18-attendance-codes-half-day.md)와 [구현 계획](../superpowers/plans/2026-11-18-attendance-codes-half-day.md)에 따라 전용 로컬 PostgreSQL과 합성 사원 두 명으로 확인했다. PC Chrome 1440×900에서 오전 반차를, 모바일 Chrome 터치 에뮬레이션 390×844에서 오후 반차를 신청했다.

| 직원·결재자 동작 | 담당자가 재조회한 원신청 | 직원 잔여 |
| --- | --- | --- |
| 신청 미리보기·제출 | 해당 오전 또는 오후 0.5일, 대기 | 2일 |
| 팀장 승인 | 실장 결재 대기 | 2일 |
| 실장 승인 | 승인·유효 | 1.5일 |
| 취소 신청·팀장 승인 | 원신청 유효, 취소는 실장 결재 대기 | 1.5일 |
| 취소 최종 승인 | 원신청 취소됨 | 2일 |

두 화면에서 담당자가 짧은 코드, 한글명, 기존 긴 코드로 연차를 찾았다. 휴가 신청 상세에서 목록으로 돌아왔을 때 조회 기간·사원·종류·상태도 유지됐다. 최종 JAR에서 연차 `A01`과 출퇴근·휴게 정정 `A02`를 번갈아 선택해 해당 유형의 정책 이력만 표시되는지 확인하고, 취소된 신청과 직원 잔여를 다시 조회했다. 두 화면 크기에서 페이지 오류와 가로 넘침은 없었다.

DB에서 원신청과 취소 총 4건의 결재 8단계를 확인했다. 사원별로 0.5일 차감 한 건과 이에 연결된 0.5일 복원 한 건이 있었고, 최종 잔여는 각각 2일이었다. 출퇴근 원천 기록은 두 사원 모두 0건이었다. 확인을 마친 후 브라우저 검증용 앱 두 개와 전용 DB를 종료했다.

## 기존 자료와 경계 조건

- 기존 고객사에 `A01`, `a03`이 있으면 연차에 `A04`를 부여하고 정정에는 `A02`를 부여했다. 다른 고객사는 연차 `A01`을 사용했다. 고객사 등록 코드와 기존 정책 버전, 신청, 결재, 원장 행을 마이그레이션 전후로 대조했다.
- 같은 날의 오전·오후 신청은 각각 허용하고, 대기·유효한 동일 구간이나 종일과 겹치는 신청은 차단했다. 휴일·잔여 부족, 반려·철회 후 재신청, 승인 명령 재전송·동시 처리도 검증했다.
- 날짜별 근거가 비어 있는 기존 연차는 캘린더에서 조회할 수 있고, 해당 일자 차감은 미확인으로 표시됐다. 반차일의 남은 근무 기록이 없으면 확인 대상으로 남았다. 검토용 Excel의 휴가량은 숫자 셀 0.5로 확인했다.
