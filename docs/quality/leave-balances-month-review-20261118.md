## 담당자와 직원의 업무 흐름

로컬 PostgreSQL에 가상 사원과 팀장·실장 결재선을 준비했다. PC Chrome 1440×900에서는 오전 반차를, 모바일 Chrome 터치 에뮬레이션 390×844에서는 오후 반차를 확인했다.

| 조작 | 조회한 결과 |
| --- | --- |
| 담당자가 한 사원의 기초 7.5일과 다른 사원의 −0.5일 조정을 같은 시트에서 미리보기 | 새 묶음은 0 → 7.5일, 조정할 묶음은 2 → 1.5일로 표시됐다. |
| 일괄 저장 후 사원별 원장과 직원 화면 재조회 | 기초·조정이 각 대상의 원장에 한 번씩 기록됐다. 직원 잔여는 7.5일이었다. |
| 직원이 반차를 신청하고 팀장·실장이 순차 승인 | 팀장 승인 뒤 7.5일이 유지됐다. 실장 승인 뒤 7일이 됐다. |
| 직원이 취소를 신청하고 팀장·실장이 순차 승인 | 팀장 승인 뒤 7일이 유지됐다. 실장 승인 뒤 원신청이 취소되고 7.5일로 복원됐다. |
| 담당자가 월말 확인 대상에서 조회 월·당시 소속·사번·정정 결재 대기로 검색 | 대상 근무일 한 행에서 정정 상세·근태 집계를 열었다. 대상일 재집계와 계산 근거 확인 후에도 같은 월·소속·사번·사유·페이지로 돌아왔다. |

두 직원의 DB 원장을 별도로 읽어 각각 7.5일 기초 1건, 0.5일 사용 1건과 그 사용 건에 연결된 복원 1건을 대조했다. 두 직원의 원신청·취소 신청에서 승인된 단계는 총 8건이었다. 정정 2건은 결재 대기로 유지됐고 각 직원의 출근 원천 1건이 보존됐다. 조정 대상 2명의 잔여는 각각 1.5일이었다.

## 자료 보존과 예외 처리

- 기존 정수 원장과 명령 재전송, 반차 차감·복원, 권한·테넌트 격리를 PostgreSQL V27 → V28에서 확인했다. 0.25일과 0.50000000000000001일은 거부했고 연도별 기초 합계에는 0.5일이 보존됐다.
- 본인 잔여 변경, 다른 회사의 묶음, 중복 행, 다른 저장으로 버전이 바뀐 묶음을 검증했다. 두 번째 행에서 DB 쓰기가 실패했을 때 첫 번째 행의 원장과 감사 기록도 롤백됐고 재전송으로 한 번만 저장됐다.
- 월말 조회는 서울 기준 당월의 어제까지와 과거 월의 말일, 입·퇴사일, 근무일 당시 소속, 휴일·종일휴가·반차, 정정 상태, 재집계가 필요한 저장 결과 및 사유 필터 적용 후 페이지 경계를 검증했다.

## 월말 조회 성능

300명·31일의 9,300 사원일과 원천 출퇴근 18,600건을 넣은 전용 로컬 DB에서 측정했다. 전체 사유 첫 페이지 50행은 289ms였고, 101쪽은 두 번 각각 2,274ms와 1,070ms였다. 사유를 지정한 첫 페이지는 28~97ms였다. 일곱 번의 서비스 호출에서 목록을 위한 MyBatis 조회는 매번 조직 1회와 날짜 후보 1회였다. 이 수치는 단일 로컬 환경 실측값이다.

## 브라우저와 자동 테스트

두 해상도에서 일괄 저장과 원장 재조회, 목록 복귀, 반차 승인·취소를 조작했다. PC에서 캡처 13장, 모바일에서 캡처 14장을 확인했고 두 환경에서 페이지 오류와 본문 가로 넘침이 없었다. 월말 대량 조회 최적화를 포함한 최종 JAR로 다시 로그인해 동일한 월말 목록, 계산 근거, 담당자 원장, 직원 잔여와 취소된 원신청을 재조회했다.

최종 코드에서 Java 단위 199건, 통합 753건과 React 631건이 모두 통과했다. Java 테스트에서 실패·오류·건너뜀은 0건이었다. TypeScript와 Vite 빌드도 성공했다. 최종 JAR에 포함된 프런트 파일을 빌드 산출물 전체와 바이트 단위로 대조했다. 확인 후 브라우저 검증용 앱 두 개와 전용 PostgreSQL 컨테이너를 종료했다. 공개 데모 배포는 보류했다.
